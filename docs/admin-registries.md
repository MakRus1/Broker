# Таблицы админки

Организации, сотрудники, ЖД-станции, порты и аэропорты фильтруются и сортируются
на сервере. Интерфейс запрашивает по 50 строк; при приближении к концу таблицы
автоматически запрашивается продолжение по next_cursor. При ошибке продолжения
загруженные строки остаются на экране, а повтор использует тот же курсор.

Поиск применяется кнопкой или Enter, фильтры сворачиваются. Сортировка доступна
по заголовкам столбцов; отдельного селектора сортировки в фильтрах нет.
Изменение запроса или организации отменяет старую загрузку и начинает первую
страницу; запоздавшие ответы не заменяют новый результат. Одновременные события
IntersectionObserver не создают повторных запросов одной страницы.

## API

Все четыре POST-ручки принимают query, sort, descending, limit (1–100) и cursor.
Ответ содержит items и optional next_cursor. Отсутствие next_cursor означает конец
списка; ровно limit строк больше не считается признаком наличия следующей страницы.

| Ручка | Дополнительные фильтры | Сортировки |
| --- | --- | --- |
| /api/admin/organizations/list | enabled | id, name, enabled |
| /api/admin/organizations/members/list | organization_id, enabled, role | subject, display_name, username, email, role, enabled |
| /api/admin/railway-stations/list | country_code | esr_code, name, country_code |
| /api/admin/route-locations/list | kind, country_code | id, name, code, country_code |

organization_id и kind обязательны в соответствующих запросах. query ищет буквальное
вхождение без учёта регистра: название организации; ФИО/логин/почту сотрудника;
название/код станции или транспортного пункта. Символы %, _ и обратная косая черта
не становятся шаблонами LIKE. Отсутствие enabled выбирает оба состояния; false
является полноценным фильтром. Глобальные справочники показывают неархивные записи.

В интерфейсе начальная сортировка — по названию или ФИО. Роль сотрудника сортируется
по названию роли организации, а не её внутреннему идентификатору. Для одинаковых
значений используются UUID, subject сотрудника или код ЕСР как вторичный ключ.

Старый after оставлен для используемого раньше порядка идентификаторов по возрастанию;
с другой сортировкой или одновременно с cursor он возвращает 400. Для справочников
поле next сохраняется для прежних клиентов, интерфейс админки использует next_cursor.
Курсор привязан к полному запросу, а для сотрудников — также к организации.
Изменение фильтров/направления или перенос курсора к другой организации возвращает 400.

## Реализация и доступ

Владельцы данных используют общий platform/registry_query.hpp. Описания полей
находятся в helpers/admin_registry.hpp каждого сервиса. SELECT с полями модели
остаётся в читаемом SQL-шаблоне; BFF передаёт типизированные запросы и курсоры.
Общий конструктор поддерживает текстовый идентификатор наряду с UUID, поэтому
пагинация сотрудников и станций не преобразует subject или ЕСР в UUID.

Правила доступа сохранены: организации и глобальные справочники доступны платформенному
администратору; сотрудники — администратору конкретной организации или платформы.
Organizations проверяет доступ до чтения сотрудников в той же транзакции, что и раньше.
Скрытие фильтра или колонки не является проверкой прав. Роли и правила поставок
внутри организации остаются отдельными формами; этот этап не меняет их контракты.

Индексы добавлены под начальный порядок по названию/ФИО и буквальное вхождение.
На каждый возможный столбец или сочетание фильтров индекс не создаётся. JOIN ролей
ограничен текущей организацией. SET LOCAL force_custom_plan не остаётся на соединении
после транзакции. Обычный CREATE INDEX при миграции может временно блокировать запись.

## Проверки

Сервисные тесты проходят страницы с повторяющимися ключами в обе стороны, комбинируют
поиск и фильтры, проверяют конец списка, организационную область и буквальные спецсимволы.
Тесты BFF проверяют доставку фильтров/курсора с cookie, CSRF и токеном пользователя.
Фронтенд-тесты загрузчика проверяют отмену и игнорирование старых ответов, защиту
от одновременной подгрузки и повтор после ошибки без потери уже полученных строк.
