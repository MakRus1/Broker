# Ревизия API и сервисов перед продажами

## Имена ручек

Начать с Shipments и Transportations. Эти сервисы дают примеры чтения карточки,
реестра, команд и межсервисных вызовов. После первого пакета применить
согласованные правила к остальным сервисам и BFF.

В текущем OpenAPI-кодгене на путь допускается один HTTP-метод. Имя клиента и
путь к обработчику выводятся из URL. Первый пакет пересматривает имена путей,
сохраняя методы, тела запросов и семантику операций. Общие префиксы
`/api/v1`, `/api/admin` и `/api/internal/v1` помогают найти границу API.

| Текущий путь после префикса | Кандидат | Что проверить |
| --- | --- | --- |
| `shipments/get`, `shipments/list` | Сохранить | Операции различаются по имени, обе принимают тело. |
| `shipments/transportation-contexts` | `shipments/route-contexts` | Пакетная выборка контекста для перевозок. Сверить имя с фактическим составом ответа. |
| `shipments/route-segments/register-usage` | `shipment-routes/register-usage` | Команда регистрации использования участков. Сохранить явное имя побочного эффекта. |
| `transportation-operations/create` | Сохранить до пересмотра создания перевозок | Это запуск операции, а `transportations/create` создаёт перевозку. Сначала проверить границы двух сценариев. |
| `shipments/ensure-created`, `transportations/ensure-created` | Сохранить | Внутренние команды гарантируют существование результата по ключу источника. |

Для каждого согласованного пути проверить исходный OpenAPI, экспорт контрактов
и `codegen.lock`, обработчики и сгенерированных клиентов, права в `service.yaml`,
HTTP-политики по путям, вызовы BFF и фронтенда, фикстуры и тесты. Для вызовов
между независимо выкатываемыми сервисами проверить порядок обновления и
необходимость временного алиаса.

## Ревизия сервисов

В обновлении маршрута поставки два последовательных запроса читают карточку
и `route_usage_version` до межсервисных проверок. Их можно заменить одним чтением,
чтобы получить оба значения из одного снимка и сэкономить обращение к БД.
Повторную проверку версии после блокировки строки в транзакции сохранить:
она защищает от пометки участка как используемого во время межсервисных проверок.

1. Сверить границы ответственности сервиса, владение данными и зависимости.
   Прочитать типовые ручки от входа до ответа. По обработчику должно быть видно,
   где проверяются права, какие компоненты и сервисы вызываются и где проходит
   граница транзакции.
2. Проверить маленькие обёртки и работу, которую можно исключить. Искать
   повторные проверки и загрузки, лишние межсервисные вызовы, перекладывание
   данных между моделями и JSON. Проверять вызывающие места до удаления.
3. Провести ревизию SQL. Проверить параметры, типы и лишние приведения,
   выбранные поля, блокировки и транзакции, дубли запросов, планы горячих
   запросов на репрезентативных данных. Учитывать работу со старыми записями.
4. Провести ревизию тестов. Проверить, какой сбой ловит каждый сценарий,
   покрыты ли права, повтор, конкурентный доступ и частичный отказ.
   Удалять дубли после проверки того, что остаётся проверка нужного поведения.

После ревизии пройти сценарий продаж от входящего запроса до поставки с
услугами. Включить запрос ставок по участку, котировку, предложение и согласование.
