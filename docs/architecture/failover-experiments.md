# Отказ узла и сетевой разрыв

Замеры ноября 2026 года выполнены на K3s, CloudNativePG 1.30.1 и PostgreSQL 16.
Узлы приложения и PostgreSQL были отдельными контейнерами на одной машине.
Ingress, оператор CNPG и Kubernetes API оставались доступны в здоровой части
стенда. Запись проверял тестовый HTTP-сервис. Подтверждённые записи сверяли по
UUID на новом primary. Задержку COMMIT измеряли отдельно с искусственной
задержкой сети.

| Сценарий | Наблюдение |
| --- | --- |
| Остановлены узел приложения и primary в одной локации | Чтение и запись восстановились через 75 с. Сохранились 74 из 74 подтверждённых записей. |
| Сетевой разрыв, асинхронная репликация, штатный smart shutdown | Уже открытая сессия старого primary продолжала фиксировать записи примерно 135 с после начала записи на новом primary. На новом primary отсутствовали 220 из 221 записей, подтверждённых локальным SQL-клиентам изолированной локации. |
| Сетевой разрыв, асинхронная репликация, `smartShutdownTimeout: 0` | Последняя запись на старом primary на 32-й секунде, первая на новом на 96-й. На новом primary отсутствовали 43 из 44 записей, подтверждённых в изолированной локации. |
| Строгое синхронное подтверждение, два экземпляра | Все 18 подтверждённых записей сохранились. Новый primary читал данные, запись возобновилась после возврата standby. |
| Строгое синхронное подтверждение, три экземпляра | Запись возобновлялась при сохранённом разрыве. В двух прогонах со штатными таймаутами первая запись прошла через 113 и 73 с. Сверка подтвердила сохранность всех 32 и 71 подтверждённых записей соответственно. |

В измерении по 400 последовательных транзакций в каждом режиме медианная
надбавка к COMMIT составила 0,22 мс на локальной сети, 10,39 мс при добавленной
задержке 10 мс и 30,52 мс при 30 мс. Оба режима ждали записи WAL на диск primary.
Рабочая нагрузка Broker и реальные межрегиональные RTT требуют отдельного замера.

Уменьшение `node-monitor-grace-period` с 50 до 35 с ускорило обнаружение узла
в одном прогоне примерно на 11 с. Запись восстановилась через 90 с, поскольку
CNPG ждал ответ `/pg/status` по открытому HTTPS-соединению около 30 с.
В отдельном сравнении на одной тестовой сборке CNPG уменьшение бюджета
`/pg/status` с 30 до 3 с сократило время первой записи с 89,9 до 62,5 с.
При ответе доступного тестового pod за 5 с короткий бюджет завершал запрос
ошибкой. Изменение отложено для MVP.

Для установки с требованием пережить потерю одной локации кандидат на
развёртывание включает три экземпляра PostgreSQL в независимых локациях,
`synchronous.method: any`, `number: 1`, `dataDurability: required`,
`failoverQuorum: true` и `smartShutdownTimeout: 0`. Перед внедрением нужны
замеры задержки под нагрузкой и тест потери локации с реальным размещением
приложения, БД, ingress и control plane.

Web BFF отдельно проверен на стейджинге. Одна сессия работала на двух репликах,
пережила замену пода и обновление токена. Для ограниченного набора Web GET
настроен повтор в Traefik. Локальная проверка потери ответа при создании
поставки показала, что повтор с тем же ключом возвращает ту же поставку.
