# Поставки и перевозки: первый серверный срез

`shipments` владеет поставкой (в интерфейсе НЛА — букингом), плановыми позициями и операциями создания перевозок. `transportations` владеет перевозками, маршрутами и последовательными транспортными плечами. Позиция «5 × 40HC» реализуется пятью перевозками; номер контейнера не является ID перевозки.

Это технически работоспособный контейнерный срез, а не полный перенос операционного учета. Воронка, тарифы, ЭДО, контейнерный парк, флот, деньги и UI пока не включены. Изменение маршрута с уже записанными фактами и отмена перевозок явно недоступны до определения правил.

## API

Сервисные OpenAPI находятся в `services/<service>/docs/api`, общие модели — в `docs/components/schemas`. Клиентские схемы экспортируются в `schemas/services/<service>`. Для создания объектов ключ идемпотентности пока передается как `idempotency_key` в JSON: текущий кодген не поддерживает header-параметры. Результат создания перевозок — `202` с операцией, завершение проверяется через `/api/v1/transportation-operations/get`.

В отличие от проектного наброска ответы оборачивают сущности именованными полями `shipment`, `item`, `operation`, `transportation`. Списки возвращают `items`, следующая страница запрашивается с `after`, равным ID последнего элемента. Порядок — UUID, стабильный курсор по ID, не хронологический порядок. Снимок всего списка между страницами не гарантируется. `limit` по умолчанию 50, максимум 100. Создание максимум 100 перевозок одной операцией.

Контейнерный код пока проверяется синтаксически, полноценный справочник еще не подключен. `customer_id` — внешний идентификатор: существование контрагента будет проверяться после подключения counterparties. Тип/SOC-COC позиции не меняются после создания; доступна отдельная команда изменения количества. SOC/COC не заменяет учет юридического владения активом.

## Авторизация

Оба сервиса проверяют JWT: issuer/JWKS из config_vars, audience и roles-client `broker-logistics`. Права: shipments.read/write, transportations.read/write; служебная команда требует отдельного transportations.create.

В каждой БД `tenant_memberships(issuer, subject, tenant_id)` содержит доверенную привязку. Публичного API назначения tenant нет; запись создается администратором через миграцию данных/контролируемую операцию. Обычному сотруднику нужна ровно одна привязка. Отсутствие и неоднозначность возвращают 403. Клиент не передает tenant в обычных запросах.

Служебный dispatcher получает client_credentials-токен. В БД transportations его subject привязывается к разрешенным tenant; служебное право само по себе не разрешает произвольный tenant. Нужно узнать реальный sub служебной учетной записи у выбранного OIDC-провайдера. Не использовать sub из примера как реальное значение. Обычным сотрудникам transportations.create не выдавать.

## Доставка и конкурентность

Операция shipments одновременно является долговечной outbox-записью. При создании блокируется только ее плановая позиция, а не все поставки. Сумма pending+succeeded не превышает план. Нельзя уменьшить план ниже зарезервированного/созданного количества.

Worker забирает одну due-операцию через `FOR UPDATE SKIP LOCKED`, выдает lease на 30 секунд и уникальный lease-token. HTTP идет вне транзакции. Потерянный ответ повторяется с прежним operation_id; receiver сохраняет inbox-результат и перевозки в одной транзакции. Просроченный worker не перезаписывает результат новой lease.

Отдельного callback нет: получатель повторно возвращает сохраненный результат. Таймаут, HTTP-ошибка и конфликт протокола сохраняют резерв. В этой версии все валидные поддерживаемые команды успешно создают перевозки; обработка терминального rejected в sender оставлена для последующих доменных отказов. Нельзя вручную переводить потерявшую ответ операцию в rejected без сверки получателя.

Для нескольких реплик используется тот же журнал и lease; локальное состояние pod не требуется для восстановления. Пулы и период worker нужно настраивать с учетом общего бюджета соединений. В первой реализации worker обрабатывает одну операцию за шаг, без обещания произвольного throughput.

## Хранение

Миграции `V0001__create_shipments.sql` / `V0001__create_transportations.sql` независимы. FK только внутри владельца, с tenant в ключах. Внешние shipment_id/item_id в transportations не имеют межсервисного FK.

Транзакционные команды и проверки количества/редакций реализованы именованными PostgreSQL-функциями; C++ repositories вызывают их через SQL-кодген. Это выбранная граница реализации данного среза: изменение правил функции требует новой миграции, не редактирования уже примененной V0001. Произвольного универсального диспетчера HTTP-команд нет: у каждого endpoint своя view и именованный метод Store.

Мутации сохраняют аудит в той же транзакции. Он не является техническими логами. Политика хранения и интерфейс просмотра аудита еще не реализованы. Данные первого среза не содержат денежных полей; точность валют и округление определяются до добавления финансов.

## Локальный запуск

1. Создать БД по миграциям средствами репозитория. Не подключать оба сервиса к одной схеме.
2. Настроить `pg-connection`, порты и auth issuer/JWKS в локальных config_vars.
3. Создать привязки сотрудников в tenant_memberships в обеих БД; роли выдать в OIDC клиенте broker-logistics.
4. Запустить transportations; указать его URL в `client-transportations-base-url` shipments.
5. Для worker задать `dispatcher-enabled: true`, token URL и client ID. Секрет передать через `SHIPMENTS_DISPATCHER_CLIENT_SECRET`, не записывать в Git. HTTP разрешать только в локальном тестовом контуре; для защищенного контура выключить auth-allow-http и использовать HTTPS endpoint провайдера.
6. Запустить shipments. По умолчанию dispatcher выключен, чтобы шаблон локальной конфигурации не делал запросы с отсутствующими учетными данными. Pending не означает успешную доставку.

Автоматическое создание realm/служебных ролей, привязок реальных сотрудников, CD и раскатка новых сервисов в действующий staging этим изменением не выполняются.

## Проверки

Testsuite каждого сервиса использует настоящую PostgreSQL и подписанные тестовые JWT. Проверяются конкуренция за количество, inbox-повторы, tenant-изоляция, редакции, маршруты и исправление фактов. В shipments внешний transportations в тесте worker мокается: получатель сохраняет результат, возвращает ошибку первой попытки, затем отвечает тем же результатом. Отдельный smoke `tests/integration/logistics_smoke.py --build-dir build-debug` запускает две реальные реплики каждого сервиса с отдельными тестовыми БД и временным OIDC-сервером, проверяет создание 3+2 перевозок и общие счетчики. Запускается Python из testsuite-venv, PostgreSQL binaries выбираются через POSTGRES_BIN (по умолчанию /usr/lib/postgresql/16/bin). В CI проверка выполняется в Debug.
