# Архитектурный обзор Broker

Базы остаются в ведении своих сервисов. При создании поставки из продажи Sales
хранит задачу доставки в outbox, а Shipments записывает поставку и ключ источника
в одной транзакции. Повтор после потери ответа находит уже созданную поставку.
Обработчики outbox берут задачи через `SKIP LOCKED` и подтверждают их по токену
аренды и поколению записи. [Отправитель](../../services/sales/src/components/shipment_dispatcher.cpp) ·
[Получатель](../../services/shipments/src/components/shipments.cpp) ·
[Запросы outbox](../../libs/outbox/postgresql/queries)

Штатный `/ping` проверяет состояние процесса и компонентов. В закреплённой
версии userver PostgreSQL наследует состояние `kOk`. При `sync-start: true`
пул ждёт первых попыток подключения и логирует их сбои. Сервисы с outbox
дополнительно проверяют его схему при старте. После запуска `/ping/ready`
проверяет состояние зарегистрированных зависимостей. Запросы к primary
выполняются при обработке операций приложения. Kubernetes использует этот адрес для startup и readiness.
[Проверка схемы](../../libs/outbox/src/component.cpp) ·
[Готовность Shipments](../../services/shipments/src/bootstrap/ping.cpp) ·
[Настройки проб](../../scripts/staging_manifest.py)

Web BFF и Admin BFF хранят сессии и незавершённые попытки входа в памяти
процесса. Для нескольких взаимозаменяемых реплик нужно общее хранилище обоих
видов состояния. Проверка перед экспериментом по локациям: начать вход на
одной реплике, завершить на другой и продолжить работу после потери первой.
Отдельно проверить переключение PostgreSQL primary при отказе узла, задержку
записей между локациями и допустимую потерю подтверждённых записей.
[Состояние сессий](../../libs/browser/include/platform/browser/sessions.hpp)

Дальнейший порядок работ:

1. Документировать параметры SQL рядом с запросами.
2. Добавить UUID в OpenAPI-кодген и проверить совместимость JSON и PostgreSQL.
3. Выделить повторяемую механику реестров в библиотеку. Поля, права и выборку
   конкретного реестра оставить в сервисе.
4. Сократить пути API и унифицировать создание перевозок.
5. Отдельно определить право чтения Inbox и порядок согласования ФИО между
   Keycloak и локальной БД при частичном сбое.
6. Решить, нужен ли сервис пользователей, когда определим владельца профиля
   и место хранения состояния браузерных сессий.
