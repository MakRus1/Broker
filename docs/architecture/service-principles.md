# Broker: общие требования к сервисам

Согласовано 20 октября 2026. Применяется ко всем новым и изменяемым сервисам, включая инфраструктурные. Для существующего кода это требование к развитию, а не заявление, что все пункты уже реализованы. Документ применяется при ревью каждого нового сервиса и изменении существующих.

## Масштабирование и изменение

- HTTP-процессы не хранят единственную копию сессий, очередей и бизнес-состояния в памяти или на локальном диске. Добавление реплик не должно менять корректность процесса.
- Фоновые задачи поддерживают несколько реплик: lease/блокировки, идемпотентная обработка, восстановление после падения, ограничение конкурентности. Не запускаем по полному независимому планировщику на каждом pod без координации.
- Каждая реплика имеет ограниченные пулы БД/HTTP, таймауты и очереди. Увеличение pod учитывает общий бюджет соединений и нагрузку на зависимости; автомасштабирование приложения не масштабирует БД автоматически.
- Сервис масштабируется и выпускается независимо. Нет чтения чужих таблиц, общей транзакции разных сервисов или необходимости одновременно обновить все сервисы.
- Контракты и события версионируются совместимо; миграции по expand/contract с учетом старых и новых реплик. Миграции не запускаются конкурентно всеми экземплярами приложения.
- Domain, сценарии, адаптеры хранения/HTTP и сборка зависимостей разделены; небольшое изменение сценария не требует менять универсальный обработчик всего сервиса. Сгенерированный и ручной код отделены.
- Чтение ограничено пагинацией; исключены неограниченные ответы, загрузка всего дерева объектов и непроверенные N+1. Индексы выбираются по запросам и проверяются на реалистичных объемах.
- Наблюдаемость показывает насыщение пулов, очереди, задержки, ошибки и возраст фоновых задач. ID бизнеса/tenant не используются как labels метрик.
- Масштабируемость проверяется по целям нагрузки и отказным сценариям. Пока объемы/целевые задержки не заданы, нельзя обещать произвольный рост без изменений.

## Владение данными и FK

Внутри базы одного сервиса FK используются там, где нужна ссылочная целостность. В shipments позиция ссылается на поставку; в transportations плечо — на перевозку. tenant включается в состав ссылки/уникальности, чтобы FK не допускал связь между клиентами. Это дополняет, но не заменяет проверку доступа на чтение и запись.

Между сервисами только логические ID и явные контракты, без FK даже при временном размещении их таблиц на одном PostgreSQL-сервере. Пример: transportation.shipment_id не является FK в базу shipments. Проверки, снимки и обработка отсутствующего/изменившегося объекта определяются бизнес-сценарием.

FK имеет стоимость проверок и блокировок при изменениях. Индекс на ссылающихся полях рассматривается явно: PostgreSQL не создает его автоматически. Не применяем массовые каскадные удаления к истории бизнеса без отдельного решения.

Несколько pod приложения с одной БД совместимы с локальными FK. Размещение связанных строк в разных независимых шардах — другая задача: обычный FK не дает межшардовой гарантии. Если появится такая потребность, связанные данные по возможности размещаются на одном шарде; кандидатом ключа распределения является tenant, но решение требует анализа размеров отдельных клиентов, запросов и hot spots. Присутствие tenant_id само по себе не делает приложение шардированным.

Партиционирование внутри PostgreSQL не равно шардированию. Для уникальных/первичных ключей партиционированных таблиц учитывается ключ партиционирования; это влияет и на ссылки. Не партиционируем все бизнес-таблицы заранее только ради гипотетического роста.

Источники: PostgreSQL 16 Constraints https://www.postgresql.org/docs/16/ddl-constraints.html ; CREATE TABLE https://www.postgresql.org/docs/16/sql-createtable.html .

## Применение к первому срезу

Поддержать минимум две одновременно работающие реплики каждого сервиса в проверке очереди/повторов и конкурентных команд; провести rolling restart при незавершенной операции создания. Зафиксировать бюджет соединений и верхние пределы batch/list. Отдельно проверить план SQL и конкуренцию за одну позицию; сериализация изменения одной позиции намеренная, глобальной блокировки tenant/всех поставок быть не должно.

Код и инфраструктура этим документом не изменены.

## Читаемость и развитие кода

- Бизнес-правила находятся в C++, PostgreSQL хранит данные и обеспечивает целостность/конкурентный доступ. Бизнес-функции, триггеры и другая исполняемая логика в БД требуют отдельного обоснования.
- Ручки и repositories обмениваются именованными моделями. Ручная сборка JSON по строковым ключам допускается на границах сериализации и для документов хранения/аудита, а не вместо типизированных команд.
- Для `std::optional` явно используем `.has_value()` при проверке, `.value()` после проверки и `.value_or(default)` для замены отсутствующего значения. Не используем неявное преобразование в bool и `operator*`/`operator->` для optional. Это правило относится и к генерируемому C++.
- SQL форматируется с явными колонками и понятными параметрами; миграция представляет связное изменение хранения. Изменение прикладного правила само по себе не требует миграции.
- OpenAPI группируется по предметным сценариям; отдельный YAML на каждый endpoint не обязателен. Описания ошибок объясняют причину конкретного статуса.
- Компоненты подключаются/отключаются стандартным `load-enabled`. Для приостановки работы без перезапуска при необходимости вводится отдельный динамический конфиг; он не уничтожает компонент и не отменяет уже выполняющиеся операции.
