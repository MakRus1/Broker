# Компоненты сервиса поставок

HTTP-обработчики проверяют права, выполняют сценарий обращения к компонентам и
формируют HTTP-ответ. Компоненты отвечают за операции с данными, правила и интеграции;
транзакционные изменения остаются внутри компонента-владельца.

| Компонент | Ответственность |
| --- | --- |
| `ShipmentsComponent` | Карточки поставок, выбор и проверка логиста, единое создание, идемпотентность, регистрация использования маршрута |
| `SettingsComponent` | Платформенные ограничения, правила организации и клиента, справочники настроек |
| `ShipmentRegistryComponent` | Запросы реестра и значений фильтров |
| `ShipmentRoutes` | Подготовка маршрута, проверка его контрагентов, транспортных пунктов и использования участков перевозками |
| `ContainerPlanComponent` | Запись и чтение плана контейнеров |
| `TransportationOperationsComponent` | Постановка и чтение операций создания перевозок |
| `CargoSuggestionsComponent` | Подсказки описания груза и их удаление |
| `TransportationDispatcher` | Доставка команд создания перевозок и проекции маршрута |
| `platform::notifications::Dispatcher` | Доставка событий в сервис уведомлений |
| `CargoSuggestionsCleanup` | Периодическая очистка подсказок |

Сопоставление плана контейнеров с фактом и незавершёнными операциями выполняют
свободные функции в `container_plan_calculation`, без компонента и доступа к БД.

Выбор логиста из карточки клиента и проверка его членства в организации принадлежат
ShipmentsComponent, который использует клиентов контрагентов и организаций.
ShipmentRoutes работает с транспортными пунктами, контрагентами маршрута и перевозками.
Во views остаются выбор между явно указанным и клиентским логистом, порядок подготовки
маршрута, проверка редакции и сохранение. Внешние запросы выполняются до транзакции записи.

Уведомления и команды перевозок регистрируются разными компонентами в общем outbox.
Для каждого типа задач библиотека запускает отдельные периодики `outbox/<topic>/<slot>`,
с отдельными лимитами параллелизма и метриками. Повторы, lease и подтверждение доставки
остаются общими; отдельной очереди или собственного цикла для уведомлений нет. Общий диспетчер находится в `libs/notifications` и принимает тип компонента клиента
Notifications и тип запроса публикации, сгенерированные для конкретного сервиса.
Оба компонента включаются существующим `dispatcher-enabled`. Маршрут для проекции
преобразуется в клиентскую модель Transportations до сериализации в outbox.

Компоненты получают конкретные зависимости из `ComponentContext`. Фоновые компоненты
не создают полный `Deps` сервиса. Преобразования моделей находятся в `src/converters`,
описание реестрового запроса — в `src/registry/query.hpp`, модели источника создания
и контейнерного плана — в `src/models`. Общие операции с транзакциями, аудитом,
идемпотентностью и outbox остаются в специализированных helpers.
Создание, обновление и проверка данных карточки, а также поиск изменённых участков
находятся в `helpers/shipment_card`: это свободные функции без DI и доступа к БД,
они не являются компонентом userver.

Именованные модели запросов и результатов генерируются из схем. Переименование
моделей не меняет JSON-контракт. Создание поставки, запись связи с источником,
аудит и постановка событий сохраняют общую транзакцию. Проверки связанных
справочников выполняются до транзакции изменения карточки, как и раньше.

Проверки: сборка сервиса, testsuite поставок, интеграционный сценарий поставок и
перевозок, актуальность кодогенерации и форматирование.
