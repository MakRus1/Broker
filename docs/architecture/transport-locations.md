# Транспортные пункты

Сервис `transport_locations` владеет общими для организаций справочниками портов,
аэропортов и ЖД-станций. Он хранит записи, предоставляет поиск, пакетное чтение для
проверки маршрутов и административное управление. Маршруты, даты и бизнесовые
правила остаются в Shipments и Transportations.

Ручное добавление, редактирование и архивирование в админке требуют прав
платформенного администратора. Внешние справочники обновляются компонентами
синхронизации: аэропорты — из OurAirports, морские порты — из UN/LOCODE,
ЖД-станции — из OSM. Периоды, повторы и включение загрузок задаются динамической
конфигурацией.

## Компоненты

- `LocationsComponent` отвечает за поиск, пакетное чтение, административный реестр,
  сохранение и архивирование портов и аэропортов.
- `RailwayStationsComponent` предоставляет те же операции для ЖД-станций.
- `AirportSync`, `SeaPortSync` и `RailwaySync` загружают, проверяют и публикуют
  соответствующий внешний справочник. HTTP-загрузка и разбор ответа выполняются
  до открытия транзакции публикации.
- `DirectorySyncComponent` управляет арендой запуска и расписанием повторов в БД.
  Он используется всеми тремя загрузчиками и предотвращает одновременный запуск
  одной синхронизации несколькими репликами сервиса. Публикация проверяет аренду
  в своей транзакции; при ошибке планируется повтор с прежней политикой задержек.

HTTP-ручки проверяют административный доступ и передают типизированные запросы
компонентам. Компоненты возвращают сгенерированные модели; ошибки преобразуются
общей HTTP-обвязкой. `converters` содержит преобразования строк БД, внешних выгрузок
и настроек синхронизации. `registry` — определения полей и построение запросов
реестров. В `helpers` остаются CSV-парсер, общие параметры транзакций и SPARQL-запрос.
JSON-контракты, SQL, правила доступа и алгоритмы синхронизации при выделении
компонентов не меняются.

## Потребители

BFF сохраняют прежние внешние URL, но обращаются к новому сервису. При сохранении
морских/авиационных данных Shipments пакетно получает активные пункты по UUID;
Transportations получает активные ЖД-станции по ЕСР. Эти HTTP-вызовы происходят
до открытия транзакции записи. При недоступности справочника возвращается 503,
а изменения не сохраняются. Уже сохранённые снимки маршрутов не требуют загрузки
справочника для чтения и остаются видимыми после архивирования записи.

Поиск и пакетное чтение требуют существующих бизнесовых прав shipments.read или
transportations.read соответственно; они проверяются через Organizations так же,
как прежде. Само административное управление по-прежнему требует platform.admin.

## Перенос существующих данных

Первый серверный переход выполняется через Deploy all, включающий новый сервис
и оба BFF, Shipments и Transportations. После применения миграций staging.py:

1. Проверяет отметку однократного переноса в целевой БД.
2. При её отсутствии требует совместный деплой всех потребителей.
3. Останавливает старые Shipments/Transportations и ждёт завершения их подов,
   чтобы административные изменения не потерялись между экспортом и переключением.
4. Через scripts/transport_location_transfer.py переносит оба справочника одной
   транзакцией, сохраняя UUID, ЕСР, коды, названия и архивное состояние.
5. Запускает новые образы обычным этапом deployment.

Первый переход включает короткую недоступность поставок и перевозок. Повторные
деплои пропускают перенос. При ошибке до commit старые реплики восстанавливаются;
при ошибке после успешного переноса нужно повторить Deploy all. После переключения
обновлять сервисы можно отдельно. Откат к образам до выделения сервиса требует
обратного переноса данных и в этом ПР не автоматизирован.

Локальное окружение выполняет тот же перенос отдельной задачей Compose до запуска
новых потребителей. При обновлении уже работающего стенда сначала собираются
образы/бинарники, затем останавливаются прежние владельцы, выполняется перенос
и запускаются новые версии.

Повторный запуск не затирает последующие ручные правки. Несовпадающие существующие
ID или конфликт уникального кода прерывают перенос; частичного результата нет.
Старые таблицы пока сохраняются как источник для перехода и восстановления.
Удаление этих таблиц — отдельная миграция после подтверждения серверного перехода.
Типы снимков, используемые в бизнесовых сущностях, удалять при этом нельзя.
