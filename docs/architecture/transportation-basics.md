# Перевозки и маршрут поставки

## Владение данными

Shipments хранит порядок, стабильные UUID и типы участков маршрута поставки.
Transportations хранит поля конкретной перевозки, плановые и фактические даты её участков.
Изменение порядка или добавление участка в поставке видно во всех перевозках при следующем чтении.
Локальные данные связываются с UUID участка, а не с его позицией.
Поля этапов, общие для поставки, будут добавляться в модель Shipments на следующем этапе.

Incoterms, загрузка и условия перевозки читаются из поставки. Они не дублируются в таблице
перевозок и не принимаются API изменения перевозки. Для списка перевозок контексты поставок
загружаются одним пакетным запросом, без отдельного HTTP-запроса на каждую строку.

Основные поля перевозки: тип (сборка, контейнер, авиа, негабарит, ЖД, судно), опасный груз,
необязательные тип и принадлежность контейнера. Контейнерные поля принимаются только для
контейнерной перевозки. Фактический номер контейнера вводится вручную и не генерируется.
В реестре, карточке и вкладках используется этот номер, а при его отсутствии — тип и «Без номера».
Техническим идентификатором перевозки остаётся UUID; номер контейнера не обязан быть уникальным.
Подсказка в UI проверяет общий формат: четыре латинские буквы и семь цифр.
Она не блокирует сохранение нестандартного номера. Структура номера описана у
[BIC](https://www.bic-code.org/identification-number/).

## Ручное создание

`POST /api/v1/transportations/create` доступен с `transportations.write` независимо от
плановых контейнеров. `id` — UUID новой перевозки и ключ повтора команды. Повтор с тем же
телом возвращает тот же результат, другое тело с тем же ключом — конфликт.
`item_id` и `operation_id` отсутствуют у ручной перевозки. Создание из плановых позиций
продолжает использовать существующий inbox/outbox без изменения протокола.

## Запрет удаления заполненного участка

Перед записью данных или факта Transportations проверяет запрос и регистрирует использование
участка в Shipments с ожидаемой редакцией поставки. Регистрация и изменение маршрута
блокируют одну строку поставки, поэтому удаление не может обогнать новую запись данных.
Shipments запрещает удаление или изменение типа зарегистрированного участка; перестановка
и добавление новых участков разрешены. Записанные факты сохраняются при редактировании
плановых данных перевозки.

Все HTTP-вызовы выполняются до открытия локальной транзакции записи. Проверка старых
данных обращается к `/api/v1/transportation-routes/usage`, который читает только БД
Transportations и не вызывает Shipments обратно. Регистрация использования также читает
только БД Shipments: рекурсивного HTTP-вызова нет.

Защита консервативна: если после успешной регистрации процесс упал до записи локальных
данных, участок остаётся защищённым. Использование не снимается автоматически, в том
числе после очистки полей: ранее записанные значения остаются в истории.

Самостоятельные маршруты старых перевозок не удаляются. Участки, которых нет в маршруте
поставки, возвращаются с `inherited: false` и доступны в UI только для просмотра.

## Доступ

Пакетные контексты раскрывают только маршрут и общие условия и требуют
`transportations.read`; регистрация — `transportations.write`. Оба API проверяют
доступ пользователя к организации через общий auth. Получение старого использования
участков требует `shipments.write`. Полный доступ к карточке поставки не добавляется
неявно к праву просмотра перевозок.

## Выкатка

Новые ручные перевозки имеют NULL в связях с плановой позицией и операцией. Сначала нужно
обновить все реплики Transportations: старые бинарники с проекцией `transportation_v2`
не умеют читать такие записи. После создания ручных перевозок откат на старый бинарник
не поддерживается; миграции назад не выполняются.

## Переход от технических номеров

Проекция `transportation_v4` и новый API используют необязательный `container_number`.
Старый числовой `number` не возвращается и не используется новым кодом. Столбец и прежние
DB-проекции пока сохраняются для старых реплик на время обновления; удаление возможно
отдельным этапом после выкатки. Старые снимки команд при повторе читаются без технического номера.

## Ошибки сохранения участков

Shipments возвращает `shipment_revision_conflict`, если изменилась редакция поставки,
и `route_changed`, если запрошенного участка больше нет в её маршруте. Transportations
перехватывает типизированный `Error409` и передаёт код и сообщение, не подменяя остальные
причины конфликта. Web показывает серверное сообщение и для данных участка, и для фактов.

## Детали железнодорожных участков

`rail` и `international_rail` используют общую модель `RailDetails`. Данные принадлежат
конкретной перевозке и привязаны к стабильному ID участка из поставки. Перевозчик —
`contractor_id`, выбранный из справочника контрагентов. ТН ВЭД не относится к участку.

ETD, ETA, отправление поезда, прибытие на станцию назначения и выгрузка хранятся как
календарные даты `YYYY-MM-DD`. Пустые значения отсутствуют. Для фактических дат действует
диапазон от 1900 года до текущего дня по Europe/Moscow; плановые даты могут быть будущими.
Проверяется последовательность ETD → ETA и отправление → прибытие → выгрузка.
Изменения фиксируются обычным аудитом маршрута и защищаются `expected_revision`.
Общий API фактов с временными метками не изменяет календарные даты ЖД.

Детали хранятся типизированной OpenAPI-моделью в существующем документе участка.
История сохраняет полный снимок. Старые временные метки остаются читаемыми;
при первом редактировании UI переносит их календарный день в поля ЖД, исходные метки сохраняются.
Заполненные ЖД-детали учитываются при защите участка от удаления и смены типа в поставке.

### Справочник станций

Transportations владеет таблицей `railway_stations`, Web BFF проксирует поиск через
`/api/geography/railway-stations`. Поиск по названию или префиксу кода возвращает до 20 записей.
Код ЕСР — строка из шести цифр, включая ведущие нули. При сохранении сервер получает
название и страну из справочника. Ранее сохранённый снимок станции остаётся пригодным
для редактирования остальных полей, если запись исключили из справочника.

Справочник общий для всех организаций. Администратор платформы ведёт его в разделе
«Станции» админки: создание, редактирование и архивирование. В миграции нет
неполного начального набора; внешние источники пока не подключены. Подробнее:
[Общий справочник станций](railway-directory.md).

Участки в просмотре и редактировании по умолчанию свёрнуты. Их можно раскрывать
по одному или все сразу.
Раскрытие сохраняется в текущей браузерной сессии. Автоматическое завершение и сворачивание
участков пока не вводятся.

Морские и авиационные данные заполняются в карточках этапов маршрута поставки.
В перевозках они доступны только для просмотра и наследуются при чтении.
[Поля моря и авиа](shipment-shared-route-details.md).

## Международное авто и вывоз

Детали международного авто и вывоза принадлежат перевозке и привязаны к стабильному ID
участка маршрута поставки. Международное авто хранит терминал погрузки, плановые даты
погрузки и выгрузки, фактические даты выхода и выгрузки, номера машины, прицепа и CMR.
Вывоз хранит плановые и фактические даты вывоза и доставки, город, страну и адрес доставки,
водителя текстом, номер машины и дату ТТН. Перевозчик выбирается из контрагентов организации.
Город и адрес вводятся вручную; выбор города в справочнике заполняет его страну.
Данные поставки в эти поля автоматически не подставляются.

Все даты задаются календарным днём. Фактические даты ограничены сегодняшним днём,
нижняя граница всех дат — 01.01.1900. Плановые и фактические интервалы проверяются
отдельно. Участки с заполненными данными нельзя удалить или сменить им тип в поставке.
