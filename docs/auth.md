# Авторизация административного API

Keycloak отвечает за вход пользователей, MFA, сессии и выдачу OIDC access token.
Сервисы самостоятельно проверяют подпись и разрешения через `libs/auth`.
Собственный сервис пользователей/паролей сейчас не нужен. Доступ к компаниям,
поставкам и другим бизнес-сущностям будет проверяться в бизнес-модулях; роли
Keycloak не заменяют эти проверки.

## Configs

Все `/admin/...` доступны только на внутреннем listener и требуют
`Authorization: Bearer <access_token>`. Публичные `/configs/values` и `/configs/status`
сохраняют сервисный протокол без пользовательского токена; сетевой доступ к ним
ограничивается инфраструктурой. Административные токены обычным сервисам не выдаются.

| Разрешение клиента `configs-admin` | Операции |
| --- | --- |
| `configs.read` | Каталог, текущее значение, история, просмотр драфтов и событий |
| `configs.write` | Создание, редактирование и отмена своего драфта |
| `configs.approve` | Подтверждение чужого драфта и публикация |

Права независимы: подтверждающему для работы админки нужны `configs.read` и
`configs.approve`. Даже обладатель всех прав не может подтвердить свой драфт.
Автор берется из проверенных `iss` и `sub`, хранится как `iss#sub`. Имя пользователя
может меняться, эта идентичность остается прежней. Поле `actor` в запросах запрещено.
Перед обновлением старой dev-базы завершите или отмените активные драфты со строковым
actor: они автоматически не связываются с OIDC-пользователями. Исторические записи сохраняются.

Без токена или с невалидным токеном возвращается 401 и `WWW-Authenticate: Bearer`;
без нужного разрешения — 403. При отсутствии пригодного кеша ключей — 503.
Наличие метода в сгенерированном клиенте не дает разрешения на его вызов.

## Проверка и подключение

Используется jwt-cpp v0.7.2, закрепленный commit и SHA256 архива в
`libs/auth/CMakeLists.txt`; подключаются только заголовки. Проверяется только RS256,
доверенный issuer, audience, обязательные exp/iat/sub, временные ограничения,
Keycloak payload `typ: Bearer` и клиентские роли `resource_access`. Допуск часов —
10 секунд. ID token, refresh token, сторонний issuer/audience и неподдерживаемые
алгоритмы отклоняются. RSA-ключ должен иметь не менее 2048 бит.

В `service.yaml` подключается `libraries: [common, auth]`, регистрируются
`platform::auth::Component` и отдельный `userver::components::HttpClient`
с именем `auth-http-client`. В `platform-http-pipeline.extra-middlewares` добавляется
`platform-auth`. Его статическая конфигурация задает доверенные `issuer`, `audience`,
`roles-client`, `jwks-url`, защищаемый префикс и таблицу путь → разрешение.
Неизвестный защищенный путь закрыт по умолчанию. Конфигурация Configs служит примером.

Адрес ключей задается оператором, из JWT URL не берутся; перенаправления отключены.
JWKS загружается при старте и каждые 15 секунд. Неизвестный kid инициирует фоновое
обновление не чаще раза в 5 секунд; первый запрос может получить 401, следующий
после обновления пройдет. При недоступности провайдера старый кеш используется до
`max-key-age-seconds` (по умолчанию 300). Затем административный доступ закрывается.
Недоступность Keycloak не блокирует чтение опубликованных конфигов другими сервисами.
Отзыв роли/сессии учитывается при истечении access token; мгновенной introspection нет.

Для окружений кроме локального нужны HTTPS issuer/JWKS, `auth-allow-http: false`,
свой realm/client, короткоживущие токены, реальные пользователи и управление секретами.
Внутренний listener не публикуется наружу. Флаги локального HTTP явно заданы только
в dev-конфигурации; библиотека по умолчанию запрещает HTTP.
Токены, заголовок Authorization и тела документов не добавляются в прикладные логи.

## Локальный стенд

`make local-up` поднимает Keycloak 26.8.1 и отдельный PostgreSQL с собственным volume.
Образы закреплены по digest, поддерживаются Linux amd64/arm64. Адрес:
http://localhost:18888, realm `broker`. Порт привязан только к loopback.
Локальные пароли генерируются один раз в `.local/auth-secrets.json` (права 0600):
`admin-password`, `author-password`, `reviewer-password`. Логины — `admin`, `author`,
`reviewer`; admin относится к master realm. Файл не отслеживается Git.
В `.local/broker-realm.json` и `.local/compose.yaml` также есть локальные секреты:
не публикуйте содержимое `.local`.

Шаблон realm лежит в `tools/local/keycloak/realm.template.json`. Импорт выполняется
при первом старте и не перезаписывает существующий realm: дальнейшее изменение
ролей/пользователей существующего стенда выполняется через консоль Keycloak.
Удалять БД для обновления настройки не требуется. `make local-down` сохраняет данные.
Потерянные локальные секреты не меняют уже импортированные учетные записи автоматически.

Для seed и smoke существуют **только локальные** client credentials:
`local-author` (read/write), `local-reviewer` (read/approve). `ConfigAdmin` получает
разные подписанные токены для создания и подтверждения. Эти клиенты не переносятся
в production. Обычные сервисы не получают административных ролей.
BFF использует пользовательский вход Authorization Code + PKCE,
держит токены на сервере и отдает браузеру защищенную session cookie.
Клиент `broker-admin` подготовлен для PKCE/device flow; password grant отключен.
Реализация и ограничения первого интерфейса: [админка Configs](admin-ui.md).

## Контракты и тесты

OpenAPI поддерживает стандартные `components.securitySchemes` с HTTP bearer JWT и
`security` на уровне документа/операции; `security: []` делает операцию публичной.
Остальные механизмы security явно отклоняются генератором. Защищенный C++-метод
клиента требует явный access token вторым аргументом; автоматически распространять
входящий токен между произвольными сервисами не нужно.
Серверный обработчик защищенной операции требует проверенный Principal в контексте,
поэтому без auth middleware бизнес-код не выполнится. Настройка прав остается в
компоненте; генератор не выводит бизнес-разрешения из URL.

Функциональные тесты Configs используют временные RSA-ключи и подписанные токены.
Мокается только JWKS endpoint: проверка подписи и прав не обходится.
`admin_client` — удобная тестовая фикстура; для отказов используется `monitor_client`
и явно заданный токен. Тесты проверяют права, подмену actor, самоподтверждение,
неверные подписи/claims, ротацию и доступ со старым кешем при сбое провайдера.

Официальная документация: [OIDC endpoints Keycloak](https://www.keycloak.org/securing-apps/oidc-layers),
[Authorization Code и PKCE](https://www.keycloak.org/securing-apps/javascript-adapter),
[jwt-cpp v0.7.2](https://github.com/Thalhammer/jwt-cpp/releases/tag/v0.7.2).
