# Следующий этап: типизированные клиенты

Это проект решения; секция clients пока не реализована и отвергается текущей
валидацией service.yaml. Она не должна молча игнорироваться.

## Контракт и подключение

Исходный OpenAPI сервиса — единый источник серверного и клиентского API.
Отдельную клиентскую спецификацию экспортируем только как воспроизводимый артефакт
или явно выбранное подмножество операций, без ручной копии контракта.
Пример будущего manifest потребителя:

```yaml
clients:
  shipments:
    service: shipment
    transport: http
```

Имя shipments определяет клиент в Deps и конфигурации. Поле service ссылается
на поставщика контракта в монорепозитории. Адрес, учетные данные, таймауты,
пулы и лимиты задаются через конфигурацию окружения, а не зашиваются в C++.
Для внешнего API можно позже добавить ссылку на зафиксированный контракт.

У каждой операции потребуется уникальный, стабильный operationId, допустимый
как имя C++ метода. Например, operationId: ApiV1FooBar дает:

```cpp
const auto response = deps.shipments.ApiV1FooBar(request);
```

Текущий серверный генератор еще не использует operationId для именования;
его обязательность, проверка коллизий и правила имен — часть будущей реализации.

## Поведение клиента

- Типизированные Request и ответы по объявленным HTTP-статусам.
- Явное различие между ответом API, транспортной ошибкой, таймаутом
  и несоответствием ответа контракту. Ожидаемые 404/409 не теряются в общей ошибке.
- Корректные path/query, enum, default, JSON, Content-Type и ответы без тела.
- Автоматическая передача контекста трассировки, deadlines и отмены;
  метрики без идентификаторов документов в labels.
- Повторы по умолчанию выключены. Включаются явно для подходящих операций;
  создание сущности требует отдельного решения об идемпотентности.
- Отдельный transport-адаптер для моков и testsuite внешних HTTP-сервисов.
- Собственные клиентские DTO не зависят от серверных handler-классов,
  ComponentContext и метаданных разбора входящего HTTP-запроса.

## Генерация и CI

Код клиента создается в каталоге сборки потребителя. Явный make gen обновляет
учитываемые в Git настройки/lock-файлы; check-gen остается немутирующим.
CMake зависит от контрактов поставщика и генератора. Изменение контракта должно
пересобирать и проверять потребителей через граф clients в service.yaml.
Это зависимость от контракта, а не линковка с исполняемым сервером.
Взаимные HTTP-вызовы не должны создавать цикл CMake-targets серверов.

Для gRPC сохраняем штатный protobuf/userver-кодогенератор клиентов;
manifest должен подключать его и унифицировать конфигурацию и Deps.
Сам транспортный код gRPC повторно не реализуем.

Начать стоит с одного HTTP-клиента между двумя тестовыми сервисами:
GET/POST, path/query/body, enum/default, 201/204, ошибки API, таймаут
и связанная трасса. После этого определить версионирование контрактов
и проверку несовместимых изменений.
