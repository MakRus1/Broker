# Контракт кодогенерации

Поддерживается OpenAPI 3.0.3 с GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS.
Каждый путь имеет ровно один HTTP-метод. Поле operationId запрещено.
Каждая операция получает независимые `Request`, `ResponseNNN` и `Handler`.
Ответ — `std::variant` типов по статусу, даже если схемы тела совпадают.
Каталог и namespace выводятся только из пути: `/foo/bar` → `src/views/foo/bar`
и `views::foo::bar`, без уровня HTTP-метода. Для `/` используется root.
Параметр `{id}` становится by_id; дефисы заменяются на подчеркивания.
Клиентский метод строится в PascalCase: `/api/v1/foo/bar` → ApiV1FooBar,
`/items/{id}` → ItemsById. Оконечный слеш, кроме `/`, запрещен.
Повтор пути, эквивалентные шаблоны URL и коллизии имен после преобразования
отклоняются, в том числе между разными серверными файлами спецификации. Клиентские копии
в серверную генерацию не включаются. Пути `/admin/...` автоматически получают
`monitor-handler: true` и обслуживаются только внутренним listener.

## Типы и ограничения

- Path/query: string, integer (int64 по умолчанию), number (double), boolean.
- `int32`, `int64`, `float`, `double` задают соответствующий тип C++.
- Boolean в URL принимает только `true` и `false`; повтор параметра отклоняется.
- JSON-тело: object со скалярными полями, общими моделями через `$ref`, свободными
  JSON-объектами и массивами этих типов.
  Свободный объект объявляется как `type: object, additionalProperties: true` и становится
  `userver::formats::json::Value`. Типизированные вложенные объекты объявляются в
  `components.schemas` либо `docs/components/schemas` и подключаются через `$ref`.
  Default и uniqueItems для массивов
  объектов пока отклоняются явно. Типы и ограничения именованных конфигов
  дополнительно проверяются каталогом схем Configs.
- `enum` скалярных значений становится `enum class`; сериализация сохраняет значения контракта.
- Строковые форматы: `uuid`, `date`, `date-time`, `byte`, `password`.
  UUID имеет форму с дефисами; даты проверяются по календарю. Date-time принимает
  RFC3339 с обязательным часовым поясом, без leap seconds; byte — base64.
  Password остается строкой, без дополнительных правил сложности.
- Числа: minimum/maximum, exclusiveMinimum/exclusiveMaximum и multipleOf.
  Для floating point кратность проверяется с допуском; это не денежный тип.
- Строки: minLength/maxLength в кодовых точках Unicode, pattern.
- Массивы: minItems/maxItems, uniqueItems; ограничения элементов проверяются отдельно.
- Pattern использует RE2: нет lookaround, backreferences и повторений свыше 1000.
- `additionalProperties: false` запрещает неизвестные поля.
- Поддерживаются локальные `$ref: '#/components/schemas/Name'`, в том числе в полях,
  элементах массивов и параметрах. Цепочки ссылок разрешены, циклы запрещены.

Необязательные поля без default и необязательное тело представлены через `std::optional`.
Поле с default имеет обычный тип и сразу содержит дефолт. Переданный параметр
перезаписывает это значение; для его чтения не нужен специальный accessor:

```cpp
request.limit;                 // Переданное значение или default.
request.WasProvided("limit");   // Отдельная метаинформация, если она нужна.
```

WasProvided отвечает, передал ли клиент поле явно. Для limit с default 10 отсутствие
параметра дает limit=10 и false; ?limit=10 дает то же значение и true.
Для чтения обычного значения этот метод не нужен.

Флаги присутствия есть у Request, RequestBody и общих object-моделей и не меняют способ чтения значений.
Ноль, false и пустая строка считаются переданными значениями. Для поля JSON с `nullable: true` используется `std::optional<T>`: null — пустое
значение, обычное значение — заполненное. Если поле еще и необязательное без default,
тип — `std::optional<std::optional<T>>`: внешний optional различает отсутствие поля
и его передачу. Null не разрешается для полей без nullable; внутри свободного JSON он
сохраняется. Nullable задается на inline-схеме поля, не рядом с `$ref`; nullable в корне
именованного компонента и nullable path/query пока явно отклоняются.
`required: true` по-прежнему требует явной передачи поля, даже если указан default.

Default и значения enum проверяются по типам и ограничениям при чтении спецификации.
Неизвестные format, неподдерживаемые конструкции и противоречивые ограничения
вызывают ошибку генерации. Типизированные inline-объекты в полях нужно вынести в
общие схемы. OneOf/allOf, сетевые и рекурсивные ссылки, security кроме HTTP bearer JWT и apiKey cookie и нестандартная
сериализация пока не поддерживаются.

Ошибки входного запроса возвращают 400 без исходного содержимого запроса.
JSON-тело требует application/json с необязательными параметрами.

## Общие модели

```yaml
components:
  schemas:
    ConfigInfo:
      type: object
      additionalProperties: false
      required: [name, version]
      properties:
        name:
          type: string
        version:
          type: integer
          minimum: 0
# В схеме ответа:
# properties:
#   items:
#     type: array
#     items:
#       $ref: '#/components/schemas/ConfigInfo'
```

Серверные типы находятся в `<openapi/models.hpp>`, namespace `<service>::models`.
В HTTP-клиенте модели принадлежат `<consumer>::clients::<alias>::models`.
Объект становится структурой; скаляр или массив — alias; enum — `enum class`.
Inline-enum поля общей модели получает имя `<Model>_<field>`. Для удобного общего
имени enum объявляйте отдельным компонентом и используйте `$ref`.

Модели генерируются один раз на сервис/клиент и объявляются в порядке зависимостей.
Одинаковые определения одного имени в нескольких спеках объединяются;
разные определения и конфликты с генерируемыми именами отклоняются.
Схемы можно объявлять внутри `components.schemas` либо в отдельных файлах
`docs/components/schemas`. Во втором случае файл содержит набор именованных схем:

```yaml
# docs/components/schemas/drafts.yaml
ConfigDraft:
  type: object
  additionalProperties: false
  required: [id]
  properties:
    id:
      type: integer
      minimum: 1
```

Например, из `docs/api/admin/configs/drafts/get.yaml`:

```yaml
schema:
  $ref: '../../../../components/schemas/drafts.yaml#/ConfigDraft'
```

Внутри файла компонентов `#/ConfigDraft` — ссылка на другую его схему;
`configs.yaml#/ConfigInfo` — на соседний файл. Имена генерируемых типов берутся
из имен схем, а не из имен файлов. Ссылка на одноименную схему через локальный alias
также поддерживается. Межфайловые ссылки направляются в `docs/components`, а не в
файлы других ручек. Поддерживаются YAML/JSON и JSON Pointer.

Все файлы компонентов проверяются, включая неиспользуемые. Генератор не обращается
в сеть, не читает файлы вне каталога контрактов и проверяет симлинки до чтения.
Компоненты учитываются в codegen.lock и зависимостях CMake. Экспортер переносит
транзитивно нужные файлы в `schemas/services/<service>/components`, пересчитывает
относительные ссылки и сохраняет прежние пути API-файлов. Подкаталог `components`
в клиентских копиях зарезервирован, поэтому не размещайте ручки в `docs/api/components`. Фильтрация ручек не
экспортирует файлы компонентов, нужные только исключенным ручкам; выбранный файл
компонентов копируется целиком вместе со своими зависимостями.

Если все тело запроса/ответа задано через `$ref`, DTO `RequestBody`/`ResponseNNN`
сохраняет непосредственный доступ к полям этой схемы. Статусы остаются разными
C++-типами даже при одинаковой схеме тела; варианты ответа не становятся дубликатами.
Вложенные ссылки уже имеют общий именованный тип, например
`std::vector<::configs::models::ConfigDraft>`.

Разбор, сериализация, default и проверки ограничений вложенных полей генерируются
для сервера и клиента. Плохой входной запрос дает 400, нарушение ответа сервера — 500,
невалидный ответ удаленного сервиса — `platform::http::ContractError`.

## Ответы

Поддерживаются явные статусы 200–599, JSON object, text/plain и ответы без тела.
HEAD и 204 не могут объявлять тело. Ключ ответа `default`, интервалы статусов
и несколько media types не поддерживаются. Генератор устанавливает статус и Content-Type.
Значения JSON-ответа также проверяются: неверная ручная реализация приводит к 500.

## Файлы и зависимости

`make gen SERVICE=broker` из корня или `make gen` из `services/broker` создает только
отсутствующие view.hpp/view.cpp, обновляет handler-блок конфигурации и codegen.lock.
Существующий ручной код не перезаписывается.

`src/deps.hpp` общий на сервис: он содержит `Deps` и `ResolveDeps`. При его наличии
все обработчики получают этот тип зависимостей. Добавление файла требует `make gen`.
В сервисе с PostgreSQL общий Deps обеспечивает зависимость обработчиков от компонента БД.

CMake генерирует DTO/обработчики в каталоге сборки, отслеживает изменения контракта
и генератора, не изменяет исходники. `make check-gen-all` ничего не исправляет.
Из каталога результата удаляются только файлы из собственного manifest генератора.

Формат C++ закреплен на clang-format 18.1.8 и `.clang-format`: отступы и продолжения
по 4 пробела, без выравнивания по первому аргументу; определения разделены пустой строкой.
Генератор сам форматирует
новые файлы и добавляет комментарии закрытия namespace. `make check-format` проверяет
ручной код, `make format` явно форматирует его. Для результата сборки:

```sh
.venv-gen/bin/python scripts/check-format.py --generated build-debug/services/broker/generated
```

## SQL

Запросы сервиса находятся в `postgresql/queries/*.sql`. Встроенный
`userver_add_sql_library` генерирует именованные `storages::Query` в каталоге сборки.
Например, `upsert_user.sql` становится `broker::sql::kUpsertUser`, доступным через
`<broker/sql_queries.hpp>`. Значения передаются параметрами `$1`, `$2`, без склейки SQL.
Изменение/добавление SQL автоматически учитывается при сборке.

Это генерация именованных запросов, а не ORM или автоматически выведенных типов БД.
Типизированные SQL DTO и денежные типы нужно определить перед бизнес-разработкой.

Enum из OpenAPI генерируется как `enum class` с именем поля в пространстве имен обработчика. Например, поле `status` со значением `success` можно вернуть как `.status = status::Success`. Преобразование в строку JSON выполняется автоматически. Значения получают PascalCase: `new` превращается в `New`, `in_transit` — в `InTransit`. Исходные строки JSON сохраняются. Недопустимые имена и коллизии после преобразования отклоняются с диагностикой. Запрос и ответ с одноименным enum используют общий тип; допустимые значения проверяются отдельно по каждому контракту.

Подключение инфраструктуры и библиотек: [service-manifest.md](service-manifest.md).
Структура сервиса и использование Deps: [service-layout.md](service-layout.md).

Клиентский экспорт и `client-api.yaml`: [инструкция](client-codegen.md).
Если контракт 400 содержит обязательные string-поля `error` и `message` без дополнительных
ограничений, ошибки разбора запроса возвращают этот JSON-контракт с `invalid_request`.

Для совместимости `/configs/values` со штатным клиентом userver в `requestBody`
указано `x-validate-content-type: false`: содержимое по-прежнему разбирается и
проверяется как JSON, но заголовок Content-Type не проверяется. По умолчанию
остальные ручки требуют `application/json`. Служебные поля клиента принимаются;
переопределения по сервису и окружению пока не применяются.

Cookie-аутентификация (`type: apiKey`, `in: cookie`) поддерживается серверным
кодгеном: обработчик требует проверенную личность в request context. Проверку
cookie и создание личности выполняет middleware сервиса (пример — `admin_bff`).
Генератор C++-клиентов явно отклоняет такие операции: браузерную сессию нельзя
неявно заменить bearer-токеном. Экспорт клиентских OpenAPI-схем cookie сохраняет.
