# Драфты конфигов

Пользователь нажимает «Редактировать» в админке и меняет значение в редакторе.
До нажатия «Готово» серверный драфт не создается. На «Готово» сервер проверяет схему,
обязательные поля, ограничения и предикаты. Невалидное значение возвращает 400 без
создания драфта. Другой пользователь подтверждает валидный драфт, и конфиг публикуется
в той же транзакции. Отдельных шагов отправки на проверку и публикации нет.

Управление доступно в админке и через внутренний API.

## Ограничения и согласованность

- Один драфт относится к одному конфигу; у конфига может быть только один активный драфт.
  Это обеспечено проверкой в транзакции и частичным уникальным индексом PostgreSQL.
- Состояния: `draft`, `published`, `cancelled`. Последние два неизменяемы и позволяют
  создать следующий драфт. Отменять или изменять активный драфт может только его автор.
- Редактирование существующего драфта тоже принимает только валидное значение.
- Каждое изменение увеличивает `version`. Подтверждение требует `expected_version`:
  правки после открытия страницы проверки не будут подтверждены по ошибке.
- У каждого конфига своя версия: изменения других конфигов не мешают подтверждению.
  Последовательность A → B → A тоже изменяет версию и считается конфликтом.
- Конфликт не публикует значение. Автор отменяет драфт и открывает редактор заново.
- Подтверждение повторно валидирует значение по текущим схемам, проверяет другого автора,
  версию конфига и драфта; затем атомарно сохраняет рабочую ревизию, закрывает драфт
  и добавляет событие. Никакой частичной публикации при ошибке не происходит.

События содержат actor, действие, снимок драфта и время. Они хранятся в БД, не в технических
логах; правила доступа и хранения полноценного пользовательского аудита определим отдельно.

## Внутренний API

Все ручки описаны в `services/configs/docs/api/admin/...` и реализованы отдельными
`src/views/admin/.../view.cpp`. Они доступны на внутреннем listener (обычно `127.0.0.1:8092`).
На публичном listener маршруты `/admin/...` отсутствуют. Экспорт клиентской спеки включает
их для будущего BFF; права доступа проверяются сервисом. Публичные `/configs/values` и `/configs/status` сохранены.

| Путь | Тело | Результат |
| --- | --- | --- |
| GET `/admin/configs/list` | — | `items`: каталог имен, версий и ID активных драфтов |
| GET `/admin/configs/history` | — | `items`: история опубликованных ревизий |
| POST `/admin/configs/current` | `config_name` | Рабочие `value`, `version`, `active_draft_id` |
| POST `/admin/configs/drafts/create` | `config_name`, `expected_config_version`, `value`, `description` | 201, валидный драфт |
| POST `/admin/configs/drafts/get` | `id` | Драфт с `base_value` и предложенным `value` |
| POST `/admin/configs/drafts/list` | необязательные `config_name`, `before_id` | До 100 драфтов, новые первыми |
| POST `/admin/configs/drafts/edit` | `id`, `expected_version`, `value` и/или `description` | Новая версия драфта |
| POST `/admin/configs/drafts/approve` | `id`, `expected_version` | Подтверждение и публикация, `published_revision` |
| POST `/admin/configs/drafts/cancel` | `id`, `expected_version` | Отмена автором |
| POST `/admin/configs/drafts/events` | `id` | События с историческими снимками |

Ответы списков и событий содержат массив `items`. Необязательные поля (например,
`active_draft_id` у `current` без драфта) могут отсутствовать.

`current.version` передается в `create.expected_config_version`: если конфиг изменился,
пока пользователь работал в редакторе, создание возвращает 409. При наличии
`active_draft_id` админка должна открыть существующий драфт вместо создания нового.

Для отката создайте драфт с `source_revision` вместо `value`. Из этой исторической
ревизии берется только указанный конфиг, проверяется по текущей схеме, затем действует
обычное подтверждение. Номер 0 означает сохранённую ревизию 0, а не встроенные значения схемы. Если конфига в указанной ревизии не было, возвращается 404.

Ошибки: 401 — отсутствует/невалиден access token; 503 — нет пригодного кеша JWKS;
400 — невалидное тело/значение, 403 — недостаточно прав, чужая правка/отмена или самоподтверждение,
404 — отсутствующий драфт/ревизия, 409 — активный драфт уже существует, устарела версия
или драфт закрыт. Ответ содержит `error` и `message`; неуспешная операция не изменяет БД.

### Пример

```sh
curl -sS http://127.0.0.1:8092/admin/configs/current \
  -H "Authorization: Bearer $AUTHOR_ACCESS_TOKEN" -H 'Content-Type: application/json' -d '{"config_name":"SHIPMENT_TERMS_CONFIG"}'

# expected_config_version берется из предыдущего ответа.
curl -sS http://127.0.0.1:8092/admin/configs/drafts/create \
  -H "Authorization: Bearer $AUTHOR_ACCESS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"config_name":"SHIPMENT_TERMS_CONFIG","expected_config_version":0,"description":"Новые условия","value":{"clauses":[],"default":{"is_enabled":true,"max_days":60}}}'

# id и expected_version берутся из ответа создания/редактирования.
curl -sS http://127.0.0.1:8092/admin/configs/drafts/approve \
  -H "Authorization: Bearer $REVIEWER_ACCESS_TOKEN" -H 'Content-Type: application/json' -d '{"id":1,"expected_version":1}'
```

## Авторизация и прямые записи

Токен проверяется библиотекой `libs/auth`: подпись, issuer, audience, срок действия
и разрешение операции. Автор берется из проверенных `iss`/`sub`; передавать `actor`
в теле запрещено. Подробнее: [авторизация](auth.md). Префикс `/admin` дополняет
проверку прав и сетевую изоляцию внутреннего listener.

Прямых ручек публикации и отката нет. Начальные конфиги и локальная smoke-проверка
также создают валидный драфт и подтверждают его от другого actor. История рабочих
ревизий доступна через GET `/admin/configs/history`.

Миграция `V0002__create_config_drafts.sql` добавляет таблицы версий, драфтов и событий.
На существующей базе начальная версия каждого известного сохраненного конфига берется
из последнего снимка; после обновления она меняется только при изменении этого конфига.


Ручки вызывают именованные методы `ConfigStore`: `CreateDraft`, `EditDraft`,
`ApproveDraft`, `CancelDraft`, `GetDraft`, `ListDrafts`. Аргументы и результаты —
обычные структуры из `src/models/`; строкового диспетчера операций нет.
Ошибки `InvalidRequest`, `DraftForbidden`, `RevisionNotFound`, `RevisionConflict`
явно переводятся во view в ответы 400/403/404/409. Неожиданные ошибки хранения
и преобразования данных остаются серверными ошибками, а не ответами 400.

JSONB-документы преобразуются в модели в `src/repositories/draft_document.cpp`.
JSON значений конфигов сохраняется, поскольку их схемы задаются отдельно.
Общие HTTP-схемы описаны в `services/configs/docs/components/schemas/`:
`drafts.yaml`, `configs.yaml`, `revisions.yaml`, `errors.yaml`. Ручки в `docs/api/`
ссылаются на них через относительные `$ref` и остаются в отдельных YAML-файлах.

`src/models/draft.hpp`, `config.hpp`, `revision.hpp`, `event.hpp` содержат
обычные структуры, доступные компонентам, репозиториям и ручкам.
Преобразования в сгенерированные DTO сгруппированы по тем же сущностям в
`src/models/*_conversions.hpp`; общего файла всех преобразований нет.
JSON-сериализация списков и вложенных снимков выполняется кодгеном.
Необязательные поля списков, например approved_by до подтверждения, опускаются;
active_draft_id в каталоге явно содержит null, если активного драфта нет.


## Создание и удаление

Создание доступно любому пользователю с `configs.read` и `configs.write`, в том числе
разработчику. Должность и роль администратора не проверяются. В админке выберите
«Создать конфиг», задайте имя вида `MY_CONFIG`, JSON-объект и описание. В API
передайте `expected_config_version: 0` для нового имени. До подтверждения
`current.value` и `draft.base_value` равны null, значение не выдаётся сервисам.
Для ещё не созданного имени `current` также возвращает null и версию 0.
Первоначальная публикация — обычная ревизия с реальным временем из БД.

Удаление также выполняется драфтом: в `drafts/create` передайте `remove: true`
и текущую версию, без `value` и `source_revision`. У драфта удаления `value: null`.
После подтверждения конфиг исключается из текущей выдачи и каталога, но история
публикаций и драфтов сохраняется. Версия удаления сохраняется для защиты от устаревших
запросов. Для восстановления передайте эту версию и `source_revision`, в которой
конфиг ещё существовал. Историю удалённого конфига можно получить через `drafts/list`
с его `config_name`; `current` вернёт null и версию удаления.

Подтверждает другой пользователь с `configs.read` и `configs.approve`.
Автоматической регистрации и очистки при деплое нет. Создавайте обязательные конфиги
до выкладки потребителя: при отсутствии обязательного значения его readiness зависит
от заданной политики `critical_dependencies` и допустимости кеша/встроенных значений.

Configs проверяет известные схемы из своего каталога. Для нового имени без схемы
проверяются имя и JSON-объект; структуру проверяет типизированный потребитель.
Неизвестные ключи не требуют пересборки Configs. Имя `BROKER_CONFIG_DELIVERY_META`
зарезервировано для метаданных доставки.


## Самоподтверждение в тестовом окружении

В статическом компоненте `config-draft-policy` параметр `allow-self-approval`
берётся из `configs-allow-self-approval` файла переменных. По умолчанию он false.
В `services/configs/configs/config_vars.staging.yaml` включён true; staging-рендерер
накладывает `config_vars.<environment>.yaml` на базовые переменные до настройки адресов.
Для других окружений без такого файла действует базовый запрет.

При включении автор может подтвердить свой драфт, только если у него есть
`configs.read` и `configs.approve`. Проверка версий, валидация и аудит сохраняются.
Админка получает этот признак от Configs, поэтому отдельная настройка BFF не нужна.
Изменение статической настройки требует перезапуска Configs.
