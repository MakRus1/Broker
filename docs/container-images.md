# Готовые окружения в GHCR

`ghcr.io/makrus1/broker-dev` содержит два многоплатформенных окружения Linux amd64/arm64:

- dev: Clang 18, инструменты, зависимости и установленный userver Debug + Release;
- sanitize: те же инструменты, userver Debug с ASan+UBSan.

Исходники Broker в образ не включаются. Санитайзеры инструментируют framework
и приложение; CMake проверяет соответствие выбранного режима маркеру установки.
При несовпадении окружения сборка останавливается, а не использует обычные библиотеки.
Нативная сборка macOS продолжает работать независимо от опубликованных образов.

## Обычная разработка и CI

```sh
make docker-pull
make docker-test-debug
make docker-test-release
make docker-test-sanitize
```

Make выбирает dev или sanitize по команде. Для нескольких режимов выполняйте
отдельные make-команды, чтобы выбор образа был однозначным.
CI выполняет только pull закрепленного digest и сборку/тесты Broker.
Проверки не требуют права записи в registry; публикация использует отдельный workflow.
Успешный CI result по-прежнему обязателен для merge.

Dev Container использует dev-образ. Изменения его image применяются после Rebuild Container.
Для быстрого запуска санитайзеров используйте docker-test-sanitize с хоста;
в обычном dev-контейнере можно собрать framework с санитайзерами из исходников,
но для этого нужно использовать окружение без BROKER_USERVER_PREFIX.

Пакет рекомендуется сделать публичным: тогда pull работает без входа, в том числе
для PR из fork. Для приватного пакета CI того же репозитория входит через GITHUB_TOKEN;
локальному пользователю нужен docker login ghcr.io с read:packages.
При первой публикации GitHub создает приватный пакет. Его видимость меняется
в настройках пакета: Package settings → Change visibility → Public.
Связь с репозиторием задается label org.opencontainers.image.source.

## Обновление окружения

Отдельный Publish environment запускается при push с изменением:
Dockerfile, build-userver.sh, apt-packages.txt, versions.env, python-constraints.txt,
requirements.txt или самого механизма публикации. Он доступен и вручную.
Push в ветки этого репозитория считается доверенным; PR из внешних fork ничего не публикуют.
Первая сборка тяжелая, последующие обычные PR используют результат независимо от ветки.

1. Измените зависимости в своей ветке и отправьте изменения.
2. Дождитесь Publish environment: четыре нативных сборки, затем два multiarch manifest.
3. Выполните `make lock-images`, отправьте lock-файл и devcontainer.json в тот же PR.
4. Дождитесь обычного CI, проверяющего Broker в новых образах.

Для локальной команды обновления нужен Docker с Buildx и доступ к пакету.
Версия окружения вычисляется SHA-256 по полному содержимому входных файлов,
включая их пути. Теги `<hash>-dev` и `<hash>-sanitize` находят опубликованные версии;
используемые digest записаны в tools/container-images.json.
CI не использует latest и не переключается автоматически на новый образ.
Если зависимости изменились, а lock не обновлен, инструменты CI завершаются ошибкой
с инструкцией. Lock проверяется до запуска дорогой матрицы.

Опубликованные теги повторно не перезаписываются. Между ветками переиспользуется
один образ для одинаковых входов, а Docker layer cache ускоряет обновления самого образа.
Изменение workflow публикации без изменения входов не создает новую версию окружения.

## Локальная сборка образа

```sh
make docker-image
make docker-test-debug DOCKER_IMAGE=broker-dev:userver-3.2
```

Это запасной путь для проверки Dockerfile до публикации. Для локального sanitizer-образа:

```sh
docker build --target sanitize -f tools/Dockerfile -t broker-dev:sanitize .
make docker-test-sanitize DOCKER_IMAGE=broker-dev:sanitize
```

Политика хранения старых digest определяется отдельно: удалять образы,
на которые ссылаются поддерживаемые ревизии, нельзя.
