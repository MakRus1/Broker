# Критические зависимости: проект политики

Этот документ описывает следующий этап. Проверка обязательного получения динамических
конфигов перед готовностью сервиса сейчас не реализована. Текущий updater допускает
запуск со встроенными значениями; включение обновлений само по себе этого не меняет.

Предлагаем разделить живость процесса и возможность обслуживать бизнес-запросы.
`/ping` остается доступен, пока процесс работает. `/ping/ready` и бизнес-обработчики
должны учитывать обязательные зависимости. Это позволит прогреть кеш или дождаться
конфигов, не перезапуская исправный процесс. Одной проверки readiness недостаточно:
до готовности прямой запрос тоже должен получать 503.

Для конфигов потребуется явная политика по каждому ключу: допустим ли встроенный
fallback, можно ли стартовать с проверенным дисковым кешем, какой возраст значения
приемлем. Пригодность определяется по происхождению, версии схемы и времени последнего
успешного обновления. Источник этих метаданных нужно добавить к Snapshot отдельно;
сегодня публичный API возвращает только типизированные значения.

При временной недоступности configs сервис продолжает использовать последний
допустимый snapshot до истечения заданного срока. После истечения сервис снимает
готовность и прекращает зависимые операции. Ошибка получения не должна очищать
рабочий кеш. Для необязательных конфигов остаются встроенные значения.

Такую политику стоит подключать через `service.yaml` после реализации метаданных,
общего readiness gate и тестов запуска без сервера, с валидным/просроченным кешем,
при недоступности после старта и при восстановлении. Синтаксис manifest пока не вводим.
Для PostgreSQL уже есть проверка готовности; configs дополнительно проверяет доступ
к таблице ревизий. Эта проверка не заменяет будущую общую политику зависимостей.
