# Критические зависимости и готовность

`platform::Readiness` объединяет проверки обязательных ресурсов. Готовность процесса
и порядок создания компонентов userver — разные вещи: существующий клиент еще не
означает, что необходимый ресурс доступен. Исключение в конструкторе по-прежнему
останавливает запуск. Механизм ниже позволяет уже созданным компонентам сообщать
о временной неготовности без перезапуска процесса.

Для сервисов с service.yaml реестр и middleware регистрируются генератором.
В старой ручной обвязке без manifest gate включается после регистрации компонентов
platform::Readiness и platform::HttpReadinessFactory и добавления их static_config.
Телеметрия старой обвязки продолжает работать без этих компонентов.

## Поведение HTTP

- `/ping` на внутреннем listener сообщает живость и доступен при неготовых зависимостях.
- `/ping/ready` возвращает 503, пока сервис не запущен полностью, есть fatal-компонент
  или не готова зарегистрированная обязательная зависимость.
- Общий HTTP middleware возвращает 503 до аутентификации и бизнес-обработчика.
  Прямой HTTP-запрос не обходит readiness. Уже начатые запросы не прерываются.
- Внутренний listener, метрики и тестовый tests-control продолжают работать.
- Восстановление зависимости автоматически открывает прием новых запросов.

Для gRPC пока сохраняется прежнее поведение: аналогичный middleware нужно добавить
отдельно. Проверки PostgreSQL в `/ping/ready` тоже сохранены; они пока не зарегистрированы
в общем реестре и не выполняются перед каждым бизнес-запросом. Общий gate сам по себе
не превращает все внешние системы в критические зависимости.

## Обязательные конфиги

```yaml
version: 1
libraries: [common, configs]
configs: [SHIPMENT_TERMS_CONFIG]
critical_dependencies:
  configs:
    SHIPMENT_TERMS_CONFIG:
      allow_builtin: false
      allow_cache: true
      max_age_seconds: 300
```

После изменения выполните `make gen`. Ключ должен быть подключен сервисом явно
или автоматически вместе с HTTP-клиентом. Неизвестные имена, опечатки в политике
и неверные типы отклоняются до записи файлов.

`allow_builtin` по умолчанию false, `allow_cache` — true. `max_age_seconds` обязателен,
допустим диапазон 1..31536000. Если ключ не перечислен в critical_dependencies,
он не влияет на готовность. Сервисы без политик сохраняют работу со встроенными
значениями. Для обязательного удаленного значения включите доставку:

```yaml
config-updates-enabled: true
config-server-url: http://configs:8090
config-cache-path: /var/cache/broker/dynamic-config.json
```

При выключенной доставке и запрещенном builtin процесс запускается, но бизнес-HTTP
и readiness остаются закрыты. Это не ошибка загрузки процесса. Не добавляйте такую
политику самому configs для ключей, которые он должен раздавать: получится зависимость
инфраструктурного сервиса от собственной доступности.

## Источник, возраст и схема

```cpp
const auto snapshot = deps.configs.GetSnapshot();
const auto metadata = snapshot.GetMetadata(configs::SHIPMENT_TERMS_CONFIG);
// metadata.Source: Builtin, Cache, Remote или Incompatible.
// metadata.LastSuccessfulUpdate: время последнего успешного получения, если оно известно.
```

Значения и метаданные принадлежат одному неизменяемому snapshot. Возраст считается
с последнего успешного получения конкретного ключа, а не с последнего изменения
значения и не с запуска процесса. Подтверждение неизменившегося значения продлевает
срок; ошибка запроса или валидации — нет. Откат системных часов в прошлое относительно
времени получения считается неготовностью, чтобы не продлевать срок неявно.

Небольшой updates-sink перед штатным storage userver проверяет полученные значения
по выбранным схемам и добавляет служебные метаданные. Updater использует только
полные обновления раз в секунду без дедупликации: это позволяет подтвердить наличие
каждого ключа. Частичный ответ полного обновления означает, что отсутствующий ключ
переходит на builtin, который разрешается только явной политикой.

В штатном файловом кеше вместе с документами сохраняются локальное время получения,
отпечатки схем и идентификатор процесса. После перезапуска источник определяется как
Cache; предыдущий timestamp сохраняется. Перезапуск не делает старое значение свежим.
Кеш с другим отпечатком схемы не удовлетворяет обязательной зависимости, даже если
его JSON удалось разобрать. Отпечаток включает контекст, defaults и ограничения.
Кеш без метаданных прежней версии сбрасывается на builtin; поврежденный кеш не дает
готовности, если builtin запрещен. При недоступном сервере пригодный кеш сохраняется.
Служебное имя BROKER_CONFIG_DELIVERY_META зарезервировано генератором.

Это локальная проверка происхождения и совместимости, а не криптографическая подпись
кеша. Файловый кеш должен быть доступен на запись только пользователю сервиса.

## Собственные зависимости

Компонент может зарегистрировать проверку через `deps.readiness`. Регистрацию нужно
хранить на протяжении жизни компонента:

```cpp
registration_ = deps.readiness->Register("port-agent", [state] {
    return platform::DependencyStatus{state->IsReady(), "agent is unavailable"};
});
```

Тип поля registration_ — `platform::Readiness::Registration`. После его удаления
проверка отключается; повторное активное имя запрещено. Callback должен быть быстрым,
потокобезопасным и проверять уже известное состояние. Не выполняйте сетевой запрос
на каждый входящий HTTP-запрос; внешнее состояние обновляйте в фоне.
Исключение callback закрывает gate. В ответ бизнес-HTTP возвращается общая причина,
а `/ping/ready` сообщает имя и безопасное описание неготовой зависимости.

Пока политика действует на сервис целиком. Ограничение отдельными операциями,
метрики состояний зависимостей и gRPC gate — следующие расширения.
