# Окружение разработки

## Зафиксированные версии

- userver 3.2, commit `19472cc41deda3fb1c7aa7d13d53235a0161a224` и SHA256 архива.
- C++20; основной Linux-компилятор Clang 18.
- CMake 3.31.6, Ninja 1.11.1.4 в общем контейнере; минимум CMake для проекта — 3.24.
- Python 3.12 в контейнере, минимум 3.10 для инструментов проекта.
- PyYAML 6.0.2 и pycodestyle 2.12.1 для инструментов проекта.
- Python-зависимости testsuite и генераторов userver закреплены в `tools/python-constraints.txt`.
- Ubuntu 24.04 закреплена по digest; системные пакеты берутся из снимка репозиториев.

`tools/versions.env` — источник версий userver и Python-инструментов. При обновлении
пересоберите общий образ. Существующий системный userver принимается только при точном
совпадении версии. Checkout `third_party/userver` дополнительно проверяется по commit
и отсутствию изменений отслеживаемых файлов.

## Linux и Docker

`make docker-pull` скачивает закрепленный образ из GHCR. Контейнер работает от
пользователя `builder`, потому что PostgreSQL testsuite нельзя запускать от root.
В dev-образе установлены Debug и Release; docker-test-sanitize использует отдельный
образ с инструментированным userver. Повторно собирать framework в каждом PR не нужно. На Linux при проблемах
с правами задайте владельца рабочего каталога под uid 1001 или используйте Dev Container.
На macOS shared mount Docker Desktop обычно обеспечивает доступ без смены владельца.
`make docker-*` хранит `.venv-gen` и каталоги сборки в отдельных Docker volumes для каждой
платформы: Linux не использует нативные файлы macOS. Dev Container также имеет отдельные volumes.
Для проверки amd64 на ARM задайте `DOCKER_PLATFORM=linux/amd64` при сборке образа и запуске
проверок; это использует эмуляцию и может работать существенно медленнее.
Закрепленные multiarch-образы автоматически выбирают нужную платформу.
Локальную пересборку и обновление окружения описывает [container-images.md](container-images.md).
Служебный порт привязан к loopback внутри контейнера. Для его просмотра используется
Dev Container port forwarding; наружу его публиковать не нужно.

Для Docker Engine на Linux используется host network. На Docker Desktop host networking
нужно включить для сценариев с локальным PostgreSQL; тесты с собственным PostgreSQL работают
внутри одного контейнера. На Windows выполняйте команды из WSL2.

## macOS

1. Установите Command Line Tools: `xcode-select --install`.
2. Установите Homebrew с официального сайта https://brew.sh.
3. Выполните `scripts/install-deps-macos.sh`.
4. Добавьте Python 3.12 и PostgreSQL 16 в PATH, как указано в README.
5. Запустите `make doctor`, затем `make gen`, `make test-debug`, `make test-release`.

CMake автоматически добавляет пути Homebrew к OpenLDAP, PostgreSQL 16, OpenSSL 3, ICU, gettext, zlib и bzip2.
Для совместимости с userver 3.2 Protobuf, gRPC, Abseil и fmt на macOS собираются
из закрепленных исходников фреймворка. CMake и Ninja запускаются из `.venv-gen`,
поэтому версия CMake из Homebrew не влияет на команды `make`.
Нативные пакеты Homebrew обновляются независимо: это удобное окружение разработки,
а воспроизводимость релизной сборки обеспечивает контейнер. Совместимость конкретного
набора macOS-пакетов подтверждается только успешной сборкой.

## Повседневная работа

Изменили спецификацию — выполните `make gen SERVICE=<имя>` и сохраните handler-блок,
lock-файл и заготовки ручной реализации. Сборка отслеживает зависимости спецификаций
и генератора; повторная ручная конфигурация CMake не требуется.

`make test-tools` проверяет инструменты без сборки userver. Как и CI, на Python 3.12+
он показывает десять самых медленных тестов вместе с подготовкой и очисткой окружения.
Тесты генератора используют отдельный небольшой репозиторий с нужными сервисами;
все проверки актуальности контрактов рабочего репозитория остаются в `check-gen-all`.
Для проверки одного сервиса используйте:

```sh
make test-debug SERVICE=shipments
# То же в закреплённом Linux-окружении:
make docker-test-debug SERVICE=shipments
# Дополнительно проверить общие клиентские контракты:
make docker-test-debug SERVICE=shipments TEST_SHARED_CONTRACTS=1
```

CMake настраивает только выбранный сервис; исходники соседних сервисов не генерируются.
При переключении `SERVICE` используется прежняя директория сборки и кэш компиляции,
а список доступных целей и тестов обновляется. CI передаёт список из плана проверок.

Собираются выбранный сервис, его зависимости и существующие тестовые цели;
запускаются только его unit/functional tests. Общие контрактные тесты по умолчанию
не входят в эту проверку. `make test-all-release` собирает и проверяет все сервисы.
Для обновления уже поднятого стенда: `make local-update SERVICE=shipments`
([подробнее](local-environment.md)).
`make new-service` не перезаписывает существующий сервис и откатывает регистрацию
при ошибке. Одновременное создание сервисов блокируется файлом `.service-create.lock`.
После аварийного завершения проверьте изменения и удалите оставшийся lock вручную.

Секреты передаются переменными окружения, например `DB_CONNECTION`. Значения testsuite
предназначены только для локальной БД. Тестовые ручки отключены в обычном config_vars.
`http-client-core` работает во всех режимах; выключать его по тестовому флагу нельзя.

В Linux используется Protobuf 3.21 из закрепленного снимка Ubuntu, в macOS — Protobuf 5.26 из исходников userver. В `tools/python-constraints.txt` соответствующие версии Python Protobuf и gRPC закреплены маркерами платформы.

В dev-образе задано `USERVER_ENABLE_STACK_USAGE_MONITOR=0`: необязательный монитор стека корутин требует `userfaultfd`, запрещенный обычным Docker. Логи, трассировка, Prometheus и санитайзеры продолжают работать; дополнительные привилегии контейнеру не нужны. В среде с доступным `userfaultfd` монитор можно явно включить переменной окружения.

## Слияние PR и обязательные проверки

Основная ветка — main. В GitHub разрешен только Squash and merge;
удаление ветки после слияния включено. Для каждого изменения создавайте новую ветку от main.
Удаление удаленной ветки не удаляет ее локальную копию.

Защита main требует PR, успешного CI result от GitHub Actions и актуальности
ветки относительно main. Если другой PR уже слит, обновите свою ветку через
rebase на origin/main либо Update branch в GitHub, разрешите конфликты и дождитесь CI.
Сам по себе зеленый статус на старой базе больше не разрешает слияние.
Обязательных одобрений ревьюеров нет; автор может слить свой прошедший проверки PR.

Полный CI запускается для PR в main. Повторного запуска на push после merge нет.
Для ручной проверки main используйте Actions → CI → Run workflow.
При ручном запуске отсутствие базовой ревизии включает все сервисы.
CI result проверяет инструменты и всю матрицу сборок; для изменений только документации
сборка пропускается, но инструменты и итоговая проверка остаются обязательными.
Отмена или ошибка сборки не превращается в зеленый итоговый статус.

В Summary запуска отображается план с причиной выбора каждого сервиса:

- Реализация, SQL, конфигурация и тесты сервиса затрагивают сам сервис.
- Публичная HTTP-схема затрагивает поставщика и прямых потребителей его клиента.
  Клиент клиента не пересобирается, пока не изменился контракт промежуточного сервиса.
- Библиотека затрагивает использующие её сервисы, включая линковку через другие библиотеки.
- Схема динамического конфига затрагивает Configs и подключившие её сервисы.
- Скрипты деплоя, локального стенда и их Python-тесты сами по себе не включают C++-сборки.
- Генератор, общее окружение, CMake/Makefile и сами правила CI включают общие проверки.
- Отсутствие базовой ревизии включает все сервисы. Ошибка определения зависимостей
  завершает CI с ошибкой, а не превращается в пустую выборку.

Полный список общих путей находится в `.github/service-deps.yaml`. Изменение только
README, сгенерированного lock-файла или дашборда сервиса не требует C++-сборки.

Быстрая задача `plan` рассчитывает выборку. Проверки инструментов и матрица сборок
затем выполняются параллельно: компиляция не ждёт завершения всех Python-тестов.
В каждой задаче собираются только выбранные executable и их unit-тесты.
CMake подтягивает необходимые библиотеки; остальные сервисы не собираются.
Общие `contract_service` и `client_contract_unittest` включаются только при изменениях
генератора, общей инфраструктуры контрактов или самого контрактного набора.
Если изменился только контрактный набор, сервисы приложения собирать не требуется.

Шаг «Тесты затронутых сервисов» содержит отдельный раскрываемый блок для каждого
сервиса с именами проверок и результатами. Падение одного сервиса не мешает проверить
остальные. Если у выбранного сервиса нет зарегистрированных тестов, CI падает.

Summary каждой задачи содержит таблицу результатов: CTest считает наборы
(unit executable / testsuite), Pytest — отдельные функциональные тесты. Эти числа
не суммируются. Ошибка сборки отображается отдельно от незапущенных тестов.
Логи каждого сервиса, JUnit CTest/pytest и `results.json` сохраняются на 14 дней в
Artifacts → `test-results-<preset>-<arch>`, в том числе при падении тестов.
Фронтенд имеет отдельные шаги форматирования, тестов и сборки.

Для локального воспроизведения тех же шагов (без изменения обычного `make test-debug`):

```sh
CI_SHARED_CONTRACTS=false CI_BUILD_SERVICES="broker configs" make docker-ci-build-debug
CI_SHARED_CONTRACTS=false CI_SERVICES="broker configs" CI_RESULTS_DIR=ci-results/debug-local make docker-ci-test-debug
python3 scripts/ci-tests.py summary --services broker configs \
  --output-dir ci-results/debug-local --preset debug --arch local \
  --build-result success --test-result success
```

Настройки защиты и способов слияния находятся в GitHub, а не применяются workflow.
При переносе репозитория их нужно настроить отдельно; публикация и CD в CI не включены.

### Выбор дорогих проверок

Проверки актуальности генерации, YAML и форматирования остаются на каждом PR.
Python-тесты инструментов выбираются по затронутым файлам. Тесты генерации четырёх
вариантов проверяют сам генератор; это не четыре настоящие сборки сервисов.

Настоящие сборки вариантов PostgreSQL/gRPC запускаются только при изменении шаблона,
генератора, создания сервисов, CMake/Makefile, общего runtime, закреплённого окружения
или самого workflow CI. Для обычной бизнес-ручки эта проверка пропускается.
Внутри неё также собирается только созданный сервис с общими контрактами.

Межсервисный сценарий запускается при затрагивании shipments/transportations или
самого интеграционного теста; оба необходимых executable включаются в план сборки.
Frontend проверяется при изменении приложения или затрагивании его BFF.
Для документации сборки сервисов и фронтендов пропускаются. При недоступной базовой
ревизии включаются все проверки. Выбор показан в Summary перед сборкой.

Проверка runtime-образов на PR запускается при изменении упаковки, build-файлов,
манифестов, генератора или frontend-зависимостей. Публикация из main остаётся
ручной и собирает полный релиз. Проверка полного локального стенда запускается
при изменении его инструментов, схем, библиотек, конфигураций и bootstrap сервисов.
Изменение обычной бизнес-ручки не запускает эти две повторные сборки всего проекта.

### Выбор тестов инструментов в CI

Job `tools` запускает `scripts/ci-tools.py`: план перечисляет выбранные Python-модули
и причины, а также сохраняется в summary. Изменения только фронтенда, документации
или бизнесовой реализации не запускают тяжёлые сценарии генератора и создания сервисов.
Изменения генератора/контрактов выбирают проверки генерации, инфраструктуры — проверки
деплоя. Изменённый тест запускается сам. Неописанные общие инструменты и отсутствие
базовой ревизии включают полный набор; ошибки git не маскируются под пустой план.
Ручной запуск CI (`workflow_dispatch`) всегда проверяет весь набор инструментов.

Быстрые общие проверки форматирования, YAML, закреплённых образов и воспроизводимости
генерации остаются на каждом PR. Правила выбора: `scripts/ci-tools.py`, тесты правил:
`tests/test_ci_tools.py`. При добавлении нового инструмента укажите его зависимости
в планировщике, иначе CI безопасно запустит полный набор.

```bash
.venv-gen/bin/python scripts/ci-tools.py --base origin/main --plan-only
.venv-gen/bin/python scripts/ci-tools.py --full
```

### Время проверок и кеш компиляции

В матрице Debug/Release/ASan+UBSan и arm64 используется ccache. Ключ разделён по
ОС, архитектуре, preset и закреплённому образу; после успешной сборки коммит сохраняет обновлённый кеш даже при последующем падении тестов.
Сам ccache проверяет компилятор, параметры, исходники и заголовки. Каталог CMake/Ninja
не переносится между runner: конфигурация и проверка зависимостей выполняются заново.
В задаче выводится статистика попаданий и промахов только текущей сборки; размер каждого кеша ограничен 512 MiB.

GitHub изолирует кеши PR: они доступны повторным запускам этого PR и недоступны другим PR.
Кеш из main доступен новым PR; его можно прогреть существующим ручным запуском CI на main.
Первый запуск без подходящего кеша остаётся холодной сборкой. Секреты в кеш не входят.

Изменения контрактов проверяются генерацией и сборкой поставщика и его клиентов.
Полный набор тестов реализации генератора нужен при изменении самого генератора,
его шаблонов и общей сборочной инфраструктуры, а не при каждом добавлении бизнесового поля.

Workflow **Local environment** запускается только вручную. Он проверяет полный Docker-стенд,
его авторизацию, мониторинг и миграции; в обычном PR повторной сборки всей платформы нет.
Во время ручного запуска каждые 30 секунд видны состояния контейнеров и последние строки
сборщика. Межсервисный тест Shipments/Transportations в основном CI использует временные БД
и две реплики без внешнего тестинга; он выполняется поверх уже собранных executable.

### Прямой запуск CMake

Без `BROKER_SERVICES` на чистой директории CMake настраивает весь каталог сервисов.
Список сохраняется в CMakeCache; для переключения передайте новое значение явно:

```sh
cmake --preset debug -DBROKER_SERVICES="shipments;transportations" -DBROKER_SHARED_CONTRACTS=OFF
cmake --preset debug -DBROKER_SERVICES=all -DBROKER_SHARED_CONTRACTS=ON
```

Пустой список (`-DBROKER_SERVICES=""`) отключает бизнесовые сервисы, например для
отдельной проверки общих контрактов. `BUILD_TESTING=OFF` отключает все тестовые цели.
Общие библиотеки доступны при любом выборе; поставщики HTTP API не добавляются
в сборку потребителя — его клиент генерируется из экспортированной схемы.

## Календарные даты

OpenAPI `type: string, format: date` генерирует `userver::utils::datetime::Date`.
JSON и HTTP query/path сохраняют ISO `YYYY-MM-DD`; строка проверяется и разбирается
на границе, внутри DTO и бизнесовой логики используются даты. `format: date-time` генерирует `std::chrono::system_clock::time_point`: это момент
времени с часовым поясом во входном RFC3339 и нормализацией в UTC на выходе.
`postgresql/types.yaml` поддерживает `type: date` с бинарным I/O PostgreSQL DATE.

В Web `DateInput` принимает `CalendarDate | null`, форматирует значение для ввода
и календаря. Незавершённый текст хранится внутри контрола и доступен через
`onDraftChange`, а `onChange` типизированного компонента отдаёт только дату или
очищенное значение. `IsoDateInput` — адаптер существующих форм, редактирующих
JSON DTO; преобразования сосредоточены в нём. `DateTimeInput` редактирует локальную
дату со временем. Календарный день не проходит через JS Date и сдвиг часового пояса.

В Shipments `shipment_v4`/`shipment_data_v3` и детали моря/авиа используют DATE.
Миграция переносит существующие маршруты в типизированные составные типы без потери
полей и удаляет прежние проекции. История Counterparties и Transportations читает
TIMESTAMPTZ без форматирования в SQL. JSON-хранилища сериализуют даты в ISO, при
чтении бизнесовые модели получают Date или time_point.
Откат на бинарник, использующий удалённые проекции, требует восстановления этих типов.

Начальная ревизия конфигов `0` создаётся миграцией в пустом хранилище.
`updated_at` содержит её настоящее время создания, после публикации — время
создания опубликованной ревизии. Повторное чтение время не меняет.


## Перед демонстрацией MVP и передачей клиенту

Согласовано 25.10.2026: перед переходом к совместной разработке и передаче MVP клиенту
подготовить два развёрнутых окружения — `testing` и `production`.

Наборы статических переменных сервисов должны называться:

- `vars_testsuite` — изолированные автоматические тесты;
- `vars_testing` — общее тестовое окружение;
- `vars_production` — рабочее окружение клиента.

Testsuite — отдельный режим автоматических тестов, а не третье развёрнутое окружение.
Точные расширения и расположение файлов согласовать при реализации. Текущие
`config_vars*` и staging пока не переименовываем: переход входит в подготовку MVP.
При планировании демонстрации, подключения команды или передачи клиенту вернуться
к этому пункту и напомнить о нём. В production самоаппрув конфигов должен оставаться
выключенным; разрешение в testing задаётся явно.

Динамические тайм-ауты PostgreSQL, настройки по ручкам и именованным транзакциям:
[SQL-тайм-ауты](sql-timeouts.md).
