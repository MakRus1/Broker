# Локальный стенд

Нужны запущенный Docker Engine с Compose v2, Python 3.12 и Git. На Windows запускайте
команды из WSL2; на macOS — из терминала. Для Docker Desktop выделите 8 ГБ памяти:
после запуска стенд потребляет примерно 1,2 ГБ, но сборке нужен дополнительный запас.

```sh
make local-up
make local-check
make local-status
make local-logs
make local-down
```

Первый запуск скачивает закрепленные образы и собирает приложения. Повторный использует
готовый SDK userver и результаты компиляции из volumes. `local-up` пересоздает контейнеры,
применяет миграции и запускает сервисы; готовность проверяет `local-check`.
Остановка сохраняет данные. Команду из подкаталога вызывайте через `make -C <корень>`.

Используется отдельный Compose-проект `broker-local`. Существующие БД из корневого
`docker-compose.yml`, нативные сборки и их volumes не используются. Сгенерированная
конфигурация находится в игнорируемом `.local/compose.yaml`; редактировать нужно исходники
в `tools/local` и `scripts/local-env.py`. Исходники в контейнере доступны только для чтения;
локальная папка `build-local` служит точкой монтирования Docker volume.

## Адреса

Все порты опубликованы только на `127.0.0.1`. PostgreSQL и Collector доступны лишь внутри
Compose-сети. Внутренние listener приложений открыты в этой сети для мониторинга.

| Назначение | Адрес |
| --- | --- |
| Grafana | http://127.0.0.1:13000 |
| Broker HTTP / мониторинг | http://127.0.0.1:18080 / http://127.0.0.1:18082 |
| Configs HTTP / управление | http://127.0.0.1:18090 / http://127.0.0.1:18092 |
| Диагностический сервис / мониторинг | http://127.0.0.1:18084 / http://127.0.0.1:18085 |
| Prometheus | http://127.0.0.1:19090 |
| Loki API | http://127.0.0.1:13100 |
| Tempo API | http://127.0.0.1:13200 |

Начальный вход в Grafana: `admin` / `admin`, затем она предлагает сменить пароль.
Измененный пароль сохраняется в volume. Логи смотрите через Grafana → Explore → Loki:

```logql
{service_name=~"broker|configs|diagnostics"}
```

У Loki нет главной веб-страницы: ответ 404 на `/` нормален. Проверка доступности — `/ready`.
В Grafana → Dashboards → Broker автоматически появляется дашборд «Broker: локальный стенд»:
готовность, RPS, HTTP 5xx, p95 по маршрутам, активные/занятые соединения PostgreSQL и логи.
Readiness собирает отдельный локальный probe через `/ping/ready`; метрика `up` отдельно
показывает доступность `/metrics`. Значения p95 берутся из готовых перцентилей userver,
не суммируются между экземплярами.

В раскрытой записи JSON доступна ссылка «Открыть трассу» по `trace_id`. В Tempo можно
вставить этот идентификатор вручную; из трассы доступен переход к логам соответствующего
сервиса. Плагины поставляются закрепленным образом Grafana; автоматическая загрузка и
обновление дополнительных плагинов при старте отключены. При временной ошибке загрузки
плагина после пересоздания контейнера полностью перезагрузите страницу.

## Сквозная проверка

`make local-check` проверяет готовность, реальный запрос к диагностическому `/scenario`,
одну трассу через HTTP-клиент → Broker → PostgreSQL и через gRPC-клиент → Broker,
логи обоих сервисов по общему `trace_id`, отсутствие `trace_id`/`span_id` в индексных
labels Loki и наличие метрик всех трех сервисов в Prometheus.

Затем проверка временно публикует timeout 1234 мс для `/hello_postgres`, дожидается его
появления в клиентском span и убеждается, что контейнеры не перезапускались. Исходный
конфиг восстанавливается через CAS. Это создает две ревизии истории; одновременное ручное
редактирование того же конфига приведет к явному конфликту вместо перезаписи чужих изменений.
При аварийном прерывании проверки восстановите конфиг через API истории/rollback.

`diagnostics` использует тестовый `contract_service`. Локальные компоненты регистрируются
только при `BROKER_LOCAL_SCENARIO=1`; обычные testsuite не включают их. Это вспомогательный
стенд, бизнес-модули от него не зависят.

## Данные, миграции и стартовые конфиги

SQL из `services/<service>/postgresql/schemas/db_1/V0001__migration_name.sql` выполняется
транзакционно под PostgreSQL advisory lock. Таблица `public.broker_schema_migrations`
хранит версию, имя, SHA-256 и время применения. Повторный запуск пропускает уже примененные
миграции, изменение или удаление примененной миграции вызывает ошибку. Добавляйте новые
версии; SQL не должен сам управлять транзакцией или требовать выполнения вне транзакции.

```sh
make local-migrate
```

Команда применяет миграции к существующим локальным volumes. Изменения схемы при работающих
сервисах должны быть совместимыми; полное пересоздание выполняйте через `local-up`.
`local-check` проверяет runner в отдельной временной БД и удаляет только эту БД после теста.
Проверяются повторное применение, новая миграция, checksum, история и атомарный откат SQL.

Первый запуск Configs публикует дефолты каталога только при ревизии 0. Существующие
пользовательские ревизии повторный запуск сохраняет. Эти значения предназначены для
локальной разработки; пароль БД `testsuite` не является секретом окружения развертывания.

## Телеметрия и ограничения

Версии и многоархитектурные digests находятся в `tools/local/images.json`. Приложения
используют SDK из `tools/container-images.json`; повторной сборки userver здесь нет.
Tempo закреплен на 2.10.8, чтобы запускаться без Kafka. Kafka добавим отдельным этапом,
когда определим требования к бизнес-событиям и доставке.

Трассы идут по OTLP/gRPC в Collector → Tempo. JSON stderr одновременно остается в
`docker compose logs` и ограниченных файлах: до трех файлов по 10 МиБ на сервис.
Collector читает текущий и ротированные файлы с сохранением offsets и отправляет в Loki.
`service_name` и окружение индексируются, идентификаторы трасс остаются metadata.
Собственные Docker logs также ограничены ротацией.

Prometheus хранит до 24 часов / 512 МиБ. Loki и Tempo настроены на 24 часа, очистка
выполняется асинхронно: это срок хранения, а не жесткая квота диска. При длительной
нагрузке контролируйте размер volumes. Collector хранит позиции файлов, но не имеет
дискового WAL экспортера; при недоступности backend дольше очереди возможна потеря данных.

Проверено выполнение на arm64 Docker Desktop. Образы содержат amd64 и arm64; CI проверяет
стенд на amd64. Для production отдельно нужны IaC, секреты, доступ, ресурсы, надежное
хранилище, резервирование и правила оповещений.
