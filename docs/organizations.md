# Организации и сотрудники

`organizations` хранит организации, членство и роли сотрудников. Keycloak хранит
учётные записи и отвечает за вход, пароли и MFA. Пользователь идентифицируется парой
issuer + subject; логин и email не используются как доказательство членства.

## Административный интерфейс

В админке есть раздел «Организации и сотрудники».

- Администратор платформы с ролью `platform.admin` клиента `broker-logistics`
  создаёт организации и управляет сотрудниками любой организации.
- Администратор организации назначается в `organizations`, управляет только своими
  сотрудниками и не может создавать организации или выдавать `platform.admin`.
- «Администратор организации», «Оператор» и «Наблюдатель» — стартовые роли.
  Роль является именованным набором разрешений: администратор создаёт собственные
  роли и отмечает права на вкладке «Роли и доступы». Изменения сразу применяются
  ко всем сотрудникам с этой ролью.
- В конструкторе доступны права поставок, перевозок, контрагентов и управления
  сотрудниками/ролями. Права Configs и платформы туда не входят. Даже `platform.admin`
  сам по себе не предоставляет `configs.read/write/approve`.
- Администратор платформы начинает с реестра организаций и открывает карточку.
  Администратор организации сразу попадает в карточку своей организации,
  без реестра. Добавление и изменение сотрудника/роли выполняется в отдельной форме.

При создании сотрудника администратор задаёт логин, имя, email, временный пароль и
роль. При первом входе Keycloak требует сменить пароль. Существующего пользователя
добавляют отдельным действием: его профиль, пароль и другие организации не меняются.
Отключение членства блокирует доступ только в данной организации. Последнего
активного администратора нельзя отключить или понизить, в том числе косвенно
через изменение прав его роли. Назначение ещё одного
администратора позволяет передать управление.

Публичная регистрация отключена. Будущий самостоятельный запрос доступа должен
проходить подтверждение администратора; регистрация учётной записи сама по себе
не предоставляет членство. Собственная форма сбора паролей на BFF не используется;
оформление страницы входа меняется через тему Keycloak.

## Проверка доступа бизнес-сервисами

В `service.yaml` бизнес-сервиса включается `auth.organization-access: true`.
Middleware сначала проверяет JWT, затем обращается к `/api/organizations/access`
с тем же токеном и требуемым разрешением. Членство и роль проверяются в центральной
БД перед открытием бизнесовой транзакции. Полученный organization доступен через
`platform::auth::GetOrganization(identity)`.

Это серверная проверка, а не доверие к полю браузера. `X-Organization-Id` можно
передать для явного выбора организации: центральный сервис проверяет членство.
Без выбора должна существовать ровно одна активная организация. Первый Web-срез
поддерживает работу сотрудника с одной организацией; выбор рабочего контекста для
нескольких организаций в Web — следующий шаг. В административном интерфейсе уже
можно управлять несколькими организациями.

Членство не кешируется: отключение учитывается в следующем запросе. При отказе
`organizations` защищённые бизнес-запросы завершаются 503, доступ не разрешается
по устаревшим данным. Сервис можно реплицировать с общей PostgreSQL; для дальнейшей
нагрузки отдельно прорабатываются измерения, кеширование и требования к отзыву.
`organization_id` остаётся у бизнесовых данных. Таблицы старых локальных привязок
сохраняются для контролируемого переноса, runtime их больше не читает.

Внутренняя команда `transportations.create` требует отдельной роли и `azp` клиента
`shipments-dispatcher`; она использует organization из сохранённой команды.
Обычный пользователь не получает это разрешение через роль сотрудника.

## Создание учётной записи и повторы

Намерение сохраняется с request_id до обращения к Keycloak. Пароль не входит в
намерение, аудит или ответ; тела запросов создания исключены из HTTP-логов обоих
сервисов. Keycloak получает метку `broker-provisioning-id`, доступную только его
административному API. Повтор с тем же идентификатором продолжает операцию; изменение
содержимого под прежним идентификатором возвращает 409. При сбое после создания
учётной записи повтор завершает членство без повторной смены пароля.
Сетевые вызовы не держат транзакцию PostgreSQL. Перед записью членства права
администратора проверяются повторно. Между Keycloak и PostgreSQL нет общей транзакции:
непривязанная учётная запись при прерванной операции не получает бизнесового доступа.

## Окружения и начальный администратор

Локальный bootstrap создаёт демонстрационную организацию и привязывает `author`
как администратора, `reviewer` как наблюдателя. Только локально `author` автоматически
получает `platform.admin`. Существующие пароли не меняются.

Для личного staging выполните Deploy all с инфраструктурой. Служебный секрет
`organizations-manager-secret` создаётся на сервере и не попадает в Git. Начального
администратора назначают один раз доверенной командой на VM:

```bash
cd ~/projects/Broker
export KUBECONFIG="$HOME/.kube/config"
.venv-gen/bin/python scripts/organization_identity.py --platform-admin author
```

После назначения нужно выйти и войти заново, чтобы получить новый access token.
Дальнейшее создание организаций и сотрудников выполняется в админке.
Не запускайте локальный bootstrap с демонстрационными пользователями в рабочем окружении.

Служебный клиент `organizations-manager` имеет только manage-users/query-users/view-users
и соответствующие scope mappings, без realm-admin. Секрет принадлежит только
`organizations`. Настройка профиля сохраняет существующие атрибуты.

Ранее созданные организации и членство переносятся отдельно с сохранением UUID:
слепое объединение таблиц из нескольких сервисов запрещено при несовпадении привязок.
До такого переноса старые сотрудники не получают доступ автоматически.


Локальная тема входа копируется в стабильный `.local/keycloak-theme`, который
монтируется в Keycloak. Это сохраняет mount при переключениях Git-веток/rebase;
обновление файлов темы выполняется `scripts/local-env.py prepare`/`make local-up`.
Тема принудительно использует светлые цвета Broker, включая случай системной тёмной темы.
