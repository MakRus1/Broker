# Добавление доставки сообщений в сервис

Outbox нужна для надёжной доставки события или команды после изменения БД. Обычный периодический sync без сообщений использует отдельную периодическую задачу.

Ниже пример для условного сервиса `orders`: после создания заказа нужно уведомить другой сервис. Имена бизнесовых моделей и клиента в примере выбирает разработчик сервиса.

## 1. Подключить библиотеку и применить миграцию

В `services/orders/service.yaml`:

```yaml
version: 1
libraries: [common, outbox]
postgresql:
  enabled: true
  cluster: orders
```

Выполнить `make gen SERVICE=orders`. Генератор добавит:

- зависимость `broker_outbox` в CMake;
- регистрацию `platform::outbox::Component`;
- секцию `platform-outbox` в статический конфиг с `postgres-component: postgres-orders`;
- очередную миграцию `Vxxxx__create_outbox.sql` со стандартной таблицей.

Миграция применяется обычным релизным механизмом перед запуском сервиса. Компонент проверяет наличие таблицы при старте и сам DDL не выполняет. Генератор сохраняет настройки компонента и не переписывает уже созданную миграцию при изменении шаблона библиотеки.

## 2. Поставить сообщение в бизнесовой транзакции

Тип сообщения задаётся константой сервиса:

```cpp
inline constexpr std::string_view kOrderCreated = "order.created";
```

После INSERT заказа, перед тем же Commit:

```cpp
userver::formats::json::ValueBuilder event;
event["order_id"] = order.id;
event["organization_id"] = organization;

platform::outbox::Enqueue(
    transaction, kOrderCreated, order.id, event.ExtractValue());
transaction.Commit();
```

Если INSERT или Commit завершится ошибкой, сообщение тоже не появится. Повторный `Enqueue` с тем же типом и ключом не заменяет уже ожидающее сообщение. После успешной доставки сообщение удаляется, поэтому долгосрочная идемпотентность бизнесовой команды обеспечивается сервисом и получателем.

Для события можно использовать сгенерированную сериализуемую модель вместо заполнения JSON вручную. Payload сохраняется вместе с изменением данных; его не нужно заново собирать из изменяемой записи при повторе.

Если требуется доставить только последнее состояние сущности, используется `EnqueueLatest` с ключом сущности. Он заменяет ожидающее состояние и инвалидирует старый lease. Такое объединение не подходит для событий, каждое из которых обязательно должно быть обработано.

## 3. Зарегистрировать обработчик

В конструкторе своего бизнесового компонента:

```cpp
auto& outbox = context.FindComponent<platform::outbox::Component>();
outbox.RegisterHandler(std::string{kOrderCreated},
    [this](const platform::outbox::Message& message) {
        SendOrderCreated(message.Payload);
    });
```

`SendOrderCreated` — метод сервиса, который разбирает payload в модель клиента, отправляет HTTP/gRPC-запрос с конечным таймаутом и проверяет результат. SQL захвата, подтверждения, повторов и удаления в сервис не добавляется. Исключение из обработчика назначает повтор; обычный возврат разрешает подтверждение.

Для бизнесового результата есть второй callback:

```cpp
outbox.RegisterHandler(std::string{kOrderCreated},
    [this](const auto& message) {
        return SendOrderCreated(message.Payload);
    },
    [](auto& transaction, const auto& message, const auto& response) {
        SaveOrderDeliveryResult(transaction, message.Payload, response);
    });
```

`SaveOrderDeliveryResult` выполняет короткие SQL-запросы в переданной транзакции. Компонент сначала проверяет актуальность lease, затем атомарно сохраняет результат и удаляет сообщение. При ошибке обе операции откатываются. HTTP-вызов должен быть только в первом callback.

Бизнесовый компонент должен явно получать `platform::outbox::Component` через `FindComponent`, чтобы userver учитывал зависимость жизненного цикла. Регистрация выполняется до завершения загрузки компонентов; обработка запускается после загрузки и останавливается до разрушения владельцев callback.

## 4. Выбрать параллельность и таймауты

```yaml
platform-outbox:
    postgres-component: postgres-orders
    max-concurrency: 6
    default-topic-concurrency: 2
    topic-concurrency:
        order.created: 2
        order.state.changed: 4
    lease-seconds: 30
    retry-seconds: 2
    max-retry-seconds: 60
```

Для второго типа нужен зарегистрированный обработчик; лишние имена в конфиге считаются ошибкой. Сумма слотов всех типов не должна превышать `max-concurrency`. По умолчанию бюджет — 8, по 2 слота на тип.

Слоты закреплены за типом: медленный `order.created` не займёт слоты `order.state.changed`. Лимиты действуют на под. Обработчики вызываются параллельно, их собственное изменяемое состояние нужно защищать. Порядок завершения сообщений не гарантируется; лимит 1 даёт последовательность только внутри одного пода.

Срок lease должен превышать максимальное время отправки, всех HTTP-попыток и подтверждения с запасом. Worker не продлевает lease автоматически. При потере ответа, истечении lease или падении пода доставка может повториться: у получателя должен быть идемпотентный ключ или проверка ревизии.

## 5. Проверить отказные сценарии

Тест сервиса должен проверить доставку после Commit, повтор после ошибки получателя и идемпотентность. Для нескольких типов — что заблокированный обработчик не мешает другому типу и не превышается лимит. Гарантии общего SQL (lease, устаревшее подтверждение, замена состояния, ограничение повторов) уже проверяются в тестах библиотеки через Shipments.

Рабочий пример двух обработчиков: `services/shipments/src/components/transportation_dispatcher.cpp`. Постановка операции — `services/shipments/src/operations/request_transportations.cpp`; замена состояния маршрута — `services/shipments/src/helpers/route_projection.hpp`.


## Индекс очереди и измерения

Каждый слот захватывает один тип через `topic = $1`; индекс `(topic, available_at, id)` поддерживает выбор ближайшего сообщения без сортировки backlog. Текущим потребителям индекс добавляется отдельной миграцией; шаблон начальной схемы для новых сервисов уже содержит его. Выпущенная начальная миграция не меняется.

В [outbox-topic-queues.json](benchmarks/outbox-topic-queues.json) сохранены измерения на 1 млн сообщений: 999 900 одного типа, 100 другого, плюс поиск отсутствующего типа. Сравнивается прежний SQL с `ANY` и индексом времени с итоговым SQL равенства и индексом типа/времени. PostgreSQL 16.14, 2 CPU, 2 GiB, 30 повторов после прогрева. Это захват одного сообщения без HTTP, конкуренции и стоимости постановки. Замер не обещает многократного ускорения: исходный уникальный индекс `(topic, message_key)` уже помогал редким типам. Полные планы и значения p50/p95 доступны в отчёте.
