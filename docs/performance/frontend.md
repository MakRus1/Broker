# Проверка производительности Web

## 2026-11-05: подписки личных настроек

Сценарий микробенчмарка: 120 подписок (условно 30 вкладок по 4 настройки),
по 100 описаний столбцов в значении. Девять серий по 500 итераций после прогрева;
в таблице медиана времени одного обхода всех подписок на локальной машине.

| Проверка snapshot | Время |
| --- | ---: |
| Чтение + JSON.stringify в каждой подписке | 0,515 мс |
| Ревизия конкретного ключа | 0,0163 мс |

Это ускорение проверки snapshot примерно в 31 раз, **не всей страницы**.
Теперь значение сравнивается один раз при изменении в store. Подтверждение
сохранения того же значения не меняет snapshot, поэтому не создаёт новый query
и повторную загрузку реестра. Повторная загрузка с сервера инвалидирует все ключи.

Запуск из корня репозитория (Node 24):

```sh
node --experimental-transform-types frontend/web/benchmarks/preferences.mjs
```

Время зависит от машины; пороги по времени в CI не заданы. Регрессионные тесты
проверяют изоляцию ключей и стабильность snapshot после сохранения.

## Браузерный сценарий

Локальная production-сборка, десять реестров в рабочих вкладках; затем шесть
переключений между поставками и перевозками. Ошибок консоли не обнаружено.
DOM после сценария: 1618 элементов, 8 скрытых панелей, 29 строк таблиц.
Запросы подсчитаны по журналам локального web_bff без содержимого ответов.
Повторное открытие поставок/перевозок выполняет новый запрос списка; остальные
скрытые реестры при этих переключениях повторно списки не запрашивали.

Проверка ограничена небольшим локальным набором и не является нагрузочным
тестом БД или замером heap/React commit duration. До заявления о готовности к
большим объёмам нужны отдельные сценарии с большими страницами/числом вкладок.

## Следующие замеры

- Стоимость React render/commit и память при 30–50 карточках с заполненными маршрутами.
- Рост DOM при последовательной автоподгрузке 1000+ строк; необходимость виртуализации.
- Повторные запросы при возврате к уже загруженному реестру: определить срок
  актуальности и события инвалидации перед введением кеширования.
- Начальная загрузка: основной JS около 800 КБ (219 КБ gzip); оценить разделение
  по функциям после измерения загрузки на медленном соединении.

Измерения полного сценария следует проводить отдельным профилировщиком браузера,
а не считать задержку вызова инструмента автоматизации временем реакции UI.

## Повторное использование загруженных страниц

Реестры поставок, перевозок, контрагентов, договоров, финансовых меток, услуг,
счетов и платежей сохраняют данные и курсор в своём смонтированном компоненте.
Быстрый возврат на вкладку не обнуляет страницы и не выполняет запрос списка.
Общая отметка актуальности учитывает пользователя/сессию, запрос, область данных,
ручную ревизию и успешные записи через API. Смена фильтров не хранит предыдущие
варианты результатов в глобальном кеше.

Срок — 60 секунд. Проверка выполняется при открытии вкладки и возврате фокуса
браузера/видимости страницы. Таймера фонового опроса нет: непрерывно открытая
таблица сама раз в минуту не перезагружается. «Обновить» обходит отметку свежести.
Успешные записи через общую функцию request консервативно инвалидируют все
реестры текущего окна, включая связанные суммы. Это не push-обновление от других
пользователей или других окон. Ошибки и отменённые загрузки не считаются успехом.

Браузерная проверка по журналам BFF:

- После прогрева десяти реестров 12 переключений: **0 запросов `/api/v1`**.
- Нажатие «Обновить» в перевозках: **1 запрос списка**.
- Возврат в поставки и перевозки спустя минуту: **по 1 запросу списка**.

## Синтетический стенд таблиц

Запуск из frontend/web:

```sh
pnpm exec vite build --config benchmarks/vite.config.ts
python3 -m http.server 14181 --bind 127.0.0.1 --directory /tmp/broker-registry-benchmark
```

Открыть `http://localhost:14181/registry.html`. Стенд использует production-сборку
реального RegistryTable, работает без API и не попадает в сборку продукта.
Кнопки задают число строк, столбцов и смонтированных вкладок. Результат на странице
показывает время от действия до двух animation frame и количество DOM-элементов.
Это ориентир для регрессий, не INP и не время одного React commit.

Разовые локальные наблюдения в IAB, без замедления CPU:

| Сценарий | Время до двух кадров | DOM-элементы |
| --- | ---: | ---: |
| 1000 строк × 20 столбцов | 201 мс | 21 127 |
| 1000 строк × 100 столбцов | 1057 мс | 101 527 |
| 10 вкладок × 100 строк × 20 столбцов: создание | 198 мс | 22 090 |
| Переключение этих вкладок | 36 мс | 22 090 |

Определения столбцов теперь индексируются один раз при рендере: раньше для
каждой ячейки дважды выполнялся линейный поиск по определениям. Однако DOM всё
ещё растёт пропорционально строкам × столбцам. Для больших широких таблиц нужна
отдельная виртуализация с проверкой выделения, переменной высоты маршрутов,
resize и сохранения позиции; в этом изменении она не включена.
