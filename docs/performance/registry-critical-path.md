# Реестр: нагрузка на полный путь

Замеры 5 ноября 2026 года. Это локальные измерения, не обещание задержек production.
Исходные результаты: [registry-critical-path-results.json](registry-critical-path-results.json).

## Что проверено

- Отдельный PostgreSQL с актуальными миграциями: 100 000 перевозок одной организации,
  10 000 поставок, 20 000 общих участков и 100 000 локальных участков маршрута.
- Отдельные Release-экземпляры `transportations`, `shipments`, `web_bff`.
  Каждый ограничен двумя CPU; сервисы — 512 MiB, BFF — 1 GiB, PostgreSQL — 768 MiB.
  Они делят Docker VM с остальным локальным стендом: 18 CPU, около 7,75 GiB памяти.
- Настоящие Keycloak, проверка членства/прав, cookie-сессия BFF и CSRF.
  В нагрузке используется одна сессия author; это параллельные запросы, а не модель
  пятидесяти независимых пользователей с обновлением токенов.
- Путь списка: BFF → transportations → PostgreSQL → shipments → PostgreSQL → BFF.
  Маршруты действительно читаются из поставок; ответы не подменяются.
- Production-сборка `RegistryTable` и настоящий экран Web.
  Для настоящего экрана личные настройки также направлены в отдельную БД.
  Рабочие базы и пользовательские настройки не изменялись.

Локальные спаны включены, экспорт в общий collector выключен (`sinks: default`),
чтобы нагрузочный тест не наполнял его очередь. Начальный прогон с неработающим
экспортом дал рост памяти BFF; его результаты не использованы как эталон.

## Сервер: отдельные запросы

Страница — 50 строк. По 20 запросов на сценарий. Столбец p95 здесь — консервативный
максимум 19 повторов после первого запроса; «холодным кэшем» первый запрос не считаем.
Все ответы HTTP 200.

| Сценарий | p50, мс | p95, мс |
| --- | ---: | ---: |
| Первая страница, номер контейнера | 29,7 | 36,7 |
| Сортировка по типу перевозки | 40,8 | 53,7 |
| Сортировка по типу контейнера | 39,5 | 40,2 |
| Поиск по вхождению одного символа | 32,6 | 42,6 |
| Поиск без результатов | 3,8 | 8,5 |
| Тип контейнера + опасный груз | 35,8 | 37,8 |

Дополнительные серии по 20 запросов, p95 — 19-й результат в отсортированной серии:

| Сценарий | p50, мс | p95, мс |
| --- | ---: | ---: |
| Курсор около номера 90 001 | 29,0 | 34,7 |

Глубокий курсор не показал деградации до стоимости прохода всех предыдущих страниц.
Это не подтверждает быстродействие всех возможных будущих комбинаций полей.

## Сервер: устойчивая нагрузка

По 15 секунд на уровень; замкнутая модель — следующий запрос после ответа на предыдущий.
Равномерно чередуются список, сортировка по типу контейнера, поиск по одному символу,
фильтр маршрута и варианты номеров. Итого 8 980 ответов, все HTTP 200.
Это короткий нагрузочный прогон, не длительный тест утечек или насыщения кэшей.

| Одновременно | Запросов | Запросов/с | p50, мс | p95, мс | p99, мс |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 3 077 | 205 | 48 | 79 | 86 |
| 25 | 2 877 | 191 | 131 | 228 | 262 |
| 50 | 3 026 | 199 | 256 | 382 | 426 |

После примерно 200 запросов/с пропускная способность перестаёт расти,
а ожидание увеличивается. Больше параллельных запросов не означает больше полезной работы.
Для поиска конкретного насыщенного ресурса нужны отдельные CPU/pool/queue профили;
этот прогон не доказывает, что узкое место находится именно в PostgreSQL или BFF.

## Один сквозной трейс

Один запрос списка из настоящего Web, без параллельной нагрузки:

| Этап | Длительность, мс |
| --- | ---: |
| BFF целиком | 39,1 |
| BFF → transportations, включая сеть | 27,1 |
| transportations целиком | 26,2 |
| Основной SELECT перевозок | 2,3 |
| SELECT локальных участков | 1,4 |
| transportations → shipments, включая сеть | 9,0 |
| SELECT контекстов поставок | 1,8 |

Это вложенные интервалы: суммировать все строки нельзя.
В этом запросе SQL занимает небольшую часть времени; остальное включает авторизацию,
межсервисный обмен, обработку данных и сериализацию. Одного трейса недостаточно,
чтобы разделить эти накладные расходы точнее.

## Браузер

Обычный viewport 1280 × 720, без CPU/network throttling. Время — до двух кадров после
commit, а не INP. Весь набор не вставляется в DOM. Часть строк имеет несколько строк текста.

| Сценарий | Результат |
| --- | --- |
| 100 000 строк × 100 столбцов, данные уже в памяти | 59–80 мс; около 2 400 DOM-элементов |
| 10 смонтированных таблиц × 100 000 × 100 | 139 мс; около 22 000 DOM-элементов |
| API → 100 строк × 100 столбцов | 208–232 мс, из них API около 58–75 мс |
| Настоящий Web, 50 строк и штатные 3 столбца | 118–153 мс от начала навигации; медиана 121 мс |

В первом сценарии строки содержат `id` и `value`, значения ста ячеек вычисляются
при отрисовке. Десять таблиц используют общий массив данных: это проверка DOM и
смонтированных компонентов, не памяти десяти независимых наборов.

**Полный широкий набор проверен отдельно:** HTTP-загрузка 100 000 строк со ста
разными строковыми значениями в каждой записи. JSON без сжатия — **232 567 296 байт**.

| Этап | Два прогона |
| --- | ---: |
| Получение тела ответа localhost | 276–292 мс |
| `JSON.parse` | 259–272 мс |
| От нажатия до двух кадров с таблицей | 902–952 мс |
| Самая длинная задача основного потока | 515–565 мс |
| Элементов DOM | около 2 400 |

Этот большой JSON отдаётся статическим сервером: в действующем API нет ста полей,
и он ограничивает страницу ста записями. Время генерации файла исключено из замера.
Это стресс сети/парсера/рендера, а не выдача 233 MB реальным BFF.
По обычной сети передача будет дольше. Размер JSON не равен занятой памяти JS heap;
точный heap/RSS браузера не измерялся.

Проверена доступность строки 100 000, сохранение фокуса и выделение 421 строки через
Shift с переходом через невидимые строки. Частота кадров непрерывной прокрутки,
INP, слабые устройства и длительный рост памяти этим прогоном не измерены.

## Найденные ограничения

1. Порог виртуализации зависит только от числа строк (150). Страница 100 × 100
   рисует все 10 000 ячеек и оказывается дороже уже виртуализированной 100 000 × 100.
   Следующая оптимизация — учитывать число видимых столбцов/ячеек.
2. Виртуализация не устраняет загрузку и парсинг всего массива. Постраничная загрузка
   должна сохраняться; для накопления очень большого числа страниц нужен предел кэша.
3. Серверный предел около 200 запросов/с относится к этому стенду и этой смеси запросов.
   Перед масштабированием нужны профили под устойчивой нагрузкой и тест на staging
   с его сетями, размерами БД и лимитами.

## Повторение

Нужен работающий `local-up`, локальный тестовый author и готовые Release-бинарники.
Сценарий создаёт отдельные контейнеры/БД с уникальными именами и удаляет их в `finally`.
Результаты и конфиги остаются во временной папке, путь выводится при запуске.

```sh
.venv-gen/bin/python scripts/benchmark-critical-path.py --concurrency 10 --seconds 15
.venv-gen/bin/python scripts/benchmark-critical-path.py --concurrency 25 --seconds 15
.venv-gen/bin/python scripts/benchmark-critical-path.py --concurrency 50 --seconds 15
```

Браузерный набор:

```sh
cd frontend/web
pnpm exec vite build --config benchmarks/vite.config.ts
cd ../..
python3 scripts/benchmark-registry-payload.py --output /tmp/broker-registry-benchmark/wide.json
python3 -m http.server 14181 --bind 127.0.0.1 --directory /tmp/broker-registry-benchmark
```

Открыть `/registry.html`; кнопка «100000 × 100: полные данные по HTTP» загружает файл.
Кнопка полного API-пути требует прокси с аутентифицированной сессией BFF и не работает
на обычном статическом сервере. Замер настоящего Web выполнен вручную через отдельный
loopback-прокси; автоматический browser load runner пока не добавлен.

## После добавления горизонтальной виртуализации

Исходные результаты выше оставлены как база сравнения. Общий компонент теперь
виртуализирует также столбцы (от 16), а вертикальный порог учитывает число ячеек.
Найденное ограничение для 100 × 100 исправлено.

На том же браузерном стенде после изменения: около 400 DOM-элементов для одной
таблицы 100 000 × 100 и около 3070 для десяти смонтированных таблиц с общими данными.
Пять повторов дают 61–64 мс до двух кадров. Серверный прогон не повторялся: изменение
затрагивает только рендеринг. Исходные серверные цифры не приписываются новой серии.
Результаты серии находятся в ключе `horizontal` JSON-файла.
