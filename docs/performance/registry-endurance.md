# Длительная работа с несколькими реестрами

Замеры 05.11.2026. Это две отдельные проверки: production-фронтенд в браузере и общий кэш в Node. Они не измеряют задержки BFF/PostgreSQL и не заменяют полный серверный нагрузочный сценарий из `registry-critical-path.md`.

## Браузер: четыре реестра × 100 столбцов

`benchmarks/endurance.html` использует настоящий `RegistryTable` и `useRegistryPage`. Одновременно смонтированы четыре таблицы, видна одна. Два круга по 60 следующих страниц в каждом реестре: 480 добавлений страниц, прокрутка вниз после каждого ответа, возврат наверх и 12 переключений между прогретыми вкладками. Каждая страница содержит 50 записей со 100 материализованными строковыми полями. Запросы имитируют задержку 10 мс; это не реальная сеть.

| Показатель | Результат |
| --- | ---: |
| Просмотрено строк на реестр | 6 050 |
| Полных записей в кэше на реестр | 400 |
| Продолжительность сценария | 12,49 с |
| Медиана переключения до двух кадров | 16,8 мс |
| Максимум переключения до двух кадров | 17,7 мс |
| Новых запросов за 12 прогретых переключений | 0 |
| Задачи длиннее 50 мс | 0 |
| DOM-элементы всех четырёх таблиц и стенда в конце | 975 |
| Ячейки tbody всех четырёх таблиц | 658 |

Время до двух кадров — лабораторная метрика, не INP. Один прогон не даёт p95/p99 и гарантий для других устройств. Цифры фиксируют результат конкретного прогона, а не норматив. Данные: `registry-endurance-results.json`.

Запуск: `pnpm --dir frontend/web exec vite build --config benchmarks/vite.config.ts`, HTTP-сервер с корнем `/tmp/broker-registry-benchmark`, открыть `/endurance.html`, нажать Run endurance. Итог и счётчики всех вкладок видны сверху. Для повторного чистого прогона обновить страницу.

## Память общего кэша: четыре реестра × 100 000 строк × 100 полей

Node v24.22.1, macOS. `cache-memory.cjs` использует скомпилированный production-класс `RegistryPageCache`. После контрольных точек вызывается GC. Измеряется весь JS heap процесса Node: кэш, его метаданные и служебные объекты. React, DOM, высоты строк и браузерные буферы сюда не входят.

| Строк на каждый из четырёх реестров | Heap после GC |
| --- | ---: |
| 0 | 3,64 МиБ |
| 1 000 | 14,69 МиБ |
| 10 000 | 19,09 МиБ |
| 25 000 | 23,44 МиБ |
| 50 000 | 31,71 МиБ |
| 100 000 | 48,74 МиБ |
| После повторного обратного обхода №1 | 48,33 МиБ |
| После повторного обратного обхода №2 | 48,34 МиБ |
| После повторного обратного обхода №3 | 48,34 МиБ |

На каждой точке после заполнения во всех четырёх кэшах остаётся по 400 полных записей. При каждом обратном обходе восстанавливаются 100 страниц на реестр без добавления новых ID. Рост при первом проходе ожидаем: сохраняются ID, границы и курсоры страниц, необходимые для восстановления прокрутки. При повторных обходах существующего набора дальнейшего существенного роста heap не наблюдалось. Это подтверждает ограничение полезной нагрузки, но не постоянный общий размер памяти при бесконечном просмотре новых строк. Данные: `registry-cache-memory-results.json`.

Воспроизведение:

```sh
pnpm --dir frontend/web exec tsc --ignoreConfig src/features/registry/registryPageCache.ts --target ES2022 --module commonjs --skipLibCheck --outDir /tmp/broker-cache-memory
node --expose-gc frontend/web/benchmarks/cache-memory.cjs /tmp/broker-cache-memory/registryPageCache.js
```

Третий аргумент задаёт количество строк на реестр, по умолчанию 100000; число должно быть кратно 50. Служебный прогресс идёт в stderr, итоговый JSON — в stdout.
