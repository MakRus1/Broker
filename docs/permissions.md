# Права модулей

Разработчик описывает право один раз в `schemas/permissions/<service>.yaml`.
Код обязан начинаться с имени владельца: `shipments.export`. Поля: `name`, `group`,
`scope` (`organization`, `platform`, `service`) и `requires` — список зависимостей.
`make gen` создаёт `<permissions/permissions.hpp>` с константами
`permissions::SHIPMENTS_EXPORT`. Дубли, циклы и неизвестные зависимости запрещены.

В обработчике проверка выглядит явно:

```cpp
platform::auth::CheckPermission(context, permissions::SHIPMENTS_WRITE);
```

Проверка использует доверенный контекст middleware без повторного HTTP. Middleware
проверяет токен и получает права выбранной организации от Organizations; SQL бизнес-сервиса
использует только эту организацию. `HasPermission(context, permission)` служит для
условных действий. Проверки middleware пока сохраняются как обязательная защита,
чтобы пропущенный вызов в обработчике не открывал доступ.

Organizations хранит назначения ролям отдельно от каталога релизов. Представление
`permission_catalog` объединяет права активных релизов, а `effective_memberships`
сопоставляет их с назначениями. Неактивное право не даёт доступ. Зависимости проверяются
при сохранении роли и передаются UI; никаких правил по суффиксам read/write нет.

## Деплой и откат

`render` сохраняет каталог checkout релиза в защищённый `permissions.json` рядом
с манифестами. `apply` после миграций, до rollout, регистрирует каталог выбранных
сервисов в БД Organizations по digest образа. Никаких ручных команд разработчика.
Регистрация использует тот же доверенный kubectl-доступ CD, что и миграции;
публичного API записи каталога нет.

После успешного rollout и завершения terminating-подов CD сверяет активные каталоги
с фактически работающими образами выбранного сервиса. При нескольких версиях права
объединяются. Неизвестная версия или ошибка чтения кластера блокирует деактивацию.
При провале rollout старые права остаются активными. Выборочный деплой не трогает
каталоги остальных сервисов. Деплои и откаты сериализуются существующей блокировкой.

Откат сначала активирует сохранённый каталог целевого digest, затем обновляет сервис
и выполняет сверку. Исчезнувшее право становится неактивным: запись и назначения
сохраняются, поэтому откат восстанавливает доступ. Идентификаторы не переиспользуем
для другого смысла. Перед первым деплоем нужен Organizations с миграцией V0005.
Первоначальные записи прав создаёт обычный pre-rollout шаг из YAML релиза.
Переходного bootstrap старых каталогов нет.
Откат к образу, который никогда не регистрировал каталог, после переходного периода
блокируется до регистрации проверенного манифеста этого образа.

Локальная подготовка стенда синхронизирует каталог автоматически. Testsuite загружает
каталог в изолированную БД. Никаких новых полномочий существующим ролям не выдаётся.

## Права платформы

Назначения `scope=platform` хранятся в `platform_access` по доверенным issuer и subject.
Только `platform.admin` может читать и менять эти назначения через административный
API. Ревизия защищает от потери параллельных изменений, каждое изменение аудируется.
Корневое право остаётся в Keycloak и не назначается через конструктор прав.
Само по себе `platform.admin` не даёт чтение, изменение или подтверждение конфигов.

В карточке сотрудника корневой администратор открывает «Права платформы» и выбирает
разрешения. У администратора организации этот блок отсутствует; сервер также
возвращает 403 при прямом вызове. Назначения платформы независимы от отдельных
организаций. Отзыв глобального права выполняется в этой форме.

Configs проверяет права через Organizations для каждого административного запроса.
Роли configs.* из JWT больше не используются. Вход админки и Configs используют
единый audience broker-logistics; существующий broker-admin уже имеет этот audience.
Для пользовательских и служебных клиентов другого audience требуется его явно
добавить в Keycloak. Исчезновение права при rollout деактивирует и платформенный
доступ; назначения сохраняются для отката.

Перед первым развёртыванием зарегистрируйте корневого администратора прежней командой
настройки Keycloak. После deploy all он назначает нужные платформенные права через
админку. Пароли и пользовательские назначения из Keycloak автоматически не импортируются.
Локальные технические local-author/local-reviewer получают минимальные назначения
через подготовку тестового стенда; обычным сотрудникам права автоматически не выдаются.
