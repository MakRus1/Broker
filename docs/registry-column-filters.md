# Фильтры столбцов реестров

Поставки, перевозки и контрагенты используют общий редактор фильтров. Кнопка в заголовке открывает условия соответствующего столбца. У составного столбца поля сгруппированы в раскрываемые секции: основная открыта, остальные свернуты, заданные условия видны в заголовках. Варианты второстепенного поля загружаются при его раскрытии. Например, например, «Контейнер» объединяет тип и принадлежность. Маршрут пока не фильтруется: его межсервисные условия требуют отдельной проекции.

Внутри списка выбранных значений действует «или», между полями — «и». Можно вставить несколько значений из Excel или строками. Для текста есть поиск по вхождению; для даты — типизированный диапазон, для логического поля — «да»/«нет». Значения загружаются с сервера страницами, включая первую страницу без поискового текста. Фильтр предлагает значения, которые подходят под **остальные** условия; собственное условие поля исключается из этого запроса.

Скрытие и перестановка столбцов меняют только представление. Фильтры и сортировка сохраняются независимо, в том числе после перезагрузки. Над таблицей остаются активные условия и отметки о скрытых столбцах. Через общую кнопку «Фильтры» можно изменить условие скрытого поля. Сброс фильтров не меняет сортировку.

## Как добавить поле

1. Описать SQL-выражение поля и добавить `RegistryField` в `registry_fields::kFields` своего сервиса. Указать подпись, SQL для значения, при необходимости `Sortable = false`, `FoldValues = true`, `Array = true` или источник подписи `Lookup`. Сортировка, фильтрация и API метаданных используют **этот же каталог**. Отдельный enum сортировок в трёх схемах не нужен.
2. Добавить отображение поля в `RegistryColumn`. Если `id` столбца совпадает с именем поля, фильтр и сортировка появятся автоматически после получения метаданных. Для составного столбца указать `filterFields: ['first', 'second']`; для отключения — `filterFields: false`.
3. Добавить проверку результата и изоляции по организации. На реалистичных данных проверить план и стоимость запроса. Индекс не создаётся автоматически на каждое поле — решение зависит от селективности, сортировки и частоты использования.

API списков и `filter-values` принимают одну модель запроса реестра. Все условия передаются в `filters`; отдельные `country_code`, `status`, `query`, `shipment_id` и прочие старые параметры удалены и возвращают 400. Запрос без фильтров не добавляет скрытых условий. Например, экран контрагентов сам задаёт `{field: 'archived', values: ['false']}` для первоначального списка действующих записей. Внутренние вызовы используют те же условия: выбор по идентификаторам — поле `id`, поиск контрагента по названию и реквизитам — поле `search`, перевозки поставки — поле `shipment_id`. BFF сохраняет отдельный контракт и типизированные преобразования. Значения передаются в PostgreSQL параметрами; имена полей и SQL-выражения выбираются только из серверного каталога. Неизвестные поля, неподдерживаемые сортировки, смешанные способы фильтрации и некорректные значения возвращают 400 до выполнения SQL. Права чтения и обязательное ограничение организации остаются на сервисе.

Для подписей связанных записей фронтенд получает страницу идентификаторов и одним пакетным запросом разрешает её через реестр источника (без N+1). При поиске по подписи сначала ищет в источнике, затем пересекает найденные идентификаторы с текущими условиями. Для этого пользователю нужны права чтения источника. Курсор такой выдачи принадлежит источнику; отдельная страница может быть пустой, но иметь продолжение.

## Границы первого варианта

- До 32 условий, 200 выбранных значений одного поля; не загрузка всего справочника в браузер.
- Сортировка по одному полю с UUID как дополнительным ключом; списки и значения используют курсоры, без OFFSET.
- Метаданные полей не означают одинаковую скорость любого сочетания условий. Новое большое поле требует замера плана.
- Нет фильтров по полям участков маршрута и пользовательских сохранённых наборов условий.
- Бенчмарк ниже измеряет SQL, а не задержку HTTP и не одновременную работу многих пользователей.

Применены настоящие миграции; новые индексы для этого PR не добавлялись. SQL получен настоящими C++-построителями. Бинарники для сравнения сохранены из main `ec0c284` до изменений. Ограничение: поиск отсутствующей подстроки по номеру контейнера с generic plan на 1 млн строк имеет p95 около 238 мс (до изменений — около 245 мс). Custom plan для того же поиска использует trigram-индекс и укладывается в 0,2 мс. Это существующая чувствительность к выбору плана, а не гарантия задержки поиска. Для следующих нагрузочных тестов нужны профиль реальных запросов, конкуренция чтения/записи и HTTP-замеры; по ним можно отдельно принять решение о custom plans для поисковых запросов.

Воспроизведение: `scripts/benchmark-column-filters.py --help`. Указать `--service`, `--query-renderer` (команда запуска `<service>_registry_query_dump`), `--baseline-renderer` (та же утилита из сравниваемой версии), `--output`. Утилита создаёт отдельный временный PostgreSQL и удаляет его после запуска; локальные и серверные БД не использует.

## Вызовы из сервиса

Описание `registry::Definition` связывает каталог полей, SQL вариантов фильтра и
функцию ограничений сервиса в `kRegistry`. Контекстом текущих реестров служит
идентификатор организации; дополнительные ограничения (например, направление
счёта и группы участков) берутся из запроса.

```cpp
const auto page = registry::BuildPage(kRegistry, request.body, organization);
const auto values = registry::BuildFilterValues(kRegistry, request.body, organization);
```

Во втором вызове передаётся тело запроса вариантов фильтра: библиотека сама
извлекает реестровый запрос, поле, поиск, курсор, лимит и кандидатов. Текущее
поле исключается из фильтрации вариантов, остальные ограничения сохраняются.
