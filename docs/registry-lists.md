# Реестры поставок и контрагентов

Продолжение [реестра перевозок](transportation-registry.md). Этот этап относится к
пользовательским поставкам и контрагентам. Таблицы админки согласованы на следующий PR.

## Поставки

`POST /api/v1/shipments/list`:

- `number_query` — вхождение в номер поставки, без учёта регистра;
- `cargo_query` — независимое вхождение в описание груза;
- `customer_id` — клиент-контрагент;
- `statuses` — набор статусов текущей организации;
- `date_from`, `date_to` — включительный диапазон календарных дат поставки;
- `sort` — `id`, `number`, `shipment_date`, `status`, `cargo_description`;
- `descending`, `limit`, `cursor` — направление, размер страницы и продолжение.

Поиск обрабатывает `%`, `_` и обратную косую черту буквально. Номер не ищется в описании и наоборот. При заполнении обоих полей должны совпасть
оба условия. Между полями — «и»,
внутри набора статусов — «или». Обратный диапазон дат возвращает 400. Пустой набор
статусов выбирает ноль записей; отсутствие поля отключает фильтр.

В API форматы `date` генерируют `userver::utils::datetime::Date`, в SQL параметры
остаются DATE. Курсор для сортировки по дате содержит `date_value` с форматом `date`,
для текстовых полей — `text_value`. Сервер проверяет соответствие типа ключа сортировке.
Дата не превращается в timestamp или произвольный строковый ключ порядка.

В интерфейсе диапазон редактируется через `DateInput` и `CalendarDate`; `toJSON()`
отдаёт ISO на границе HTTP. В таблице календарный день отображается без времени
и преобразований часового пояса. Начальный порядок — свежие даты первыми.
Имена клиентов для загруженной страницы читаются пакетно через `ids`,
а не отдельным HTTP-запросом для каждого клиента. Клиент не сортируется по UUID под видом имени: для сортировки по имени клиента
потребуется индексируемая проекция данных владельца Counterparties.

## Контрагенты

`POST /api/v1/counterparties/list` сохраняет `query`, `role`, `status` и добавляет:

- `country_code` — код страны из двух заглавных букв;
- `ids` — до 100 идентификаторов для пакетного чтения карточек;
- `sort` — `id`, `name`, `country_code`, `tax_id`, `archived`;
- `descending`, `cursor` — направление и продолжение.

Поиск выполняется по названию, юридическому названию и налоговому номеру. Пустые
реквизиты сортируются как пустая строка, затем UUID задаёт однозначный порядок.
Состояния сортируются как действующий, архивный; обратный порядок меняет это направление.
В интерфейсе по умолчанию используется название по возрастанию. Роль — массив,
поэтому она остаётся фильтром, без неявного порядка по «первой роли».

## Общие правила

SQL целиком хранится в файлах владельцев данных. Общими являются только небольшие
примитивы `platform/registry.hpp`: буквальный LIKE и стабильная привязка курсора
к организации и запросу. Реестр перевозок использует те же функции. Общие React-
компоненты отвечают только за оболочку фильтров и заголовок сортировки, без каталога
полей или универсального бизнесового сервиса. В перевозках отдельно испытывается
[локальный конструктор SQL](transportation-query-builder.md); эти два реестра
на него не переведены.

Сервер читает `limit + 1` записей. Если есть продолжение, возвращается `next_cursor`.
Хеш включает фильтры, сортировку и организацию из проверенной identity, исключает
сам курсор и размер страницы. При смене запроса требуется первая страница.
Старое `after: UUID` оставлено для используемых сейчас вызовов по UUID по возрастанию;
в остальных порядках применяется составной курсор.

Короткая read-only транзакция ограничивает действие `SET LOCAL plan_cache_mode =
force_custom_plan`. Все проверки запроса выполняются до неё; HTTP-вызовов и записи
бизнесовых данных внутри нет. После commit/rollback настройка не остаётся на соединении.

Фильтры сворачиваются, поиск и «Применить» остаются видимыми. Сортировка находится
в заголовках столбцов. Изменение фильтров сбрасывает страницу, ответы старых запросов
не заменяют новый результат. Страницы контрагентов и поставок не сортируются и не
фильтруются по уже загруженной части данных во фронтенде.

## Индексы и измерения

Поставки: B-tree по организации/дате/UUID, B-tree по организации/номеру/UUID и GIN
с двумя независимыми триграммными колонками номера и груза. Контрагенты: B-tree по организации/названию/UUID
и GIN по поисковому тексту. Для GIN используется pg_trgm. Индексы на все сочетания
фильтров заранее не создаются. Создание индексов в миграции может временно блокировать
запись; это нужно учитывать при подготовке production.

Воспроизведение:

```bash
python3 scripts/benchmark-registry-lists.py --service shipments --rows 50000 \
  --output /tmp/shipments-registry.json
python3 scripts/benchmark-registry-lists.py --service counterparties --rows 100000 \
  --output /tmp/counterparties-registry.json
```

Скрипт создаёт собственный PostgreSQL 16.14 без открытых портов, применяет реальные
миграции, генерирует данные и удаляет свой контейнер в finally. Рабочие БД не используются.
Медианы трёх последовательных запусков 27.10.2026, 80% записей в одной организации:

| Реестр и сценарий | План под параметры | Общий план |
| --- | ---: | ---: |
| Поставки: первая страница по дате | 0,22 мс | 16,67 мс |
| Поставки: глубокая страница по дате | 0,22 мс | 10,49 мс |
| Поставки: редкий груз | 0,93 мс | 10,72 мс |
| Поставки: клиент + статус + диапазон дат | 0,44 мс | 4,75 мс |
| Поставки: сортировка по грузу без отдельного индекса | 15,75 мс | 22,90 мс |
| Контрагенты: первая страница по названию | 0,08 мс | 26,36 мс |
| Контрагенты: глубокая страница | 0,09 мс | 27,26 мс |
| Контрагенты: редкое вхождение | 1,12 мс | 24,21 мс |
| Контрагенты: поиск + роль + состояние + страна | 0,14 мс | 15,80 мс |
| Контрагенты: сортировка по стране без отдельного индекса | 19,25 мс | 27,57 мс |

В JSON сохраняются полные EXPLAIN ANALYZE/BUFFERS, разброс времени и размеры индексов.
Это прогретый кеш и время только SQL: HTTP, конкурентные изменения и холодный кеш
измеряются отдельно. Принципы дальнейшего масштабирования и появления поисковых
проекций описаны в документации реестра перевозок.
