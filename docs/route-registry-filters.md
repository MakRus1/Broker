# Фильтры участков маршрута

Реестр перевозок принимает `route_filters`: массив групп, внутри каждой — обычный `RegistryFilter`. Между группами действует «и». Все условия одной группы должны выполниться на **одном текущем участке**. Две группы могут совпасть как с разными участками, так и с одним: требование разных участков не задаётся.

```json
{
  "route_filters": [
    {"filters": [
      {"field": "mode", "values": ["sea"]},
      {"field": "pol", "values": ["<UUID порта>"]}
    ]},
    {"filters": [
      {"field": "mode", "values": ["rail"]},
      {"field": "destination_station", "values": ["<UUID станции>"]}
    ]}
  ]
}
```

Фильтры выполняются до сортировки и LIMIT. Корневые условия и группы включены в scope курсора. Скрытие столбца маршрута не сбрасывает группы: изменить или удалить их можно над таблицей.

В первом варианте доступны тип участка, станции, порты и аэропорты отправления/назначения. Участки, исключённые из текущей структуры поставки и сохранённые для исторического просмотра, в этот поиск не входят. Сортировка по коллекции участков не добавлена: сначала потребуется определить, какое значение использовать при нескольких совпадениях.

## Расширение каталога

Поле добавляется в `services/transportations/src/helpers/route_registry.hpp`, в `kFields`. Условия и значения используют одну запись. Пример даты для следующего расширения:

```cpp
{
    .Field = registry::Field<userver::utils::datetime::Date>{
        "arrival_date", "(local.document #>> '{rail,arrival_date}')::DATE", "DATE"},
    .Label = "Прибытие поезда",
    .ValueSql = "(local.document #>> '{rail,arrival_date}')::DATE",
    .Sortable = false,
    .ValuesFrom = "route_segments AS local",
},
```

`shared.document` — данные участка из поставки (море/авиа); `local.document` — данные перевозки. Тип C++ задаёт редактор даты; текст, набор значений, диапазон и заполненность обрабатывает существующий `ApplyFilters`. `ValuesFrom` задаёт источник кандидатов для дискретных значений. Для ссылок указывается `Lookup`, чтобы UI предлагал выбор по подписи, а не ввод/поиск UUID.

Не нужны новые поля запроса, converter BFF, view или компонент UI. Метаданные возвращаются через `filter-values` с `scope: route`, редактор строится по ним. Для поля со специфическим видом ввода расширяется общий вид поля, а не добавляется условие с его именем в UI.

При добавлении поля проверяются сочетания условий на одном участке, изоляция организации и планы запросов. Индексы выбираются по измерениям. Сейчас точные фильтры двух станций поддержаны expression-индексами; для портов и аэропортов есть статистика выражений, чтобы планировщик корректно выбирал порядок нескольких групп.

## Как доставляется маршрут поставки

Shipments остаётся владельцем маршрута. Его создание/изменение в одной транзакции вызывает `platform::outbox::EnqueueLatest`: стандартная `outbox` хранит последнее состояние маршрута по ключу организации и поставки. Вторая тема той же таблицы доставляет операции создания перевозок. Бизнесовое состояние и результаты операций остаются в `creation_operations`.

Общий PostgreSQL-компонент `platform::outbox::Component` владеет SQL очереди. Он захватывает сообщение через `FOR UPDATE SKIP LOCKED`, назначает уникальный lease и завершает запрос до HTTP-вызова. `available_at` хранит время следующей попытки, а во время доставки — срок lease. После ошибки задержка линейно растёт до настроенного максимума. Авария пода допускает повторный захват после истечения lease.

При подтверждении компонент блокирует сообщение и проверяет lease и generation. Затем бизнесовый callback и удаление сообщения выполняются в одной транзакции. Ошибка callback откатывает обе операции. `EnqueueLatest` увеличивает generation и инвалидирует прежний lease: старый ответ не может подтвердить новое состояние или применить к нему бизнесовый callback. Успешные сообщения удаляются физически.

Каждый тип получает независимый пул слотов доставки. По умолчанию выделяются 2 слота на тип, общий бюджет — 8 слотов на под. Сумма выделенных слотов не может превышать бюджет: неверная конфигурация отклоняется до запуска обработки. Поэтому медленный тип не занимает слоты другого типа. Каждый слот использует общий `Worker`: пачка до 50 сообщений, пауза после полной пачки 100 мс, при пустой очереди или ошибке хранилища 1 с. Настройки пачки, пауз, lease и повторов задаются в статическом конфиге компонента. Обработка запускается после регистрации всех обработчиков, останавливается до разрушения их владельцев; отмена прерывает ожидание и текущую доставку.

Transportations атомарно применяет только возрастающие версии. Повторы и запоздавшая доставка безопасны. В поисковой проекции хранится структура поставки и общие данные моря/авиа, без копирования их в каждую перевозку. Собственные поля перевозки читаются из её участков. Изменение общего участка не требует обновлять все перевозки поставки.

Поиск согласуется с изменением маршрута **асинхронно**: сразу после сохранения возможна небольшая задержка, при недоступности получателя — до восстановления доставки. Это не строгая read-after-write гарантия. Уже выполняющийся запрос читает согласованный снимок БД.

Первое развёртывание: сначала Transportations; затем остановить все старые поды Shipments, применить его миграции и запустить новую версию; затем BFF и Web. Это одноразовое несовместимое переключение: V0027 переносит ожидающие операции и проекции в стандартную outbox, удаляет старую очередь и служебные колонки. Старые writer/dispatcher-поды не должны работать во время переноса. Бизнесовые операции, результаты и резервы сохраняются. Откат на старые бинарники Shipments после этой миграции не поддерживается. Ручной импорт маршрутов не нужен.

## Бенчмарк

`scripts/benchmark-column-filters.py --service transportations --route ...` заполняет миллион перевозок, общие структуры поставок и миллион собственных ЖД-участков. Проверяются тип, станция, две группы, отсутствие совпадений и первые значения станции. Отчёт с p50/p95, SQL и EXPLAIN: [route-filters-transportations.json](benchmarks/route-filters-transportations.json).

Условия: PostgreSQL 16.14, linux/arm64, контейнер 2 CPU / 2 GiB RAM, shared memory 512 MiB, shared_buffers 256 MiB, work_mem 16 MiB; 30 повторов после прогрева. Замеряется SQL, без HTTP, конкурентных пользователей и записей. Скорость зависит от селективности: каталог поля сам по себе не гарантирует быстрый любой запрос.

На этом наборе custom plan: p95 0,506 мс для типа участка, 29,103 мс для станции, 46,815 мс для двух групп, 0,083 мс для отсутствующей станции, 30,963 мс для первых вариантов станции. Generic plan вариантов даёт до 3388 мс. Поэтому новый endpoint вариантов, как существующий список реестра, использует `SET LOCAL plan_cache_mode = force_custom_plan` внутри ограниченной read-only транзакции. Плохой generic plan оставлен в отчёте, а не скрыт из измерений.


## Подключение в другом сервисе

В `service.yaml`:

```yaml
libraries: [common, outbox]
postgresql:
  enabled: true
  cluster: example
```

`make gen SERVICE=example` добавит линковку, регистрацию компонента, `postgres-component: postgres-example` в статический конфиг и следующую миграцию `Vxxxx__create_outbox.sql` из стандартной схемы библиотеки. Применённая миграция не перезаписывается при изменении шаблона: следующие изменения схемы требуют новой миграции. При запуске компонент проверяет таблицу, не создавая её самостоятельно.

Сервис в транзакции бизнесового изменения вызывает:

```cpp
platform::outbox::Enqueue(transaction, kMessageType, event_id, payload);
```

Для заменяемого последнего состояния по ключу — `EnqueueLatest`. При этом объединяются только ещё не подтверждённые сообщения. Обработчик регистрируется в конструкторе компонента-владельца:

```cpp
auto& outbox = context.FindComponent<platform::outbox::Component>();
outbox.RegisterHandler(std::string{kMessageType},
    [this](const auto& message) { return Send(message.Payload); },
    [](auto& transaction, const auto& message, const auto& result) {
        SaveBusinessResult(transaction, message, result);
    });
```

Для доставки без изменения бизнесового состояния достаточно первого callback. Сервис не пишет SQL захвата, lease, подтверждения и повторов. Неизвестные текущему поду темы не захватываются. Доставка — как минимум один раз: получатель обязан быть идемпотентным. HTTP выполняется только в первом callback; callback подтверждения предназначен для коротких изменений в переданной транзакции.


### Параллельность

```yaml
platform-outbox:
    postgres-component: postgres-shipments
    max-concurrency: 6
    default-topic-concurrency: 2
    topic-concurrency:
        transportations.create: 2
        shipment.route.project: 4
```

Лимиты действуют на один под; несколько подов координируются lease в PostgreSQL. Из 6 слотов 2 закреплены за созданием перевозок, 4 за проекциями. Свободные слоты одного типа не передаются другому: это намеренная изоляция от долгих доставок. Тип с лимитом 1 последователен внутри пода, но не гарантирует глобальный порядок между подами. Для наших обработчиков повтор и изменение порядка безопасны благодаря идемпотентности операции и ревизии маршрута. Изменение лимитов требует перезапуска пода. Обработчики одного типа могут вызываться одновременно: их собственное изменяемое состояние должно быть защищено либо отсутствовать.

HTTP-вызов должен иметь конечный таймаут; lease выбирается с запасом на доставку и подтверждение. Пул не продлевает lease автоматически: при превышении его срока возможна повторная доставка на другом поде. Имена фоновых задач включают тип и номер слота: `outbox/<topic>/<slot>`.


Каталог вариантов един для реестра и маршрута: `/api/v1/transportations/filter-values`. Область выбирается `scope: registry` (по умолчанию) или `scope: route`; для маршрута `group` указывает группу условий. Отдельной ручки маршрута и отдельного BFF-view нет. Фильтрация списка остаётся в `/list`.

Пошаговый пример подключения нового обработчика: [outbox.md](outbox.md).
