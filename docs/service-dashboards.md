# Сервисные дашборды

`make gen SERVICE=<service>` создает `services/<service>/monitoring/grafana.json`.
Из каталога сервиса достаточно `make gen`. Дашборд добавляется автоматически и при
`make new-service`. JSON коммитится вместе с manifest; правки в нем заменяются генерацией.
`make check-gen-all` проверяет актуальность без записи. Сборка не генерирует JSON в исходниках.

Без дополнительных настроек включаются HTTP-сервер, процесс, HTTP-клиенты и логи.
PostgreSQL и gRPC-сервер добавляются, когда включены соответствующие секции manifest.
Метрики берутся из стандартного экспорта userver; бизнесовые labels не добавляются.

## Настройка через service.yaml

```yaml
dashboard:
  title: Broker · Поставки
  description: Техническое состояние сервиса поставок
  tags: [logistics]
  refresh: 10s
  sections: [http, process, http_clients, postgresql, logs]
  panels:
    - title: Размер очереди обработки
      expr: sum(work_queue_size{service="$service",environment=~"$environment",instance=~"$instance"})
      unit: short
      legend: Очередь
      description: Только если сервис уже экспортирует метрику work_queue_size
```

`sections` задает точный состав и порядок. Если секция не задана, используется
автоматический состав. Пустой список отключает стандартные разделы; пользовательские
панели остаются. PostgreSQL/gRPC нельзя добавить для сервиса с отключенной инфраструктурой.
`refresh` принимает `5s`, `10s`, `30s`, `1m` или `5m`.

`panels` добавляет PromQL timeseries-панели в отдельный раздел. Обязательны `title` и
`expr`; необязательны `unit` (идентификатор единицы Grafana), `legend`, `description`.
Текст выражения сохраняется целиком: фильтры и агрегацию своих панелей задавайте явно.
Генератор проверяет структуру настроек, но не разбирает произвольный PromQL и не создает
бизнес-метрики. Проверяйте свои выражения в Prometheus/Grafana.
Неизвестные поля и неверные типы отклоняются до записи файлов сервиса.

UID дашборда стабилен: `broker-service-<service>` (для длинных имен используется хеш).
Изменение title не меняет ссылку. ID стандартных панелей не меняются при отключении
других разделов. Для кастомных панелей ID зависит от позиции в списке.

## Фильтры и источники

В дашборде доступны выбор источника Prometheus/Loki, окружения и инстанса.
Скрытая константа `$service` равна имени сервиса. Все стандартные PromQL-запросы
ограничены service/environment/instance; по умолчанию выбраны все окружения и инстансы.
Источники по умолчанию имеют UID `prometheus` и `loki`; их можно переключить в дашборде.
Для другого стенда импортируйте тот же JSON и выберите свои источники.

Prometheus должен добавлять к собираемым метрикам labels `service`, `environment`
и `instance`; локальный стенд это уже делает. Для `up` service/environment задаются
на scrape target. `up` показывает доступность `/metrics`, а не readiness приложения.
На общем локальном дашборде readiness по-прежнему проверяется отдельными HTTP-пробами.

Логи фильтруются по `service_name` и `deployment_environment_name`, как в текущей
цепочке Collector → Loki. Выбор инстанса относится только к метрикам: соответствующего
label у логов пока нет. Переход из trace_id в Tempo задается provisioning источника Loki.
При отсутствии Loki можно убрать раздел `logs`.

HTTP-панели исключают `/ping`, `/ping/ready`, `/metrics` и `/tests/...`, чтобы
scrape/health-трафик не скрывал поведение API. Латентность берется из готовых gauge
`*_timings{percentile="p95"}`. Максимум p95 по инстансам не равен общему p95 запросов;
агрегировать эти метрики через `histogram_quantile` нельзя.
Метрики процесса показывают uptime, задачи и нагрузку event threads. Это не общий CPU
процесса; память процесса пока не экспортируется нашим набором метрик userver.

При отсутствии запросов или неподключенной интеграции отдельные панели могут показывать
No data. Генератор не подменяет отсутствие метрики нулем.

## Локальная Grafana

`make local-up` проверяет актуальность сервисных JSON и копирует их вместе с общим
дашбордом в `.local/grafana-dashboards`. Исходники не изменяются. Grafana provisioning
читает этот каталог; все дашборды находятся в папке **Broker**:

- `/d/broker-local` — обзор локального стенда;
- `/d/broker-service-broker` — Broker;
- `/d/broker-service-configs` — Configs;
- `/d/broker-service-admin_bff` — BFF.

Базовый адрес — http://localhost:13000. При удалении сервиса его сгенерированная копия
убирается при следующей подготовке стенда. UI-правки provisioned-дашборда не сохраняются:
меняйте `service.yaml`, запускайте `make gen`, затем подготовьте стенд через
`make local-status` (или `make local-up`). После подготовки Grafana перечитает файлы
в течение 30 секунд. При первом переходе со старого единственного дашборда нужен
`make local-up`, поскольку меняется mount каталога.

Поведение файлового provisioning описано в [документации Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/#dashboards).
Production provisioning, алерты и права доступа относятся к отдельному этапу инфраструктуры.

## Фильтр уровня логов

В сервисных дашбордах и общем обзоре есть мультивыбор **Уровень**:
`TRACE`, `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`. По умолчанию выбраны все.
Для ошибок и предупреждений выберите `WARNING`, `ERROR`, `CRITICAL`.

Для ручного поиска в Explore:

```logql
{service_name="broker", level="ERROR"}
```

Индексированный `level` появляется у новых записей после обновления Loki.
Ранее загруженные записи содержат его в structured metadata; фильтр после selector
работает с обоими вариантами (именно он используется в дашбордах):

```logql
{service_name="broker"} | level="ERROR"
{service_name="broker"} | level=~"WARNING|ERROR|CRITICAL"
```

Значения чувствительны к регистру и сохраняют названия уровней userver.
Collector также заполняет стандартные OpenTelemetry SeverityText/SeverityNumber:
`WARNING` соответствует `WARN/13`, `CRITICAL` — `FATAL/21`.
Grafana использует их для определения уровня и цвета записи.
Время записи Loki теперь берется из JSON `timestamp`, а не из момента чтения файла.
У уже загруженных записей время и индекс не переписываются.

Loki индексирует только service/environment/level. Trace ID, span ID, прочие поля
остаются structured metadata и доступны в деталях записи и фильтрах после `|`.
Исходная JSON-строка сохраняется, включая переход к трассе Tempo.

Настройки применяются через `make local-up`; данные volumes и позиции чтения Collector
сохраняются. `make local-check` проверяет доставку шести диагностических записей через
настоящую цепочку filelog → Collector → Loki, их уровни, время и фильтр `ERROR`.
Сами записи отмечены полем `check_id` с префиксом `loki-smoke-`.
