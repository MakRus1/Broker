# Структура сервиса

Экспортированные клиентские контракты находятся в `schemas/services/<service>` в корне
репозитория; C++-клиенты создаются в каталоге сборки потребителя.
Каталоги создаются по необходимости. В демонстрационном broker пока нет
бизнес-компонентов, репозиториев и внешних клиентов.

```text
services/<service>/
├── service.yaml                   # Инфраструктура, клиенты, конфиги и библиотеки
├── client-api.yaml                # include либо exclude для экспорта HTTP API
├── CMakeLists.txt
├── Makefile                       # Команды из каталога сервиса
├── configs/                       # userver и переменные окружения
├── docs/
│   ├── api/                       # Серверные ручки OpenAPI и codegen.lock
│   └── components/schemas/        # Общие HTTP-схемы, ссылки из API
├── proto/                         # gRPC-контракты
├── postgresql/
│   ├── schemas/db_1/              # V0001__migration_name.sql для БД
│   ├── data/                      # Тестовые данные
│   └── queries/                   # Именованные SQL-запросы
├── src/
│   ├── main.cpp                   # Запуск и регистрация
│   ├── deps.hpp                   # Зависимости сервиса
│   ├── models/                    # Структуры и преобразования по сущностям
│   ├── domain/                    # Бизнес-правила, если выделены отдельно
│   ├── components/                # Обычные C++ компоненты и сценарии
│   ├── repositories/              # Загрузка и сохранение сущностей
│   ├── clients/                   # Внешние сервисы и интеграции
│   ├── views/<path>/                 # HTTP-адаптеры
│   ├── transport/grpc/            # gRPC-адаптеры
│   └── bootstrap/                 # Обвязка userver, ping
└── tests/
    ├── unit/
    ├── benchmarks/
    └── test_*.py                  # Функциональные тесты testsuite
```

`models/` содержит обычные структуры, доступные всем частям сервиса.
Преобразования моделей группируются по сущности в `*_conversions.hpp`;
они подключаются только там, где нужны. Например, так организован Configs.

`domain/`, если нужен, содержит бизнес-правила без HTTP, userver и SQL.
Например, поставка, маршрут и допустимые переходы состояния контейнера.
Сейчас туда перенесена только демонстрационная функция greeting.

`components/` не требует наследования от userver. Например, ShipmentManager
проверяет правила, создает поставку и сохраняет ее через ShipmentRepository.
Адаптер в `bootstrap/` собирает объект из зависимостей контейнера userver.
HTTP и gRPC вызывают один и тот же бизнес-компонент.

`repositories/` содержит код загрузки и сохранения сущностей, преобразование
результатов SQL и транзакции. ShipmentRepository может сохранять поставку
вместе с маршрутами; класс на каждую таблицу не нужен. SQL лежит отдельно
в `postgresql/queries/`. Для простого справочника отдельный класс необязателен.
`clients/` содержит обращения к другим системам, например API порта.

Общие `Deps` допустимы при сборке сервиса и в небольших компонентах.
Крупным бизнес-компонентам передавайте только нужные интерфейсы через конструктор.
Не допускайте циклов при разрешении зависимостей. Утилиты размещайте рядом
с потребителем; общий каталог helpers создавайте только для реально общего кода.

Генерируемые C++ DTO/handlers, SQL и protobuf находятся в каталоге сборки.
`make gen` поддерживает явно отмеченные блоки исходников; остальной код ручной.
