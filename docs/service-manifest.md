# service.yaml

Файл в корне сервиса описывает его инфраструктуру и библиотеки:

```yaml
version: 1
libraries: [common]
postgresql:
  enabled: true
  cluster: main
grpc:
  enabled: true
```

Применение из каталога сервиса:

```sh
make gen
make test-debug
```

Из корня: `make gen SERVICE=orders`, `make test-debug SERVICE=orders`.
`make new-service NAME=orders POSTGRES=1 GRPC=1` создает такой manifest сразу.
Для существующего сервиса меняйте manifest, повторять new-service не нужно.
Отсутствующая секция PostgreSQL/gRPC означает enabled: false;
при отсутствии libraries используется [common]. Неизвестные ключи, повторения
и неверные типы отклоняются до изменения файлов.

## Что обновляется

Генератор меняет только блоки между парными маркерами `SERVICE_*_BEGIN/END`:

- CMake: библиотеки, SQL и protobuf-кодогенерация;
- main.cpp: include и регистрация компонентов;
- deps.hpp: PostgreSQL-зависимость и получение кластера;
- bootstrap/ping.cpp: проверка БД в готовности;
- static_config.yaml: PostgreSQL, gRPC-listener и middleware трассировки;
- tests/conftest.py: плагины и fixtures PostgreSQL/gRPC.

Ручные изменения внутри этих блоков заменяются. Вне блоков код сохраняется.
Новый сервис содержит только инфраструктуру, ping/готовность и их тесты.
Бизнес-спецификаций, view, демонстрационных таблиц и gRPC-методов в шаблоне нет.
Кодген поддерживает сервис без OpenAPI-операций. При включении PostgreSQL/gRPC
создаются пустые каталоги для миграций, SQL и proto; сборка работает и до добавления файлов.
Первую OpenAPI-спеку добавьте в docs/api, затем выполните make gen.
Собственные gRPC-компоненты регистрируйте вне управляемого блока;
все `.proto` из proto/ автоматически участвуют в сборке.

Секреты и адреса не хранятся в manifest: dbconnection поддерживает DB_CONNECTION,
переменные находятся в configs/config_vars*.yaml. Отсутствующие переменные добавляются,
существующие значения сохраняются. После подключения БД проверьте pg-connection.
Testsuite запускает свою БД самостоятельно. Для ручного запуска нужен доступный PostgreSQL;
manifest не поднимает БД и не меняет docker-compose существующего сервиса.

`.service-features.json` фиксирует примененные инфраструктурные возможности,
его нужно коммитить. Автоматическое отключение уже включенных PostgreSQL/gRPC
отклоняется: сначала нужно отдельно убрать использующий их ручной код, настройки
и тесты, затем выполнить осознанную миграцию состояния генератора.
Сейчас автоматизировано безопасное добавление, а не удаление инфраструктуры.

`make check-gen-all` проверяет manifest и обвязку без записи.
Сборка требует актуального `make gen` и не меняет исходники.
Старые сервисы без service.yaml продолжают работать; для миграции понадобятся
управляемые блоки из актуального шаблона. Текущий broker уже мигрирован.

## Библиотеки

`libraries` содержит имена каталогов `libs/<name>`, соответствующие CMake-target
`broker_<name>`. Каталог должен содержать CMakeLists.txt. Например:

```yaml
libraries: [common, routing]
```

```cmake
# libs/routing/CMakeLists.txt
add_library(broker_routing INTERFACE)
target_include_directories(broker_routing INTERFACE ${CMAKE_CURRENT_SOURCE_DIR}/include)
```

Корневая сборка автоматически находит библиотеки libs/*/CMakeLists.txt.
Порядок межбиблиотечных зависимостей задавайте через CMake-targets, не через include-пути сервиса.
`common` пока обязательна: в ней находятся middleware телеметрии.
Скрипт выборочного CI читает libraries прямо из manifest. Для старых сервисов
без manifest остается карта .github/service-deps.yaml. Дублировать зависимости
нового сервиса в этой карте вручную не нужно.

Подключение HTTP-клиентов в секции `clients`: [типизированные клиенты](client-codegen.md).

## Динамические конфиги

```yaml
libraries: [common, configs]
configs: [SHIPMENT_TERMS_CONFIG]
```

Ссылки используют глобально уникальные имена, без путей к YAML. Генератор находит
схему в `schemas/configs`, создает ключи и DTO в каталоге сборки, добавляет
`deps.configs` и штатные компоненты обновления userver. Неизвестное имя запрещено.
HTTP-клиенты автоматически подключают библиотеку и конфиг своего поставщика;
добавлять их ключи в `configs` вручную не нужно.
Обновления по умолчанию выключены; настройка доставки и схемы: [dynamic-configs.md](dynamic-configs.md).

## Имя PostgreSQL-кластера

`postgresql.cluster` задает логическое имя кластера; по умолчанию `main`.
Например, `cluster: accounting` создает компонент `postgres-accounting`.
Генератор согласованно обновляет регистрацию, static_config и получение `deps.pg_cluster`.
Имя допускает строчные латинские буквы, цифры и одиночные разделители `-`/`_`.
После изменения выполните `make gen`; ручные FindComponent с прежним именем нужно
обновить самостоятельно. Обычным компонентам лучше передавать `deps.pg_cluster`.

Имя кластера не переименовывает саму БД, каталог SQL, PostgreSQL-сервер или compose-сервис.
Имя базы и адрес задаются в `pg-connection`/`DB_CONNECTION`; каталог `schemas/db_1`
соответствует имени тестовой базы `<service>_db_1` и остается отдельным понятием.
Пока manifest поддерживает один PostgreSQL-кластер на сервис.

## Критические зависимости

Секция `critical_dependencies.configs` задает готовность по подключенным ключам:

```yaml
critical_dependencies:
  configs:
    SHIPMENT_TERMS_CONFIG:
      allow_builtin: false
      allow_cache: true
      max_age_seconds: 300
```

`max_age_seconds` обязателен; allow_builtin по умолчанию false, allow_cache — true.
Необязательные ключи не нужно перечислять. Генератор добавляет общий реестр готовности
и политики конфигов. HTTP/gRPC gate, кеш и интерфейс собственных проверок описаны в
[critical-dependencies.md](critical-dependencies.md).

При включении gRPC автоматически регистрируется platform-grpc-readiness. Он использует
тот же реестр критических зависимостей и возвращает UNAVAILABLE новым RPC при неготовности.
Отдельные правила для gRPC в manifest не требуются. Открытые вызовы/потоки не прерываются.

## Grafana

`make gen` автоматически создает `monitoring/grafana.json` для сервиса. Состав
учитывает PostgreSQL/gRPC. Необязательная секция `dashboard` задает название, теги,
разделы и дополнительные PromQL-панели: [настройка](service-dashboards.md).

## Тела HTTP в логах

Все сгенерированные HTTP-ручки по умолчанию логируют тела запросов и ответов,
до 32 КиБ каждое. Добавлять секцию в каждый сервис не нужно. Необязательная секция
позволяет исключить пути и изменить лимиты:

```yaml
http_logging:
  exclude_paths: [/auth/**, /api/session, /api/logout]
  request_body_limit: 32768
  response_body_limit: 32768
```

Политика применяется после `make gen`. `exclude_paths` — пути или glob-маски;
`*`/`**` могут охватывать `/`. Исключенные пути не логируют оба тела. Пустой список
означает отсутствие исключений. `0` в лимите отключает соответствующее тело для
всего сервиса. Заголовки этой политикой не включаются.

При превышении лимита userver оставляет UTF-8-префикс и добавляет штатную пометку
`...(truncated, total N bytes)`. Пометка добавляется сверх лимита префикса.
Сам HTTP-запрос или ответ не обрезается. Проверка генерации остается немутирующей.

В BFF исключены сессии и выход; ручные обработчики входа сохраняют отключенное
логирование тел. Служебные и другие ручные обработчики используют собственную
конфигурацию. Маскировка полей — отдельный этап.

## Развёртывание

Необязательная секция `deployment` задаёт `replicas` и Kubernetes `resources`
(`requests`/`limits`, CPU и memory). При генерации эти поля валидируются. Настройки
окружения и порядок переопределений описаны в [гайде staging](staging.md).


## Авторизация Bearer API

Секция `auth` задает `audience`, `roles-client`, `protected-prefix` и таблицу
`permissions` (полный шаблон пути → право). Она подключает библиотеку `auth`,
компонент, HTTP-клиент для JWKS и middleware автоматически. Bearer security в
OpenAPI и политика должны совпадать; генератор отклоняет пропущенные/лишние пути
и публичные ручки внутри защищаемого префикса. Значения issuer/JWKS зависят от
окружения и остаются в config vars. Пример и границы ответственности:
[Авторизация API](auth.md).

Новый сервис не требует удаления примеров перед началом работы. `make new-service`
создает чистый каркас; бизнес-API добавляется первой собственной спецификацией.
Проверены все четыре комбинации PostgreSQL/gRPC: создание, сборка и ping-тесты.
Демонстрационный `services/broker` сохранен как отдельный пример; шаблон его не копирует.

## Служебные OAuth-клиенты

Секция `service_accounts` описывает, под какой технической учётной записью сервис
обращается к другому сервису. Например, в Shipments:

```yaml
service_accounts:
  dispatcher:
    client_id: shipments-dispatcher
    audience: broker-logistics
    permissions:
    - transportations.create
    config:
      client_id: dispatcher-client-id
      client_secret: dispatcher-client-secret
      token_url: dispatcher-token-url
      enabled: dispatcher-enabled
```

`dispatcher` — локальное имя подключения, `client_id` — уникальное имя OAuth-клиента,
`audience` — получатель токена. `permissions` ссылается на права `scope: service`
из `schemas/permissions`. Получатель явно разрешает этот клиент для нужного права
через `auth.service-clients`. Это две стороны одного договора: запрошенное право
у отправителя и разрешённый вызывающий клиент у получателя. Генератор проверяет их
согласованность; менять скрипты окружения при добавлении подключения не нужно.

`config` связывает стандартные параметры с уже существующими переменными сервиса.
`enabled` необязателен: нужен только компонентам с флагом включения. Привязки и
клиент проверяются до применения настроек. Настройка не генерирует сетевые вызовы:
в C++ по-прежнему явно вызываются `GetAccessToken()` и клиент нужного сервиса.
Регистрацию пользовательского компонента и провайдера токена разработчик добавляет
обычным способом. `make gen` проверяет декларацию.

Подготовка локального стенда и рендер staging читают одну декларацию. Они подставляют
ID клиента, секрет, адрес token endpoint и включают компонент, если задан `enabled`.
Секрет не хранится в YAML: локально он находится в `.local/auth-secrets.json`,
на сервере — в `.staging/<client_id>-secret`. Повторная подготовка сохраняет секрет.
Локальный сервис дожидается завершения `keycloak-setup`.

CD настраивает служебных клиентов перед rollout их владельцев, в том числе при
выборочном деплое. Deploy infrastructure настраивает все объявленные подключения.
Создаются клиент, audience mapper, служебные роли и scope mappings. Пароли людей и
`platform.admin` этим механизмом не назначаются. Дубликаты client ID, неизвестные
права и переменные, а также несогласованная политика получателя отклоняются.

Для обращения к административному API Keycloak вместо бизнесовых `permissions`
используется `keycloak_roles`: таблица клиент → список существующих внешних ролей.
Organizations объявляет только `manage-users`, `query-users`, `view-users` клиента
`realm-management`. Эти роли должны существовать у провайдера; собственные права
модулей создаются автоматически из каталога. Композитные роли Keycloak могут
добавлять вложенные роли в токен.

Автоматическое удаление OAuth-клиентов и ранее выданных технических ролей пока не
выполняется: старые поды могут продолжать использовать их при rollout или откате.
После удаления последнего потребителя учётную запись отключают отдельно, когда
старые версии окончательно выведены. Жизненный цикл бизнесовых прав описан
в [permissions.md](permissions.md).
