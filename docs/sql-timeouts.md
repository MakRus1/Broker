# Динамические SQL-тайм-ауты

Сервисы с подключённым обновлением Configs получают стандартные ключи userver
без преобразования значений. Публикация новой ревизии в админке применяется
без перезапуска. Сервисы без клиента Configs продолжают использовать статику.

## Ключи и область действия

- `POSTGRES_DEFAULT_COMMAND_CONTROL` — общие настройки PostgreSQL-клиента.
- `POSTGRES_HANDLERS_COMMAND_CONTROL` — переопределения по пути HTTP-ручки и методу.
- `POSTGRES_QUERIES_COMMAND_CONTROL` — переопределения по имени SQL-запроса
  или именованной транзакции.

Эти ключи общие для подписанных сервисов. Для адресной настройки массового
импорта используйте уникальное имя транзакции, а не увеличивайте общий тайм-аут.

Общий конфиг, например:

```json
{
  "network_timeout_ms": 2000,
  "statement_timeout_ms": 1000
}
```

`network_timeout_ms` ограничивает ожидание ответа драйвером, включая COMMIT.
`statement_timeout_ms` ограничивает выполнение SQL на PostgreSQL. Допустимы
значения от 1 мс до часа. Необязательный `prepared_statements_enabled` управляет
подготовленными запросами. Если поле не указано, действуют встроенные значения
userver, а не значения из другого уровня настройки.

Для отдельной ручки:

```json
{
  "/api/admin/railway-stations/list": {
    "POST": {
      "network_timeout_ms": 2000,
      "statement_timeout_ms": 1500
    }
  }
}
```

Для импортов транспортных справочников:

```json
{
  "directory-sync.airports": {
    "network_timeout_ms": 30000,
    "statement_timeout_ms": 25000
  },
  "directory-sync.sea-ports": {
    "network_timeout_ms": 30000,
    "statement_timeout_ms": 25000
  },
  "directory-sync.railway": {
    "network_timeout_ms": 60000,
    "statement_timeout_ms": 50000
  }
}
```

Отсутствующий ключ использует настройки из статики сервиса. В transport_locations
для трёх импортов сохранены прежние 30/25 секунд, для обычных операций — 750/500 мс.
Опубликованный словарь заменяет весь словарь соответствующего ключа: это не патч.
Сохраняйте записи импортов при публикации, иначе удалённое переопределение
вернётся к общим тайм-аутам. Пустой словарь удаляет все переопределения этого уровня.

Именованная транзакция получает настройки при Begin; они действуют на её запросы
и COMMIT. Уже начатая транзакция завершает работу с прежними параметрами.
Внутри такой транзакции отдельные настройки запросов уступают настройке транзакции.
Явный CommandControl в C++ имеет приоритет перед динамическими настройками, поэтому
для динамически управляемых операций его передавать не нужно.

## Разработчику

SQL-запросы, сгенерированные из файлов, имеют имя файла без `.sql`, например
`claim_directory_sync`. Для нового запроса достаточно добавить его имя в словарь
`POSTGRES_QUERIES_COMMAND_CONTROL`: менять C++ и схемы конфигов не требуется.

Для настройки всей транзакции задайте уникальное имя при Begin:

```cpp
auto transaction = cluster->Begin(
    "my-service.import", pg::ClusterHostType::kMaster, pg::TransactionOptions{});
// Execute ...
transaction.Commit();
```

Три схемы в `schemas/configs/postgresql` используют общий режим `json-schema`.
Это JSON Schema Draft 4: генератор проверяет схему и default, а потребитель и
Configs проверяют значения через валидатор userver. Разрешены только локальные
`$ref`; внешние ссылки не загружаются. Режим не создаёт дополнительных SQL-клиентов
или отдельного механизма применения настроек — их применяет PostgreSQL-клиент userver.

## Выкатка

Сначала выкатить Configs с новым каталогом схем, затем transport_locations.
Новых миграций для SQL-настроек нет. Ключи создаются вручную через админку;
до их создания используются текущие статические настройки.
