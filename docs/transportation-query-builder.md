# Прототип конструктора запросов реестра перевозок

API, фильтры, сортировки и курсоры сохранены. Изменение касается только Transportations;
поставки и контрагенты продолжают выполнять статические запросы.

## Где смотреть

- `services/transportations/postgresql/queries/list_transportations.sql` — базовая выборка
  и состав возвращаемой модели, по одному полю на строку.
- `services/transportations/src/helpers/registry_query.hpp` — разрешённые поля,
  выбор сортировки и применение фильтров запроса.
- `services/transportations/src/helpers/registry_query_builder.hpp` — небольшой локальный
  построитель SQL и параметров userver. В common он пока не перенесён.

Обработчик проверяет права и курсор, вызывает `BuildRegistryQuery`, затем выполняет
полученный `Query` с `ParameterStore`. Проверки и построение выполняются до транзакции.
Транзакция нужна для согласованного чтения перевозок и участков маршрута, а также SET LOCAL.

## Как подключаются фильтр и сортировка

Пример для принадлежности SOC/COC (поле уже есть в БД):

1. Добавить `container_ownership` в запрос API и его enum сортировки.
2. Описать поле один раз в registry_fields:

```cpp
inline constexpr registry::Field<std::string> kOwnership{
    "container_ownership", "COALESCE(container_ownership, '') COLLATE \"C\""};
```

3. Добавить `kOwnership` в существующий массив `kSortableFields`.
4. Подключить фильтр:

```cpp
query.WhereEqual(kOwnership, request.container_ownership);
```

Фильтр и сортировка используют одно Expression. Отдельного switch или функции
для нового порядка нет: `OrderBy(kSortableFields, models::EnumValue(request.sort))`
находит зарегистрированное поле и передаёт его выражение конструктору.
Незарегистрированное имя сортировки отклоняется. UUID остаётся вторичным ключом.
Добавление и сортировка по этому примеру проверяются отдельным unit-тестом.

SQL-файл менять не нужно: поле исходной таблицы доступно в WHERE и ORDER BY,
даже если не возвращается отдельной колонкой SELECT. Для нового хранимого поля
понадобится миграция, а для вывода нового столбца — изменение модели/проекции.
BFF-контракт, передача поля и UI всё ещё требуют обычных изменений; прототип
не устраняет дублирование контрактов между сервисами.

При отсутствии значения фильтр не добавляется. Номер параметра назначается
конструктором; значение хранится в ParameterStore, а не вставляется в SQL.
Поддержаны равенство, принадлежность массиву и буквальное вхождение строки.
Пустой массив означает отсутствие совпадений; optional=false остаётся фильтром.
Строка из пробелов отключает поиск; `%`, `_` и `\` экранируются общим SearchPattern.

`Field<T>` связывает операцию с типом C++-значения. PostgreSQL-тип по умолчанию TEXT;
UUID и BOOLEAN указаны явно. UUID пока передаётся строкой, как в моделях API:
это не полноценная система SQL-типов и не ORM. Порядки текущего реестра текстовые;
поддержку порядка по датам или числам нужно проектировать отдельно.

## Как выглядит SQL

Файл содержит обычный SELECT с возвращаемой моделью и четырьмя именованными местами:

```sql
SELECT
    ROW(
        -- поля TransportationV4, по одному на строке
    )::public.transportation_v4 AS transportation,
    {sort_key} AS sort_key
FROM transportations
WHERE {where}
ORDER BY {order_by}
LIMIT {limit};
```

Этот файл — шаблон, он не предназначен для прямого Execute до построения запроса.
Конструктор заполняет только эти места через именованные аргументы fmt.
Каждое место обязательно и должно встречаться ровно один раз; это проверяется
до выполнения запроса, чтобы ошибка шаблона не потеряла условие организации.
Ни поиска слова WHERE, ни разбора SQL, ни оборачивающего CTE нет.

Например, для поиска по номеру итоговые условия:

```sql
WHERE organization_id = $1::UUID
  AND lower(COALESCE(container_number, '')) COLLATE "C" LIKE lower($2::TEXT)
ORDER BY lower(COALESCE(container_number, '')) COLLATE "C" ASC, id ASC
LIMIT $3::INTEGER;
```

Выбранное Expression одновременно задаёт возвращаемый ключ курсора, ORDER BY
и сравнение с курсором. Для UUID-порядка используется сам id; для совместимости
значение текстового ключа курсора остаётся пустой строкой.
Выражения задаёт разработчик, значения запроса проходят через ParameterStore.
Пользователь не может передать SQL-оператор, направление или имя колонки напрямую.

## Границы

Этот прототип всё ещё формирует SQL в C++, но делает это в одном ограниченном месте.
Он не поддерживает произвольные JOIN, группировки или деревья AND/OR и не пытается
автоматически определить стоимость фильтра. Фильтр по связанной таблице потребует
явного проектирования SQL и тестов. Индекс добавляется после измерения плана.

Число вариантов подготовленных запросов растёт с комбинациями активных фильтров;
запросы с разными значениями одного набора фильтров имеют одинаковый текст.
Имя запроса для метрик стабильно: `transportations_registry`.

SET LOCAL force_custom_plan сохранён: даже без CASE общий план LIKE на измеренной
выборке может проигрывать плану под конкретный шаблон. Это не устраняет потребность
в индексах и измерениях. API и интерфейс пользователя не меняются.

## Проверки и воспроизведение измерений

Существующие тесты проверяют все направления сортировки, повторы/пустые значения,
пересечение фильтров, организационную изоляцию, буквальный поиск и курсоры.
Добавлены проверки пропущенных фильтров, пустых наборов, false и отделения значений
от SQL-текста. Диагностическая утилита строит SQL тем же BuildRegistryQuery, что и API.

Внутри dev-контейнера после конфигурации Transportations:

```bash
.venv-gen/bin/cmake --build build-debug --target transportations_registry_query_dump
printf '%s' '{"sort":"container_number","query":"MSCU"}' | \
  build-debug/services/transportations/transportations_registry_query_dump
```

Для сравнения сохранить прежний запрос из main до этого ПР в `/tmp/registry-before.sql`.
Запустить dev-контейнер с собранным бинарником и смонтированным build-debug, затем на хосте:

```bash
python3 scripts/benchmark-transportation-registry.py --rows 100000 \
  --baseline /tmp/registry-before.sql \
  --query-renderer 'docker exec -i broker-query-prototype build-debug/services/transportations/transportations_registry_query_dump' \
  --output /tmp/registry-comparison.json
```

Бенчмарк сам создаёт и удаляет отдельный PostgreSQL без опубликованных портов.
Он сравнивает строки и порядок старого и нового запросов, затем сохраняет реальный SQL,
EXPLAIN ANALYZE/BUFFERS и медианы трёх запусков. Рабочие базы не используются.
Время только SQL на прогретом кеше не является временем HTTP-запроса или p95 под нагрузкой.


Локальное сравнение 27.10.2026, 100 тысяч строк (80 тысяч в одной организации),
три запуска каждого сценария. Во всех восьми сценариях строки и порядок совпали:

| Сценарий | Прежний SQL, custom | Конструктор, custom | Конструктор, generic |
| --- | ---: | ---: | ---: |
| Первая страница по номеру | 0,21 мс | 0,21 мс | 0,22 мс |
| Глубокая страница | 0,05 мс | 0,04 мс | 0,05 мс |
| Поиск + тип + контейнер + опасность | 0,77 мс | 0,74 мс | 8,20 мс |
| Поиск одного символа | 4,19 мс | 3,98 мс | 4,44 мс |
| Поиск отсутствующей строки | 0,97 мс | 0,99 мс | 19,44 мс |

Разница в сотые миллисекунды не доказывает ускорение. На этой выборке конструктор
сохранил сопоставимые планы и время custom-плана; generic-план поиска всё ещё
проигрывает. Основная цель прототипа — читаемое расширение фильтров.
