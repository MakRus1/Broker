# Реестр перевозок: фильтры, порядок и масштабирование

Этот документ описывает реестр перевозок. Продолжение для поставок и контрагентов:
[реестры поставок и контрагентов](registry-lists.md).

## Запрос и результат

`POST /api/v1/transportations/list` принимает типизированные поля:

- `query` — вхождение в номер контейнера, без учёта регистра; `%`, `_` и `\` трактуются буквально;
- `types` — один или несколько типов перевозки;
- `container_types` — один или несколько типов контейнера;
- `hazardous` — опасные (`true`), неопасные (`false`) или все (поле отсутствует);
- `shipment_id`, `item_id` — существующие ограничения области списка;
- `sort` — `id`, `container_number`, `container_type` или `type`;
- `descending` — направление сортировки;
- `limit` — размер страницы, от 1 до 100.

Между полями действует «и», внутри массива — «или». Пустой массив не выбирает ничего;
для отключения фильтра поле нужно опустить. Произвольные SQL-выражения, имена колонок
и операторы от пользователя не принимаются. Группы произвольных «и/или» и несколько
пользовательских ключей сортировки в первом этапе не реализованы.

Ответ содержит `items` и, если есть следующая страница, `next_cursor`. Следующий запрос
передаёт этот объект в `cursor`. Сервер читает на одну строку больше и не запускает
`COUNT(*)` при каждой загрузке. Одинаковые и отсутствующие значения упорядочены по UUID.
Пустые номера сортируются как пустая строка: в начале при возрастании и в конце при убывании.

Курсор содержит ключ порядка, UUID и хеш запроса с организацией. Хеш считается штатным
`ToStableString` и SHA-256; порядок JSON-полей не влияет на продолжение. Изменение фильтров
или сортировки требует первой страницы. Размер страницы можно менять. Это не токен
авторизации: организация по-прежнему берётся только из проверенной identity, а все
значения остаются связанными SQL-параметрами.

Старое `after: UUID` остаётся для сортировки по UUID по возрастанию, чтобы не менять
загрузку перевозок в поставке одновременно с новым реестром. Для других сортировок
используется только `cursor`. Сервер возвращает `next_cursor`, если есть следующая
страница, без дополнительного переключателя режима. Совместимость со старым BFF
на этом этапе не обеспечивается: окружение ещё не production.

## Где находится логика

Запрос целиком лежит в `services/transportations/postgresql/queries/list_transportations.sql`.
В C++ не склеиваются SELECT, WHERE и ORDER BY. В нём проверяется курсор, экранируется
строка LIKE и передаются параметры. Даты будущих фильтров должны оставаться типами
`date` / `date-time` в контракте и DATE / TIMESTAMPTZ в PostgreSQL.

В запросе фиксированный CASE выбирает известный ключ сортировки. PostgreSQL сворачивает
его при построении плана под конкретные параметры, поэтому индекс номера доступен
для сортировки и перехода к следующей странице. Для этого внутри короткой транзакции
реестра выполняется `SET LOCAL plan_cache_mode = 'force_custom_plan'`. Настройка не
остаётся на соединении после commit/rollback. Без неё общий план подготовленного
запроса может потерять индексный порядок из-за необязательных предикатов и CASE.

Добавляются два индекса: B-tree по организации, нормализованному номеру и UUID для
порядка страниц; GIN с pg_trgm для поиска по вхождению. Индексы на каждое
поле и каждую комбинацию фильтров заранее не создаются. Сортировки по типам сейчас
сортируют подходящие строки в PostgreSQL: на измеренной выборке они занимают около
35–40 мс. Если реальная нагрузка покажет, что этого много, индекс добавляется для
конкретного частого порядка после EXPLAIN, с учётом размера и стоимости записи.

Маршруты выбранной страницы читаются одним запросом, контексты поставок — одним
пакетным запросом. Фильтры применяются до LIMIT, а не к уже загруженной странице.
Транзакция чтения закрывается до обращения к Shipments.

## Как добавить поле

1. Определить владельца данных и точную семантику: равенство, набор значений, диапазон
   дат, префикс текста. Добавить типизированное поле в контракт Transportations.
2. Добавить явный предикат в тот же SQL. Если меняется порядок, добавить отдельный
   типизированный ключ и соответствующее сравнение курсора, не приводить даты и числа
   к произвольной строке ради общей сортировки.
3. Обновить контракт BFF и преобразование DTO, затем элемент фильтра во фронтенде.
   Привязка курсора автоматически включает новые сериализованные поля запроса.
4. Проверить сочетания с существующими фильтрами и EXPLAIN на реалистичных распределениях.
   Добавлять индекс только под подтверждённую проблему.

Станция назначения ЖД хранится в деталях перевозки: для неё возможен EXISTS по участкам
и отдельный измеренный индекс. Номер морского/авиарейса наследуется из поставки. Его
нельзя корректно искать после загрузки страницы или последовательными HTTP-запросами.
Перед таким фильтром потребуется локальная поисковая проекция актуальных полей поставки
в Transportations, с обновлением при изменении маршрута и определённой задержкой
синхронизации. Она нужна при появлении такого фильтра, сейчас отдельная инфраструктура
проекций не вводится.

Страницы не удерживают один снимок БД на всё время работы пользователя. Изменение номера
между запросами может переместить запись относительно курсора; обновление реестра
строит список заново. Для экспорта с фиксированным снимком нужен отдельный процесс,
а не долгоживущая транзакция интерфейса.

## Воспроизводимое измерение

```bash
python3 scripts/benchmark-transportation-registry.py \
  --rows 500000 --repetitions 3 --output /tmp/transportation-registry.json
```

Нужен Docker и образ PostgreSQL 16.14. Скрипт создаёт отдельный контейнер без проброса
портов, применяет настоящие миграции, заполняет синтетическими данными и удаляет только
свой контейнер в finally. Рабочие базы и Kubernetes не затрагиваются. Измерение не
включено в обязательные проверки каждого PR.

Результат локального запуска 27.10.2026: 500 тысяч перевозок, из них 400 тысяч в одной
организации; повторяющиеся и пустые номера, опасный груз у 1% записей. Медиана трёх
запусков, прогретый кеш, последовательные запросы PostgreSQL:

| Сценарий | План под параметры | Общий план |
| --- | ---: | ---: |
| Первая страница по номеру | 0,23 мс | 79,48 мс |
| Глубокая страница по курсору | 0,09 мс | 42,37 мс |
| Опасный груз | 20,15 мс | 17,65 мс |
| Вхождение + тип перевозки + тип контейнера + опасность | 4,58 мс | 17,59 мс |
| Поиск одного символа | 21,21 мс | 74,12 мс |
| Поиск отсутствующей строки | 1,59 мс | 40,08 мс |
| Сортировка по типу контейнера | 38,28 мс | 62,37 мс |
| Сортировка по типу перевозки | 35,51 мс | 63,34 мс |

B-tree занял около 42 МиБ, GIN — около 15 МиБ. Для строк короче трёх символов
триграммный индекс не обеспечивает выборочность: такой поиск разрешён, но на больших
объёмах может потребовать сканирования. Таблица выше показывает этот случай отдельно. В JSON-отчёте сохраняются полные планы,
буферы, минимум, максимум и версия PostgreSQL. Это измерения SQL на конкретном
синтетическом наборе, не SLA пользовательского HTTP-запроса. Перед production отдельно
проверяются реальные распределения, одновременные пользователи, изменения данных,
холодный кеш, время пакетной загрузки маршрутов и полный путь через BFF.


## Когда объём и команда вырастут

- До сотен тысяч записей: этот контракт, ограниченный размер страницы, keyset без OFFSET,
  индексы под реальные запросы и пакетное чтение связанных данных. Сначала измерять
  полный p95/p99 HTTP, частоту фильтров, буферы, строки до/после фильтра и время сортировки.
- При частых тяжёлых сочетаниях: добавить адресный составной или частичный индекс,
  скорректировать статистику и проверить план на перекосах между организациями.
  `hazardous = true` с 1% записей отличается от `false` с 99%; общий индекс на флаг
  без контекста запроса обычно не решает задачу. Учитывать время INSERT/UPDATE и размер БД.
- При поиске по данным разных владельцев: обновляемая локальная проекция реестра с
  индексируемыми полями и явными правилами актуальности. Не делать запрос к поставке
  для каждой строки и не фильтровать после LIMIT. Передавать изменения надёжно через
  существующий механизм событий/outbox, когда появится конкретная потребность.
- Если один PostgreSQL перестанет справляться: сначала оптимизация планов и ресурсов,
  затем реплика чтения с допустимой задержкой. Партиционирование и распределение данных
  вводить только после измерений; организация остаётся обязательной областью доступа.
- Отдельный поисковый движок нужен для нечёткого поиска и сложных межсущностных условий,
  которые уже не укладываются в приемлемый бюджет PostgreSQL. Он добавляет синхронизацию,
  задержку и эксплуатацию, поэтому не является обязательной частью текущего MVP.

Для параллельной разработки фильтры остаются частью контракта и SQL владельца данных;
нет общего редактируемого каталога всех фильтров всех сервисов. Настройки видимых колонок
и сохранённые пользовательские наборы должны хранить только идентификаторы разрешённых
полей; скрытие колонки никогда не заменяет проверку прав на сервере.
