# Пользовательское приложение Broker

`frontend/web` — рабочее место логиста, `services/web_bff` — его BFF.
Админка конфигов остается отдельным приложением `frontend/admin` на своем BFF.
Вход, PKCE, проверка сессии, CSRF и раздача статики вынесены в `libs/browser`.
Токены не передаются JavaScript: браузер получает HttpOnly cookie и CSRF-токен.
Cookies пользовательского приложения и админки имеют разные имена.

## Локальный запуск

```sh
make local-up
```

Пользовательское приложение: http://localhost:14080. Админка конфигов: http://localhost:13080.
Вход через Keycloak: `author` может читать и изменять логистические данные,
`reviewer` имеет только чтение. Пароли существующих локальных пользователей лежат
в `.local/auth-secrets.json`; настройка логистики их не меняет.

Локальный bootstrap идемпотентно добавляет клиент `broker-web`, роли
`broker-logistics`, сервисную учетную запись dispatcher и привязку этих тестовых
пользователей к organization `11111111-1111-4111-8111-111111111111`.
Это исключительно локальные стартовые данные. В рабочем окружении организации и
сотрудники создаются через административный интерфейс; членство хранится в `organizations`.
PostgreSQL shipments/transportations/counterparties сохраняется в собственных Docker volumes.
Обновление локального стека не удаляет существующие БД.

## Первый рабочий сценарий

1. Создайте поставку, выберите клиента из справочника по названию или ИНН.
   Локально уже доступен «Демонстрационный клиент».
2. Откройте поставку, добавьте позицию: например, 40HC, COC, количество 5.
3. Создайте 3 перевозки. Сначала количество резервируется, затем статус операции
   и счетчики обновляются автоматически. Останутся 2 доступные единицы.
4. Создайте оставшиеся 2. Во вкладке «Перевозки» появятся пять самостоятельных записей.

Реестры поддерживают автоматическую подгрузку следующих страниц. Реестры и карточки
открываются в рабочих вкладках внутри приложения; при переключении формы сохраняются.
Новая карточка поставки описана в [shipment-card.md](shipment-card.md). Небольшие действия
с контейнерами и фактами открываются в диалогах; Escape/закрытие предупреждают о потере данных.
При отправке команды повторное нажатие блокируется. После сетевого сбоя повтор
использует тот же ключ идемпотентности и исходное тело. При явном конфликте
проверьте актуальную редакцию и повторите команду.
Ошибки видны возле формы и в уведомлении с X-Trace-Id, если сервер его вернул.

Список операций сейчас хранит только операции, запущенные на этом устройстве;
их идентификаторы сохраняются отдельно для пользователя и поставки в localStorage.
Статусы читаются с сервера. После перезагрузки и повторного открытия карточки
наблюдение продолжается. Количества позиции всегда берутся из БД, независимо
от локального списка операций.

## Границы этого среза

Поставки и позиции можно создавать. Перевозки открываются отдельными страницами;
маршруты и фактические даты доступны для редактирования в рамках правил ниже.
Остальные логистические модули пока не представлены в UI.

Браузерные сессии используют существующее хранилище в памяти процесса.
Для нескольких реплик BFF нужны привязка сессии к реплике либо общее хранилище;
эта реализация вынесена в одну библиотеку, чтобы менять ее одновременно у обоих BFF.
Перезапуск BFF требует повторного входа. Бизнес-операции при этом сохраняются в БД.

На staging образы содержат обе сборки фронтенда, пользовательский BFF отдает
`/app/web-assets`. На данном этапе пользовательский вход настроен на
`http://localhost:14080`: для отдельного LAN-имени нужны отдельные redirect URI,
HTTPS-маршрут и конфигурация origin. Существующие admin/auth/grafana домены не меняются.
Локальная автоматическая привязка к organization и клиент dispatcher на staging не переносятся;
их настройка и включение worker нужны до пользовательского сценария на staging.

## Проверки

```sh
cd frontend/web
pnpm install --frozen-lockfile
pnpm check-format
pnpm test
pnpm build
```

В CI приложения проверяются выборочно по изменениям фронтенда и зависимостям BFF. Testsuite web_bff проверяет вход с настоящей
RSA-подписью, CSRF, изоляцию cookies и типизированные запросы к бизнес-сервисам;
мокируется только OIDC и граница HTTP этих зависимостей.

## Навигация и имена

Карточка поставки — полноценная страница `/#/shipments/<uuid>`, создание — `/#/shipments/new`.
Ссылку можно открыть в другой вкладке. Списки сохраняются при переходе в карточку;
назад/вперед браузера работают. Hash-маршруты не требуют отдельных правил раздачи
SPA и подходят для будущей настольной оболочки. Поля создания сохраняются
в sessionStorage отдельно для пользователя; при успешном создании черновик удаляется.
Это локальное восстановление формы, а не серверный бизнес-черновик.

Контрагенты принадлежат сервису `counterparties`: название хранится один раз,
поставка ссылается на UUID. BFF передает Bearer-токен, справочник проверяет organization
и права `counterparties.read/write`. Доступны поиск, чтение, создание, редактирование реквизитов и архивирование.
Создание повторяется с тем же UUID безопасно: другой текст с этим UUID дает 409.
Перевозки имеют постоянный уникальный номер `T-<число>`, поставки — `S-<число>`;
пропуски номеров допустимы, UUID остается техническим идентификатором.

## Рабочее место перевозки

Номер в реестре и в поставке открывает `/#/transportations/<uuid>`. Карточка
связывает перевозку с поставкой и клиентом, показывает контейнер, SOC/COC,
участки маршрута, плановые и фактические даты. Ссылки открываются в отдельных
вкладках браузера; редактор маршрута имеет адрес `/#/transportations/<uuid>/route`.

Маршрут содержит 1–32 упорядоченных участка: море, авто или ЖД. Пункты пока
задаются названиями и двухбуквенными кодами стран; подрядчик выбирается из
справочника контрагентов. Участки можно переставлять и удалять. Стабильные UUID
сохраняются при редактировании. Все изменения маршрута сохраняются одной командой.
После появления фактических дат замена маршрута запрещена существующим правилом API.

Время в форме соответствует часовому поясу устройства, который указан рядом;
на сервер отправляется UTC. Факт отправления и прибытия записывается отдельно.
Для исправления существующей даты обязательна причина. Сервер проверяет порядок
дат и expected_revision. При 409 форма предлагает обновить карточку; автоматического
повтора изменяющих команд нет, чтобы не перезаписать параллельное изменение.

Черновик маршрута сохраняется в sessionStorage по пользователю и перевозке.
Он переживает переходы и обновление страницы в пределах вкладки. Серверный драфт
при этом не создается. Если редакция перевозки изменилась, старый черновик нельзя
сохранить: нужно отменить его и открыть актуальные данные.

История маршрута и фактов читается через organization-изолированный
`/api/v1/transportations/history` с правом transportations.read. Она использует
существующий business_audit, показывает автора, время, действие, причину исправления
и снимок участков после изменения. Пагинация: limit и before по ID события.
Для новых событий сохраняется проверенное отображаемое имя автора;
для старых записей без него показывается «Имя не сохранено».
Создание партии перевозок по-прежнему аудируется как операция поставки;
история отдельной карточки начинается с изменения её маршрута или фактов.


### Действия и подтверждения в карточках

Вкладки переключают содержимое карточки. Действие «Обновить» вынесено в отдельную
кнопку справа с состоянием загрузки и защитой от повторного запуска.

Отмена изменённой формы использует диалог приложения с действиями
«Продолжить редактирование» и «Отменить изменения». Escape и закрытие диалога
возвращают к вводу; начальный фокус находится на безопасном действии. Пустой
редактор маршрута не считается изменённым, локально сохраняются только изменения.
При закрытии или перезагрузке самой вкладки с несохранёнными данными остаётся
защита `beforeunload`: вид этого предупреждения определяет браузер.

История использует одинаковые колонки события, автора с датой и редакции во всех
строках. На узком экране название события занимает отдельную строку.


### Справочник контрагентов

`#/counterparties` — поиск по названию/юридическому наименованию/налоговому номеру,
фильтры по роли и состоянию, страницы по 50 записей. Карточка имеет отдельный URL
`#/counterparties/<uuid>`, редактирование — `#/counterparties/<uuid>/edit`.

Первая версия представляет конкретные юридические лица. Клиент — роль контрагента,
совместимая с ролями перевозчика, агента, поставщика и партнёра. Роли помогают
фильтровать справочник, но не ограничивают выбор в поставке или маршруте.
Правила реквизитов принадлежат сервису Counterparties: удаляются только краевые
пробелы, код страны приводится к верхнему регистру. Содержимое налогового номера
(включая дефисы, внутренние пробелы и регистр) сохраняется. При указанном налоговом номере обязательна страна. Совпадение
страны и номера в одной организации блокирует дубликат, в том числе архивного
контрагента: вместо новой карточки следует восстановить существующую.

Архивирование не удаляет запись или внешние UUID-ссылки. Карточка остаётся доступной,
а выбор новых клиентов/подрядчиков запрашивает действующие записи. Выбор использует
серверный поиск с лимитом 100; связанные имена вне первой страницы читаются по ID.

Редактирование и архивирование используют `expected_revision`, изменения сохраняются
с аудитом в одной транзакции. Конфликт не перезаписывается автоматически. Черновик
реквизитов хранится в sessionStorage текущей вкладки; черновик другой редакции
не разрешается сохранить без отмены и повторного открытия актуальной карточки.

Новая миграция расширяет существующие записи и вводит `counterparty_v3`; старые типы
`counterparty_v1`/`counterparty_v2` и идентификаторы сохранены. Неполные реквизиты разрешены для уже
существующих карточек и быстрого создания при оформлении поставки.

Необязательные реквизиты и поля контактов хранятся как SQL NULL / JSON `null`.
Пустые строки после нормализации также становятся NULL. При обновлении отсутствующий
реквизит сохраняется, явный `null` очищает его, строка заменяет. Роли и контакты
при отсутствии сохраняются, переданный `[]` очищает список; `null` для списков запрещён.
Название при обновлении обязательно. В форме NULL отображается пустым полем.
Миграция V0006 разрешает NULL и снимает строковые defaults; существующие значения не изменяет.

Переход с v2 на v3 меняет nullable-контракт: Counterparties и Web BFF обновляются
согласованно. Сохранение определения старого composite-типа само по себе не делает
старые бинарники, ожидающие обязательные строки, совместимыми с NULL в колонках.

Создание и изменение одной карточки сначала блокируют её UUID (в пределах организации),
затем реквизиты. Это позволяет обновлению один раз прочитать карточку FOR UPDATE,
проверить наличие/редакцию, объединить частичные поля и записать composite-параметр.
Проверка редакции и аудит остаются внутри транзакции.

UI также удаляет краевые пробелы и приводит код страны к верхнему регистру для удобства ввода; сервис применяет эти правила независимо от клиента.

В карточке контрагента вкладка «История» показывает создание, изменение реквизитов,
архивирование и восстановление. События идут от новых к старым, по 50 за страницу.
Клик по строке открывает сравнение «До изменения» / «После изменения» на ширину карточки;
неизменённые поля скрыты и доступны по переключателю. Кнопка «К истории» возвращает
к загруженному списку. Автор — сохранённое отображаемое имя проверенной identity.
Для старых событий без имени/полей показано «Имя не сохранено» / «Не сохранено».
В старом аудите предыдущее состояние берётся только из соседней редакции;
при пропуске редакций сравнение с недостоверным снимком не строится.

API `/api/v1/counterparties/history` требует `counterparties.read` и проверяет
принадлежность карточки доступной организации. Курсор `before` — ID события,
лимит 1–100 (по умолчанию 50). Снимки `before`/`after` типизированы, но старые
неизвестные поля не заменяются выдуманными пустыми значениями. Новые изменения
сохраняют имя автора и снимок «до» атомарно с записью данных. Создание и повтор
уже выполненной операции не дублируют события. Миграция V0007 добавляет только
PostgreSQL-тип строки истории и не меняет существующие данные.
