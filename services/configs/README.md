# Сервис configs

Хранит JSON-конфиги в PostgreSQL, проверяет их по общему каталогу схем и выдает
через протокол dynamic-config userver. Каждая публикация создает неизменяемую ревизию.
Сервис включает все схемы из `schemas/configs`, включая автоматические HTTP-настройки.

## Разработка

Из каталога сервиса: `make gen`, `make test-debug`. Из корня:

```sh
make gen SERVICE=configs
make db-up SERVICE=configs
make run-debug SERVICE=configs
```

PostgreSQL из compose доступен на 15434, публичный HTTP — 8090, внутренний listener —
127.0.0.1:8092. Testsuite сам создает отдельную БД; `db-up` для тестов не нужен.
В контейнерном окружении доступны `make docker-test-debug SERVICE=configs`
и аналогичные команды release/sanitize.

Миграции: `postgresql/schemas/db_1/V0001__create_config_revisions.sql`.
Следующие файлы именуются `V0002__migration_name.sql`. `make check-gen-all` проверяет
формат и уникальность версии внутри БД. Testsuite и Docker init применяют SQL к новой
БД по порядку имен. Это не production migration runner: существующий volume не
обновляется при добавлении файла. Для существующей БД миграцию нужно применить явно
перед запуском новой версии. Реестр примененных миграций и checksum пока не реализован.

## Публичный API

- POST `/configs/values`: штатный протокол updater userver; принимает `ids` и
  `updated_since`, возвращает `configs`, `updated_at`, `revision`.
- GET `/configs/status`: текущая ревизия.

Без сохраненной ревизии возвращаются значения из схем с revision=0. Неизвестные
идентификаторы (например, штатные ключи userver вне нашего каталога) пропускаются.
`updated_at` — сортируемый строковый маркер ревизии, а не календарное время.
Текущая реализация возвращает актуальные значения целиком для запрошенных ключей,
даже если клиент уже видел эту ревизию.

## Управление через админку

Изменения доступны только через внутренние `/admin/configs/...` ручки.
Пользователь редактирует значение в админке; на «Готово» создается валидный драфт
одного конфига. Другой пользователь подтверждает его, и он сразу публикуется.
На конфиг допускается один активный драфт. Правки во время редактирования или
проверки защищены версиями; есть отмена, откат одного конфига через драфт и история.

[Полный API, ограничения и примеры](../../docs/config-drafts.md).

Прямых ручек публикации и отката нет: локальные seed и smoke тоже создают и подтверждают драфты.
Идентификация пока передается полем `actor`; аутентификация и роли будут добавлены
до внешнего доступа. Значения конфигов и тела административных запросов не логируются.

Внутренние `/ping` и `/ping/ready` добавляются автоматически. Readiness проверяет БД
и доступ к таблице ревизий. Схемы, C++ API и доставка описаны в
[docs/dynamic-configs.md](../../docs/dynamic-configs.md).
