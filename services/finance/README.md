# Разработка сервиса

Общие инструкции находятся в README корня репозитория и docs/development.md.
В VS Code используйте Dev Containers: Reopen in Container или нативный Clang.

Команды из каталога сервиса перенаправляются в корень монорепозитория:

```sh
make gen
make test-debug
```

Новый API описывается в docs/api. После изменения контракта выполните make gen.
Файлы ручной реализации не перезаписываются; DTO и обработчики создаются в каталоге сборки.
Внутренние /ping и /ping/ready добавляются автоматически при создании сервиса.

Инфраструктура и библиотеки описываются в service.yaml; изменения применяются через make gen.
Структура каталогов: docs/service-layout.md в корне монорепозитория.
Правила manifest и границы генерации: docs/service-manifest.md.

## Входящие и исходящие счета

Счёт оформляет существующие финансовые строки поставок и перевозок. Он не добавляет
доход или расход в сводку повторно. Исходящий счёт включает доходные строки,
входящий — расходные. В одном счёте совпадают контрагент, договор и валюта всех строк;
стороны и банковские счета проверяются через Counterparties и Contracts до транзакции.
Суммы без НДС, НДС и итог рассчитываются сервером по выбранным строкам.

Одна строка целиком включается только в один действующий счёт. Строки блокируются
в порядке UUID; уникальный частичный индекс дополнительно защищает назначение.
При редактировании связанной услуги её снимок, итоги и редакция счёта обновляются в той же транзакции. Для этого требуется право изменения счетов. Архивирование требует сначала исключить услугу из счёта. Исключение
из счёта или архивирование счёта освобождает строку. Снимки строк и история редакций
счёта сохраняются, поэтому последующее изменение услуги не меняет архивный документ.
Сохранение документа, состава строк и истории атомарно; редакция проверяется через CAS.

API `/api/v1/invoices/{list,get,save,candidates,add-service-charge,filter-values}` разделяет права
`finance.read_invoices` и `finance.write_invoices`. Новые права назначаются вручную.
Печатная форма исходящего счёта доступна через `/api/v1/invoices/print-data`
с правом `finance.read_invoices` и ожидаемой редакцией. Первый запрос редакции
фиксирует в БД её реквизиты и строки. Повторные запросы используют снимок:
изменение справочников не меняет уже сформированную редакцию. До первого
формирования требуются права чтения контрагентов и выбранного банковского счёта.
Сетевые запросы выполняются вне транзакции; перед записью редакция проверяется снова.
PDF формируется в Web по снимку, суммы берутся из Finance в валюте счёта.
Новая редакция получает отдельный снимок; шаблон PDF версионируется с Web.

В форме услуги можно выбрать счёт либо подготовить новый без перехода в реестр.
При сохранении сначала сохраняется услуга, затем создаётся/дополняется счёт. Если
второй шаг не удался, форма явно сообщает, что услуга сохранена, и сохраняет выбор
для повторной попытки. Проверка документа по тому же UUID распознаёт потерянный
ответ после успешного commit. Номер и дата счёта возвращаются вместе со списком услуг.

Из формы услуги доступны отвязка и перенос в другой (в том числе новый) счёт.
Связь проверяется по ожидаемому исходному счёту; услуга и затронутые счета блокируются
в постоянном порядке. Состав, итоги и история обоих счетов меняются атомарно.
После отвязки счёт может остаться без услуг, с нулевой суммой; он не удаляется.

## История финансовых документов

`/api/v1/service-charges/history`, `/api/v1/invoices/history` и
`/api/v1/payments/history` показывают различия сохранённых редакций. Права совпадают
с чтением соответствующего документа. История ограничена текущей организацией;
связанные счета/оплаты показываются только с правом их чтения.

В услуге видны включение в счёт, отвязка и освобождение через архивирование счёта.
В счёте — изменения его строк, распределение и отмена оплаты. Платёж показывает
изменения распределения по каждому счёту. Несвязанные изменения других оплат не
попадают в ленту. Курсор включает время, источник, UUID и редакцию, чтобы события с
одинаковым временем не терялись при подгрузке.

Новые снимки хранят имя автора. Для старых записей Web пытается показать текущее имя
профиля, а если профиль недоступен — сохранённый идентификатор.
При пропуске предыдущей редакции состояние «до» не выдумывается. Исторические суммы
берутся из снимков. Номера счетов в истории распределения платежа подставляются из
текущего справочника счетов; сама связь сохраняется по UUID. Миграция V0013 добавляет
GIN-индексы для поиска связанных документов в истории.
