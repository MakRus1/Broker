# Уведомления

Первый рабочий сценарий — изменение маршрута поставки. Источник — `shipments`,
получатель личного уведомления — назначенный поставке логист на момент изменения.
Создание поставки и изменение её остальных полей уведомление не создают.
Если логист не назначен или сам является автором изменения, факт события всё равно
сохраняется без личного уведомления.

## Доставка и повторные запросы

Shipments пишет `notifications.publish` в стандартный outbox в одной транзакции
с изменением поставки. Существующий `TransportationDispatcher` регистрирует ещё
один обработчик в общей библиотеке outbox. Дополнительного периодика нет.

Служебный клиент `shipments-dispatcher` передаёт типизированное событие в
`POST /api/internal/v1/events/publish`. Пользовательский токен
не подходит даже при наличии одноимённого права: проверяются право и client ID.

Ключ события — отправитель, организация и постоянный `id` события.
Поставки формируют `id` из организации, ID поставки и ревизии.
Общий конверт содержит `id`, `type`, `version`, `organization_id` и `payload`.
Сейчас поддерживается `shipment.route_changed`, версия 1. `PublishedEvent` —
`oneOf` типизированных конвертов. У `ShipmentRouteChanged` поля `type` и `version`
заданы singleton-enum, а `payload` имеет тип `ShipmentRouteChangedPayload`.
Организация находится только в конверте. Кодген проверяет все обязательные поля,
типы, ограничения, неизвестные поля и ровно один подходящий вариант до вызова ручки.
Для разных версий одного события можно добавить отдельные варианты с одинаковым
`type` и разными `version`; отдельный discriminator для этого не нужен.

После проверки контракта `std::visit` выбирает типизированные `Validate` и `Apply`.
Отдельного реестра типов, ручного разбора JSON и строковых сравнений type/version нет.
Авторизация отправителя и проверка контекста выполняются до транзакции, затем приём
и создание личного уведомления выполняются в одной транзакции. Подтверждение
отправляется после commit. Повтор с тем же содержимым возвращает успех;
тот же ключ с другим содержимым возвращает `409 event_conflict`.
Запись `notification_events` сохраняется после прочтения и очистки уведомления.
Удаление этого журнала без отдельной политики дедупликации недопустимо.

Для первого сценария обработка короткая и полностью локальная: отдельный
асинхронный worker внутри notifications пока не нужен. Внешние обращения
и почтовая отправка в транзакции приёма запрещены.

## Web

`POST /api/v1/notifications/list` и `/read` принимают организацию, но не получателя.
Issuer и subject берутся из проверенного токена. Дополнительно сервис организаций
проверяет действующее членство и право `shipments.read` перед каждым чтением
или изменением. Отзыв прав закрывает доступ и к уже сохранённым сообщениям.

Список использует пагинацию `(created_at, id)`; курсор проверяется в области
текущего получателя и организации. Это история, не журнал доставки с гарантией
порядка коммитов. Web обновляет последние 100 записей целиком, без курсора
«последний увиденный ID», поэтому поздний commit попадёт в следующий опрос.

Центр уведомлений опрашивает сервер примерно каждые 20 секунд с jitter,
останавливается в скрытой вкладке, не выполняет параллельных опросов и увеличивает
паузу при ошибках. После возврата на вкладку делает новый запрос.
Новые непрочитанные события после первой загрузки всплывают на 7 секунд;
первоначальная история не всплывает. Максимум три всплывашки на пачку, остальные
события остаются в центре. Повторный опрос и смена языка их не показывают заново.
Переход ведёт прямо на маршрут поставки, в том числе в уже открытой карточке.
Прочтение и очистка сохраняются на сервере по явному списку показанных ID.
Обычные сообщения об успехе/ошибках интерфейса остаются локальными.

## Границы первой реализации

Это не клиентская email-рассылка: почтовый транспорт, настраиваемые правила,
шаблоны, расписания и генерация отчётов ещё не реализованы. Пока действует
фиксированное правило «изменение маршрута → назначенный логист».
События без получателя не переигрываются автоматически при изменении правила.
Доставка разных ревизий может завершаться не по порядку; каждая сохраняется отдельно.

Перед расширением на внешнюю отправку нужно добавить постоянную очередь доставок,
разделение временных/окончательных ошибок, повторный запуск и мониторинг backlog.
Для расписаний — ревизии, отмену не начатых запусков и снимки параметров запущенных.
Архитектура: [RFC](../../docs/architecture/notifications-rfc.md).

## Проверка

`make docker-test-debug SERVICE=notifications` — реальные PostgreSQL и HTTP:
параллельные повторы, поздний повтор после прочтения/очистки, конфликт содержимого,
изоляция получателей/организаций, отзыв права, пагинация и проверка service client.

`make docker-test-debug SERVICE=shipments` проверяет сохранение события при изменении
маршрута и повтор после ошибки приёмника. Общие rollback/lease-сценарии проверяются
существующими тестами библиотеки outbox.


## Добавление нового события

1. Описать payload и полный конверт в OpenAPI. У `type` и `version` — singleton-enum
   с default для удобного создания C++-модели; на HTTP-границе эти поля обязательны.
   Добавить ссылку на конверт в `PublishedEvent.oneOf` и запустить кодген.
2. Добавить перегрузки `Validate(identity, const NewEvent&)` и
   `Apply(transaction, const NewEvent&)`, подключить файл в `events/publish.hpp`.
   `Validate` проверяет доверенного отправителя, право и контекст. `Apply` выполняет
   только локальные записи. Если перегрузки забыты, обработчик variant не соберётся.
   Для нового отправителя также изменить декларацию служебного доступа.
3. В сервисе-источнике создать типизированный конверт, обернуть в `PublishedEvent`
   и записать в стандартный outbox вместе с бизнесовым изменением. ID должен быть
   постоянным для одного события, включая все повторы.

Пример отправителя (namespace `events` — модели сгенерированного клиента notifications):

```cpp
const events::PublishedEvent event{
    .value = events::ShipmentRouteChanged{
        .id = stable_id, .organization_id = organization, .payload = payload}};
platform::outbox::Enqueue(transaction, kPublishNotificationEvent, stable_id,
    userver::formats::json::ValueBuilder(event).ExtractValue());
```

`type` и `version` берутся из defaults типизированной модели. Для всех событий
notifications используется один topic `notifications.publish` и один обработчик
доставки, вызывающий ту же ручку. В shipments он уже зарегистрирован. В новом
сервисе нужно один раз подключить стандартные таблицу/компонент outbox, HTTP-клиент
notifications и обработчик доставки; собственный периодик и SQL повторов не нужны.
Отдельной библиотеки событий поверх outbox пока нет.

Внутри notifications до транзакции проверяются контекст и сериализуется событие.
В транзакции — INSERT журнала с дедупликацией, проверка совпадения содержимого при
повторе и `Apply` только для нового события. Подтверждение возвращается после commit.
HTTP-ручка не знает отдельных видов событий. Для тяжёлых правил, внешней отправки
и email `Apply` должен записывать локальное задание, а выполнять его нужно вне этой
транзакции; такого конвейера в первой реализации ещё нет.
