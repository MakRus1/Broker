# Разработка сервиса

Общие инструкции находятся в README корня репозитория и docs/development.md.
В VS Code используйте Dev Containers: Reopen in Container или нативный Clang.

Команды из каталога сервиса перенаправляются в корень монорепозитория:

```sh
make gen
make test-debug
```

Новый API описывается в docs/api. После изменения контракта выполните make gen.
Файлы ручной реализации не перезаписываются; DTO и обработчики создаются в каталоге сборки.
Внутренние /ping и /ping/ready добавляются автоматически при создании сервиса.

Инфраструктура и библиотеки описываются в service.yaml; изменения применяются через make gen.
Структура каталогов: docs/service-layout.md в корне монорепозитория.
Правила manifest и границы генерации: docs/service-manifest.md.

## Автоматическое обновление аэропортов

Компонент `airport-sync` загружает CSV [OurAirports](https://ourairports.com/data/)
после запуска сервиса и далее раз в сутки. Источник бесплатный (Public Domain),
обновляется ежедневно и не гарантирует полноту или точность. В импорт входят
`large_airport`, `medium_airport`, `small_airport` с IATA или ICAO. Признак
`scheduled_service` не используется: отсутствие регулярных пассажирских рейсов
не исключает грузовой аэропорт. Вертодромы, закрытые аэропорты и площадки без
этих кодов автоматически не добавляются; ручное добавление остаётся доступным.

Фронтенд ищет в локальной БД, без обращения к OurAirports. Поиск учитывает
название, IATA, ICAO, город и ключевые слова поставщика. В карточке показывается
IATA, при его отсутствии — ICAO. Оба кода хранятся раздельно в `airport_sources`.
`ident` не принимается за ICAO.

Постоянный ID OurAirports определяет стабильный UUID новой записи. При первом
импорте уже существующий аэропорт связывается по точному коду и стране.
Ручные записи, перенесённые справочники и правки администратора сохраняют свои
название, страну, код и состояние архива при последующих обновлениях. Для
автоматически созданных и ещё не изменённых записей эти поля обновляются из
источника. Удаление строки из выгрузки не удаляет аэропорт из Broker.

Полная выгрузка проверяется до записи: обязательные колонки, CSV, ID, коды,
дубли, минимальный объём и сокращение числа аэропортов не более чем на 20%.
Обновление источника и поискового справочника коммитится одной транзакцией.
Любая ошибка оставляет предыдущую версию доступной. Транзакция не удерживается
во время HTTP-запроса и разбора CSV.

Несколько подов координируются через `directory_sync`: атомарно берут аренду на
время, достаточное для HTTP-попыток и публикации (не менее пяти минут),
перед публикацией проверяют её под блокировкой строки. По умолчанию после
успеха следующая загрузка назначается через сутки, после ошибки — через пять минут. Компонент проверяет расписание каждую минуту. В `directory_sync` остаются
время успешного импорта, SHA-256 и число записей; ошибки и успешные обновления
видны в логах компонента.

Настройки находятся в статическом компоненте `airport-sync`: `url`,
`minimum-records`. Переменная `airport-sync-enabled` включает компонент через
`load-enabled`; по умолчанию он включён, в testsuite выключен. Функциональные
тесты включают его с локальным mockserver и не ходят в интернет.

## Автоматическое обновление морских портов

Компонент `sea-port-sync` раз в сутки проверяет официальные выпуски
[UN/LOCODE](https://unlocode.unece.org/publications/). Выбирается самый новый тег
вида `YYYY-1` или `YYYY-2` официального репозитория; предварительные версии
(`latest`, `rc` и т. п.) не используются. Три CSV-части скачиваются напрямую
из артефактов этого выпуска, без распаковки ZIP и новых системных зависимостей.

В справочник входят записи с морской функцией `1` и статусами
`AM`, `RL`, `AA`, `AC`, `AF`, `AI`, `AS`, `AQ`, `RN`. Пометки удаления `X`,
ссылочные строки `=`, неподтверждённые/неизвестные статусы и пункты только
с речной функцией `8` исключаются. LOCODE обозначает транспортный населённый
пункт с портом; конкретный терминал по-прежнему выбирается как контрагент.
Справочник не гарантирует наличие всех терминалов или возможность обработки
конкретного груза.

Новый порт получает полный пятисимвольный LOCODE, например `NLRTM`.
Ручной порт связывается по полному коду или трёхсимвольной части вместе со
страной. При нескольких совпадениях объединение не выполняется; конфликт
при публикации откатывает весь импорт. UUID остаётся постоянным при
обновлении названия. Ручные изменения и архивирование сохраняют приоритет.

В исходнике встречаются несколько названий одного LOCODE. Актуальное
выбирается по дате записи, затем по пометке переименования `#`; при равенстве
порядок сравнения названий обеспечивает воспроизводимость. Остальные
названия и варианты без диакритики сохраняются в поисковых терминах.
Названия преимущественно латиницей; автоматического перевода нет.

Расписание и аренды двух источников находятся в `directory_sync` и независимы
по ключам `ourairports` и `unlocode`. Как у аэропортов, данные публикуются
одной транзакцией после скачивания и проверки полного набора. Ошибки HTTP,
CSV, подозрительное сокращение более чем на 20% или конфликт в БД не меняют
предыдущий набор. Пропавшие записи не удаляются. Сохраняются тег выпуска,
SHA-256, количество записей и время успешной публикации.

Компонент включается через `sea-port-sync-enabled`; testsuite использует
mockserver. Настройки `releases-url`, `download-base-url` и
`minimum-records` находятся в статическом конфиге сервиса. Ключ API не нужен.

Условия источника: UNECE описывает UN/LOCODE как общедоступный справочник
([история](https://unece.org/trade/uncefact/unlocode/history-1981)), но
[Terms сайта](https://unlocode.unece.org/terms/) ограничивают использование
материалов личными некоммерческими целями, а подвал заявляет CC BY 4.0 для
стандартов UN/CEFACT. Применимость этой лицензии именно к данным не удалось
однозначно подтвердить. Для текущего некоммерческого MVP используем официальный
источник с указанием происхождения; до коммерческого запуска нужно уточнить
условия использования данных у UNECE. Выгрузка в репозиторий не включается.

## Автоматическое обновление железнодорожных станций

`railway-sync` раз в неделю получает мировую выгрузку OpenStreetMap через
[QLever](https://wiki.openstreetmap.org/wiki/QLever). Выбираются объекты
`railway=station` и `railway=yard`; метро и другие городские системы исключены.
Это общий географический справочник, а не официальный перечень грузовых станций:
в нём есть пассажирские станции и отдельные парки. Полнота по странам различается.

У станции внутренний UUID, коды ЕСР и UIC необязательны. UUID импорта зависит
от OSM-объекта и сохраняется при смене имени или кода. Разные объекты не объединяются
по совпадению имени или кода. Объекты с неоднозначной страной не публикуются.
Существующие ручные записи сохраняют свой UUID; импорт их автоматически не объединяет.

`esr:user` — [подсказка валидатора OSM](https://wiki.openstreetmap.org/wiki/Key:esr:user),
а не подтверждённый код ЕСР. Такой код имеет `esr_source=osm_hint` и отмечается в UI.
Ручное сохранение помечает источник кода как `manual`. Правки и архивирование
имеют приоритет над последующими импортами. Пропавшие из источника записи
автоматически не удаляются: сохранённые маршруты продолжают ссылаться на них.

Скачивание и разбор выполняются до транзакции. Аренда источника в `directory_sync`
защищает от параллельной публикации. Ошибка, неполная выгрузка, достижение лимита
200 000 строк или сокращение количества записей более чем на 20% оставляют
справочник без изменений. Успешная публикация назначает следующую попытку через
семь дней; повторы после ошибок управляются динамическими настройками.

Настройки: `railway-sync-enabled`, `url`, `minimum-records`.
Публичный QLever не гарантирует доступность; при его недоступности поиск использует
уже загруженные данные. OSM распространяется под ODbL, атрибуция —
[© участники OpenStreetMap](https://www.openstreetmap.org/copyright).
Данные выгрузки в Git не хранятся.

## Динамические настройки синков

Для каждого источника в Configs предусмотрен отдельный ключ:

- `AIRPORT_SYNC_SETTINGS` — OurAirports;
- `SEA_PORT_SYNC_SETTINGS` — UN/LOCODE;
- `RAILWAY_SYNC_SETTINGS` — OSM.

Значения по умолчанию и допустимые диапазоны описаны в
`schemas/configs/transport_locations/`. Создайте нужный конфиг через админку;
публикация новой ревизии не требует перезапуска сервиса. Пока ключ не создан,
используются встроенные значения. Сначала нужно выкатить Configs с новым каталогом.

Пример для железнодорожных станций:

```json
{
  "enabled": true,
  "period_seconds": 604800,
  "http_timeout_ms": 90000,
  "http_retries": 0,
  "retry_initial_seconds": 300,
  "retry_max_seconds": 3600
}
```

`http_retries` — дополнительные попытки одного HTTP-запроса. При неуспехе
всего синка следующее выполнение откладывается на `retry_initial_seconds`,
затем задержка удваивается до `retry_max_seconds`. Попытки продолжаются
до успеха или выключения источника; успешная публикация сбрасывает счётчик.

Планировщик проверяет настройки раз в минуту. Изменение периода и задержек
учитывается и для уже запланированного запуска. Пауза не прерывает текущую
работу; её снимок настроек действует до завершения. Действующая аренда
другого пода не отбирается при изменении параметров. После падения пода
повтор возможен по истечении аренды. Расписание, счётчик ошибок и последняя
успешная публикация хранятся в `directory_sync`.
